# Arc F — TUI 120 fps — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The owner asked for 120 fps (2026-09-25 ruling F1) and for the engine's progress-report gate to become a knob. Three changes and one sweep. The TUI's one `tea.NewProgram` call gains `tea.WithFPS(120)` — bubbletea's own ceiling — instead of taking its default 60. The TUI's fast progress tick drops from 16 ms to 8 ms, so a progress change can reach the screen on the next frame instead of waiting out a beat that is now twice as long as one. And `ProgressTracker`'s hard-coded 16 ms report gate becomes `downloader.progress_interval_ms`, read per job from the worker's config snapshot, so 8 ms can be tried on one machine without a rebuild. The standing rule holds throughout: updates get cheaper or more frequent, never rarer.

**Architecture:** One arc, one worktree, five tasks run in order. Task 1 is `internal/config` alone (the key, its default, its validation, its documentation in `config.example.toml`). Task 2 is `internal/worker` alone (the tracker reads the interval; the plumbing from `buildJobContext`'s config snapshot through `JobConfig` to both `NewProgressTracker` sites; a fake-clock burst test). Task 3 is `internal/tui` alone (the renderer option, the 8 ms tick, two pins). Task 4 is the prose: `SPEC.md`, four `docs/spec/*.md`, and the code comments in `internal/web` and `internal/tui` that name a number this arc invalidated. Task 5 merges `main`, runs the merge-candidate gates and deletes this plan.

Tasks 1 → 2 → 3 is a dependency chain by signature, not by convenience: Task 2's `buildJobContext` reads the field Task 1 declares, and Task 2's default-agreement pin reads `config.Defaults()`. Task 3 is independent of both and could run first; it is placed third so the one task that touches `internal/tui` lands after the two that cannot. Task 4 depends on all three having landed, because it describes what they did.

Nothing here is a rewrite. Task 1 adds one struct field, one default and one validation block in the shape Arc B's reorder keys established on 2026-09-24. Task 2 adds one parameter, two fields and one clock seam; the gate's arithmetic is untouched. Task 3 changes two literals. Task 4 changes only prose.

**Tech Stack:** Go 1.27 (`toolchain go1.27.1`), no CGo, pure-Go dependencies. `charm.land/bubbletea/v2 v2.0.9` drives the TUI — its `WithFPS` option, `defaultFPS = 60` and `maxFPS = 120` live in `options.go:142` and `renderer.go:13-14`, and the clamp runs inside `NewProgram` (`tea.go:634-638`), which is what makes Task 3's behavioural pin possible. `modernc.org/sqlite` behind `internal/database` for Task 2's burst counter. `BurntSushi/toml` behind `config.Save`/`config.Load` for Task 1's round-trip. Node 24 for `web/tests` (gates only; this arc touches no JS). Git Bash on Windows for every command below.

**Spec:** `docs/superpowers/specs/2026-09-25-tui-120fps-and-chat-cards-design.md` — §0 F1 (the owner's ruling verbatim), §1 (Arc F: today, the four changes, and the Constraints paragraph copied verbatim below), §3 (order: `tui-120fps` and `chat-cards` run in parallel from main `aa91c748`; the second to merge merges `main` first; `docs/spec/user-interfaces.md` is the one file both arcs touch, in different sections). ### Task 1: `downloader.progress_interval_ms`

Spec §1 change 3, first half. A new integer-milliseconds key on `DownloaderConfig`, default 16, minimum 1, no maximum, in the shape Arc B's `reorder_buffer_mb` / `reorder_budget_mb` established on 2026-09-24 — **minus** the two Settings rows and the Web validator arm, by the owner's ruling. The closest existing precedent for a config-file-only key is `cookies.dpapi_profile_dir` (`internal/config/types.go:284`): declared, validated, documented in `config.example.toml` and in the `docs/spec/data-and-storage.md` table, and reachable from nothing but a text editor.

One difference from the reorder pair is worth stating in the code: on those two, `0` is the documented "unbounded" value and only a negative is an error. Here `0` is **not** legal. An ungated `ProgressTracker` would write the database once per arriving segment callback, on every download at once, which is the exact failure the gate exists to prevent — so anything below 1 ms resets to the default.

**Files:**
- Modify: `internal/config/types.go`
- Modify: `internal/config/config.go`
- Modify: `config.example.toml`
- Create: `internal/config/progress_interval_test.go`

**Interfaces:**
- Produces: `DownloaderConfig.ProgressIntervalMS int` (TOML `progress_interval_ms`, JSON `progress_interval_ms`), default 16, consumed in Task 2 by `buildJobContext`.
- Consumes: nothing new. `Defaults()`, `validateOrNormalize`, `Save`, `Load` are all already in this file.

**Ruling — an `int` of milliseconds, not a `FlexDuration`.** `FlexDuration` exists for the keys an operator writes as `"30d"` or `"2m"` and whose unit is minutes or days (`interruption_timeout`, `probe_cooldown`, `hide_finished_age_days`). This value's whole point is that it is a small integer count of milliseconds compared against a frame budget; `SegmentWorkers`, `MaximumTimeout` and the two reorder ceilings are all plain ints for the same reason. Why: a `FlexDuration` here would invite `"8ms"` and `"0.008"` as synonyms and add a parse path to a value read once per job. Cost if wrong: a later migration converting `int` → `FlexDuration`, which `migrateOldFormat` already has the shape for.

**Ruling — no accessor method on `DownloaderConfig`.** `ReorderLimitBytes()` exists because two keys have to be reconciled against each other. This one is converted at exactly one site (`buildJobContext`, Task 2), so a `ProgressInterval() time.Duration` method would be a second place for the `< 1` rule to live and disagree with `Validate`. Why: one conversion, one rule. Cost if wrong: one method, added when a second consumer appears.

```go
package config

import (
	"path/filepath"
	"strings"
	"testing"
)

// TestProgressIntervalDefault pins the default the whole arc is calibrated
// against: 16 ms, the value ProgressTracker's gate carried as a constant
// before it became configurable, so an operator who never writes the key
// keeps exactly today's ~60 reports/second per job.
//
// MUTANT: leaving ProgressIntervalMS out of the Defaults() literal — it reads
// 0 here, and every job would then take NewProgressTracker's fallback rather
// than a value anyone can see in the config.
func TestProgressIntervalDefault(t *testing.T) {
	if got := Defaults().Downloader.ProgressIntervalMS; got != 16 {
		t.Errorf("default ProgressIntervalMS = %d, want 16", got)
	}
}

// TestProgressIntervalValidation mirrors SegmentWorkers' clamp style rather
// than the reorder ceilings': 0 is NOT a documented "disabled" value here.
// An ungated ProgressTracker writes the database once per arriving segment
// callback on every download at once, which is what the gate exists to
// prevent — so anything below 1 ms is an error that resets to the default.
// There is deliberately no maximum: progress_interval_ms = 1000 is a
// once-a-second progress line, which is slow but legal.
//
// MUTANT: writing the guard as `< 0` (the reorder ceilings' shape) — the
// "zero" row then keeps 0 and fails. MUTANT: adding an upper clamp — the
// 1000 row fails. MUTANT: resetting to a literal 16 instead of
// defaults.Downloader.ProgressIntervalMS — passes today and silently
// diverges the moment the default moves, which is why
// TestProgressIntervalDefault above is a separate assertion.
func TestProgressIntervalValidation(t *testing.T) {
	tests := []struct {
		name string
		in   int
		want int
	}{
		{"zero falls back to the default", 0, 16},
		{"negative falls back to the default", -8, 16},
		{"one millisecond is honoured", 1, 1},
		{"the eight-millisecond knob is honoured", 8, 8},
		{"the default", 16, 16},
		{"a slow value is NOT clamped", 1000, 1000},
	}
	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			cfg := Defaults()
			cfg.Downloader.ProgressIntervalMS = tc.in
			Normalize(cfg)
			if got := cfg.Downloader.ProgressIntervalMS; got != tc.want {
				t.Errorf("ProgressIntervalMS = %d, want %d", got, tc.want)
			}
		})
	}
}

// TestProgressIntervalValidateReportsWithoutMutating pins the other half of
// the validateOrNormalize contract (DECISIONS #9): Validate REPORTS, Normalize
// REWRITES. Save runs Validate and refuses to write a failing config, so the
// error text is what an operator sees when a hand-edited 0 blocks their next
// settings save — it has to name the key.
//
// MUTANT: calling fail() outside the reportOnly branch or forgetting the
// `if !reportOnly` guard around the assignment — cfg is mutated here and the
// second assertion fails. MUTANT: a message that does not name the key (e.g.
// "progress interval too small") — the Contains assertion fails.
func TestProgressIntervalValidateReportsWithoutMutating(t *testing.T) {
	cfg := Defaults()
	cfg.Downloader.ProgressIntervalMS = 0

	errs := Validate(cfg)
	if len(errs) == 0 {
		t.Fatal("Validate accepted progress_interval_ms = 0")
	}
	var joined []string
	for _, err := range errs {
		joined = append(joined, err.Error())
	}
	all := strings.Join(joined, "\n")
	if !strings.Contains(all, "downloader.progress_interval_ms") {
		t.Errorf("no error named the key:\n%s", all)
	}
	if cfg.Downloader.ProgressIntervalMS != 0 {
		t.Errorf("Validate mutated cfg: ProgressIntervalMS = %d, want the offending 0 left alone",
			cfg.Downloader.ProgressIntervalMS)
	}
}

// TestProgressIntervalRoundTripsThroughSave proves Save accepts the 8 ms
// value the owner asked to be able to try, and that Load reads it back. Save
// validates first and REFUSES a failing config, so a value the validator did
// not know would make every subsequent settings save fail — losing every
// other edit in the same save. The same pin CookiesAcquisition carries.
//
// MUTANT: a toml tag that does not match the documented key (e.g.
// `progress_interval`) — Save writes one spelling and Load looks for another,
// so the reloaded value is the default 16 and this fails.
func TestProgressIntervalRoundTripsThroughSave(t *testing.T) {
	dir := t.TempDir()
	path := filepath.Join(dir, "config.toml")
	cfg := Defaults()
	cfg.Downloader.ProgressIntervalMS = 8
	if err := Save(cfg, path); err != nil {
		t.Fatalf("Save refused a legal progress_interval_ms: %v", err)
	}
	reloaded, err := Load(path)
	if err != nil {
		t.Fatal(err)
	}
	if reloaded.Downloader.ProgressIntervalMS != 8 {
		t.Errorf("progress_interval_ms round-tripped as %d, want 8",
			reloaded.Downloader.ProgressIntervalMS)
	}
}
```

### Task 2: the tracker reads the interval

Spec §1 change 3, second half, and change 4's first test. `ProgressTracker.maybeUpdate` gates on the package constant `progressUpdateInterval` (`internal/worker/progress.go:15`, gate at `:483`). It must gate on a per-tracker value that came from `downloader.progress_interval_ms`.

**The plumbing, traced.** The orchestrator holds no config at all — `DownloadOrchestrator` (`internal/worker/orchestrator.go:141`) has a db, a queue, solvers, a notifier and a muxer, and its one hot-reloadable value (`ffmpegPath`) arrives through a setter. What it does have at both `NewProgressTracker` sites is `jobCtx`, and `JobContext.Config` is `*JobConfig` — the per-job snapshot `DownloadWorker.buildJobContext` (`internal/worker/worker.go:1084`) takes under `readConfig`, which is `configStore.Read` once the store is wired and a direct read of `w.cfg` during early init. `MaximumTimeout`, `SegmentWorkers` and `InterruptionTimeout` already ride that snapshot to exactly these call sites. So: one more field on `JobConfig`, one more line in the `readConfig` closure, one conversion in the literal, and a fourth parameter on `NewProgressTracker`. That is the least invasive path, and the compiler finds every construction site for us.

**Ruling — a fourth positional parameter, not a setter.** `NewProgressTracker` has three call sites in the whole repo (`orchestrator.go:384`, `orchestrator_twitch.go:314`, and `newDBProgressTracker` in `progress_activity_ticker_test.go:26`). A parameter makes the compiler enumerate them; a `SetUpdateInterval` setter would compile fine at a site that forgot to call it, and the tracker would silently run at the default. Why: three sites is few enough that the churn is trivial and a missed site is the only real risk. Cost if wrong: a fourth parameter to change again if a fifth knob appears — at which point an options struct is the answer, not a setter.

**Ruling — `progressUpdateInterval` keeps its name and becomes the default.** `defaultProgressInterval` would read better, but `docs/spec/architecture.md:593` and `docs/spec/user-interfaces.md:601` cite the constant by name beside `internal/worker/progress.go`, and Task 4 is the task that rewrites those sentences. Renaming here would leave the citation gate red between Task 2 and Task 4 for no behavioural gain. Why: the name is load-bearing in two docs and the comment can carry the meaning instead. Cost if wrong: a rename commit later, which is a `git grep` and four lines.

**Ruling — the clock seam is a struct field, not a package-level `var now`.** `internal/twitch/emotes.go:47` (`EmoteResolver.now func() time.Time`, assigned `time.Now` in the constructor, "production never assigns it"), `internal/monitor/backfill.go:220` and `internal/logger/logger.go:78` all use the field shape. A package-level var in `internal/worker` would be shared by every test in a package that runs `t.Parallel()` subtests today, and `go test -race` would report the swap against any tracker a neighbouring test left running. Why: the repo has a precedent and it is the safe one. Cost if wrong: none — a field can always be lifted to a var.

**Ruling — ALL SIX in-lock `time.Now()` reads move to `pt.now()`, not just the gate's.** `progress.go` reads the wall clock at `:141` and `:201` (the two `OnProgress` closures' `lastSegmentAt`), `:251` (`noteFetch`'s `lastFetchAt`), `:286` (`setActivity`), `:440` (`activityRefreshLoop`) and `:482` (`maybeUpdate`'s gate). // fakeClock is a hand-advanced clock for the burst below. ProgressTracker
```go
// reads the wall clock only through pt.now, and only under pt.mu, so a test
// that installs this must hold pt.mu to swap it and to advance it.
type fakeClock struct{ t time.Time }

func (c *fakeClock) now() time.Time { return c.t }

func (c *fakeClock) advance(d time.Duration) { c.t = c.t.Add(d) }

// The synthetic burst: 160 events one fake millisecond apart. Chosen so both
// intervals under test divide it exactly — a 16 ms gate admits 10 of them and
// an 8 ms gate admits 20 — which makes the expected counts arithmetic rather
// than a tolerance band.
const (
	burstStep  = time.Millisecond
	burstSteps = 160
)

// reportsInOneBurst drives burstSteps chat-count updates through a tracker
// built with the given interval, advancing a fake clock by burstStep before
// each one, and returns how many DB writes came out the other end.
//
// The count is taken at the database's OnJobUpdate fan-out rather than by
// watching the job row, because maybeUpdate writes the same columns every
// time and a row cannot say how often it was written. UpdateJobFields
// notifies inline on the calling goroutine (internal/database/database.go:404
// releases db.mu and then calls notifyJobUpdate), so the counter needs no
// synchronisation and the total is exact rather than eventually-consistent.
//
// No activity is ever set, so ensureActivityTickerLocked never fires and this
// tracker owns no goroutine: the fake clock has exactly one reader.
func reportsInOneBurst(t *testing.T, interval time.Duration) int {
	t.Helper()
	db, err := database.Open(filepath.Join(t.TempDir(), "burst.db"))
	if err != nil {
		t.Fatalf("database.Open: %v", err)
	}
	t.Cleanup(func() { db.Close() })
	if _, err := db.AddJob(&database.Job{ID: "burst", Status: database.StatusDownloading}); err != nil {
		t.Fatalf("AddJob: %v", err)
	}

	reports := 0
	t.Cleanup(db.OnJobUpdate(func(*database.Job) { reports++ }))

	pt := NewProgressTracker(db, "burst", nopProgressLogger{}, interval)
	t.Cleanup(pt.Close)

	clk := &fakeClock{t: time.Date(2026, 9, 25, 12, 0, 0, 0, time.UTC)}
	pt.mu.Lock()
	pt.now = clk.now
	// The constructor stamped these from the real clock; re-stamp them onto
	// the fake one so the first gate comparison starts from t0.
	pt.lastUpdate, pt.lastPersist, pt.startTime = clk.t, clk.t, clk.t
	pt.mu.Unlock()

	for i := 1; i <= burstSteps; i++ {
		pt.mu.Lock()
		clk.advance(burstStep)
		pt.mu.Unlock()
		pt.SetChatCount(i)
	}
	return reports
}
```

### Task 3: the renderer at 120 fps and the 8 ms tick

Spec §1 changes 1 and 2. Two literals and two pins.

**The renderer.** `Run` (`internal/tui/app_commands.go:675`) calls `tea.NewProgram(app)` with no options, so bubbletea applies `defaultFPS = 60`. `tea.WithFPS(120)` is the whole change; 120 is `maxFPS`, bubbletea's own ceiling (`charm.land/bubbletea/v2@v2.0.9/renderer.go:13-14`), so there is nothing above it to ask for. The clamp runs inside `NewProgram` (`tea.go:634-638`), not at `Run` time, which is what makes the behavioural pin below cheap: constructing a `Program` is enough to observe the stored value.

**The tick.** `progressFastInterval = 16 * time.Millisecond` (`internal/tui/app.go:980`) is the progress-tick cadence while a download delivers. At 120 fps a frame is 8.33 ms, so a 16 ms tick lets a progress change sit for up to a whole extra frame before the model even hears about it. 8 ms is one tick per frame. The idle 500 ms class and the phase-locked 1 Hz `tickMsg` are untouched, and so is every assertion in `tick_lifecycle_test.go` — it compares `app.progressInterval` against the constants, not against literals.

**Why the extra ticks are free.** `JobDetailsModel.SetProgress` (`internal/tui/job_details.go:178`) returns immediately when the `*ProgressData` pointer and the wall-clock second are both unchanged, and `handleJobUpdate`'s display/tally gates already refuse to rebuild on a no-change write. A tick that finds nothing new therefore does the same nothing it did at 16 ms, and bubbletea renders a frame only when the view actually changed. The FrameCost pins are the measurement of that claim and must hold unchanged at `-count=5`.

**Ruling — an AST pin plus a behavioural pin, not a source-text grep and not a `newProgram` seam.** `tea.Program.fps` is unexported and bubbletea exposes no getter, so a seam that "returns the options" would hand the test a `ProgramOption` closure it cannot look inside — it would assert a number the production code might not pass. Two assertions get the real thing instead:

1. **AST** (`go/parser` + `go/ast`, the shape `internal/web/routes/cookies_import_callsite_test.go` already uses in this repo): package `tui` contains exactly ONE `tea.NewProgram` call in non-test source, and its second argument is `tea.WithFPS(tuiTargetFPS)`. This is what stops a future edit constructing a second, optionless Program.
2. **Behavioural**: build a real `*tea.Program` with that option and read `fps` back through `reflect` + `unsafe`, asserting 120 — and build one WITHOUT the option and assert 60, so a read that silently returned a constant could not pass. This is what catches a dependency bump that lowers `maxFPS` or renames the field, which the AST pin cannot see.

`unsafe` appears nowhere else in `internal/tui`, and that is worth stating: it is confined to one test helper, reads one int, and was verified vet-clean and staticcheck-clean during planning (`go vet` accepts `unsafe.Pointer(f.UnsafeAddr())` in a single expression; splitting it across statements is the form the `unsafeptr` analyzer rejects). Why both: the AST pin proves the call site, the behavioural pin proves the effect, and each is blind to the other's regression. Cost if wrong: the behavioural pin fails loudly with a message naming the field, and a maintainer deletes eight lines.

```go
func isSelectorCall(fun ast.Expr, pkg, name string) bool {
	sel, ok := fun.(*ast.SelectorExpr)
	if !ok || sel.Sel.Name != name {
		return false
	}
	ident, ok := sel.X.(*ast.Ident)
	return ok && ident.Name == pkg

		t.Fatalf("glob package sources: %v", err)

		if strings.HasSuffix(name, "_test.go") {

// is unexported and there is no getter, but NewProgram resolves it eagerly
// (charm.land/bubbletea/v2 tea.go: below 1 becomes defaultFPS, above maxFPS is
// clamped to it), so constructing a Program is enough to observe the value the
// renderer will use. reflect.NewAt in a single expression is the form go vet's
// unsafeptr analyzer accepts.
func programFPS(t *testing.T, p *tea.Program) int {
	t.Helper()
	f := reflect.ValueOf(p).Elem().FieldByName("fps")
	if !f.IsValid() {
		t.Fatal("charm.land/bubbletea/v2's Program has no fps field any more — re-point this pin at whatever replaced it")
	}
	return int(reflect.NewAt(f.Type(), unsafe.Pointer(f.UnsafeAddr())).Elem().Int())
}
```
