## 0. The four items (verbatim from the chain's Fable reviews)

1. **`writeDescriptionAtomic` adopts `utils.WriteFileAtomic`.** Arc U's close review found it as a same-shape fixed-name `.tmp` writer (open `path + ".tmp"`, write, sync, rename, hand-remove the temp on failure) in a file Arc A owned at the time, and left it for a later adopt. Same discipline as Arc U's two adoptions: the written bytes are byte-identical, the only behaviour delta is the POSIX file mode (exactly 0644 instead of `0644 &^ umask`; a no-op on Windows), the failure paths leave no temp and the previous target intact, pinned by a directory glob (`assertNoTempSurvives` or its twin in the owning package). The engine's own `saveResume` stays fixed-name (its test pins the literal `.tmp` name) — do not touch it.
2. **`tallyColumns` beside `displayColumns`.** Arc C's Task 4 fix made `handleJobUpdate` re-feed `statusBar.SetJobs` when a change key is one the status-bar tally reads (`status`, `platform` — a two-key `slices.Contains` today). Make that coupling checkable: a `tallyColumns` set in `internal/tui` names the keys, the gate reads the set, and a test pins the set against what `tallyJobs`/`barJobCounts`/`parkedCookieJobs` actually read (a job whose only difference is in a tally column must change the tally; a job differing only outside the set must not). `platform` stays in the set (`parkedCookieJobs` reads it) even though `UpdateJobFields` never emits it today. No per-frame work; FrameCost pins 60 / 2 unchanged; a progress tick never re-tallies.
3. **`release()` zeroes `b.bytes`.** Arc B's close wave added `clear(b.seg)` to `reorderBuffer.release()` but left `b.bytes` non-zero, so `residentBytes()` reports stale bytes for an empty map. Zero it in the same critical section; pin: `residentBytes() == 0` after `release()`, and the budget accounting (`reserved`) unchanged. One line plus one assertion.
4. **The cold `-race` failure in `render_cache_test.go`.** At Arc C's close, one cold `-race` invocation of `internal/tui` failed on the cached-vs-fresh frame dump in `render_cache_test.go` and never recurred in 79 further iterations. Diagnose before fixing: run the file's tests cold under `-race` repeatedly (`-count=1` in a loop with a fresh build cache, and `-count=50` warm), read the failing assertion for wall-clock dependence (the task-list and details keys carry the wall-clock second; a frame pair straddling a second boundary renders differently), and rule: a timing-sensitive assertion → freeze the clock through the package's existing seam (test-only); a real data race → fix it (production); not reproducible and no wall-clock path → record the evidence and leave it. No change to the ~60 Hz behaviour or to any pin.
