# Post-sweep-2 follow-ups — design (2026-09-24)

The sweep-2 fix chain (spec `2026-09-17-sweep2-fix-chain-design.md`, merged as T d14490c4, Y 6adf09ca, E af710920, W cae8d7aa, M b0112018, C 917266c5, X f1f7f578) left six items for the owner's ruling and four unowned follow-ups. The owner ruled on all of them on 2026-09-19 and 2026-09-24. This spec turns those rulings into five arcs.

## 0. Owner decisions (verbatim rulings; the arcs implement these as stated)

- **R1 — resolution cap semantics.** `max_video_resolution` compares the SHORTER dimension: height for landscape, width for portrait, so `2160` recognises 4K whichever way the dimensions are ordered. Selection picks the largest rendition at or below the cap; if nothing is at or below it and something exists above, it picks the CLOSEST one above — the cap is a preference among the available qualities, never an exclusion that leaves nothing. An explicit UNBOUNDED mode always picks the largest. Applies to both platforms. Both UIs may present the setting as a picker (480p, 720p, 1080p, 1440p, 4K, 8K, Unbounded, plus Custom) if that reads better than a typed number.
- **R1 format (2026-09-24).** The config key stays an integer; `0` means unbounded; the picker is UI-only and maps presets to numbers; no config migration.
- **R2 — codec ranking.** Size first (the R1 rule), then AV1 > HEVC > H.264 among renditions of the chosen size, mirroring the YouTube order already used (av01 > vp9 > avc1).
- **R3 — memory caps.** Add a shared process-wide VOD reorder budget config. This budget and every other cap whose value was chosen for arm's memory — including the existing 256 MB per-job reorder ceiling — apply ONLY on arm64. The keys exist on every platform; only the defaults differ.
- **R3 defaults (2026-09-24).** arm64: 256 MB per job, 1 GB process-wide. Everything else: 1 GB per job, 4 GB process-wide.
- **D-1 — set-aside recordings.** Both UIs list set-aside recordings and kept chat sidecars under their job and offer a Recover action that muxes the aside into a proper output beside the original; the kept chat sidecar goes with it.
- **W R-3 — folder-open quoting.** Apply the browser-launch command-line quoting to both folder-open paths (the dashboard route and the TUI `O F` chord) in the shared helper, so a Windows directory whose path contains `=` opens.
- **C L17 — downgrade refusal message.** Correct `migrations.go`'s schema-downgrade message platform-aware — artifact names built from the binary's actual name — and drop the misleading `.old` clause (the newer binary is only ever the `.failed` file the marker names, or a fresh download). Message text only.
- **Closed with no change:** the TUI's unreadable-cookie glyph keeps the cookie accent colour (M L-9); the uncached log-panel allocation budget stays at 7,500 (C M8).
- **Follow-ups taken:** the worker race-test flake; the status-bar frame cache; `chatfile.go` and `resumestore.go` adopt `utils.WriteFileAtomic`; the indirect module updates.

## 3. Arcs (five; file sets are disjoint within a wave — the two shared files are called out)

### Arc R — resolution cap (branch `followup-r-resolution`) — wave 1

**Rulings:** R1, R1 format, R2.

**Where the cap lives today (main f1f7f578).** `DownloaderConfig.MaxVideoResolution` (`internal/config/types.go`, default 2160, validation floor 1 in `config.go` and `internal/web/routes/config_routes.go`). Four selection sites, all comparing the LONG edge (`max(width, height)`): `Format.MaxDimension` used by `selectBestFormatsImpl` in `internal/youtube/format_selector.go`; `SelectBestDashStream` in `internal/worker/format_utils.go`; the variant filter in `internal/worker/strategy_youtube_hls.go`; `SelectBestVariant` in `internal/twitch/hls.go`. They disagree when nothing fits: the YouTube format selector and DASH return nil, YouTube live HLS returns a hard error ("no HLS variants found within resolution limit"), and Twitch falls through to the UNFILTERED list and may pick the largest variant. The TUI hint reads "pixels (e.g. 1080, 2160)"; the Web field is `cfg-max-resolution` with help text listing pixel values; the setup wizard has `setup-max-resolution`.

**Design.**
- One shared predicate in `internal/utils` (new file `resolution.go`): `CapDimension(width, height int) int` returns the shorter of the two positive dimensions (a single-dimension rendition uses what it has), and `SelectByCap(cap int, candidates []Cand) (index int, ok bool)` picks the largest candidate whose `CapDimension` is ≤ cap, else the smallest candidate above it, else none; `cap == 0` picks the largest. `Cand` is a tiny struct `{Width, Height int}` so every caller maps its own type into it and back by index. Ties (same short dimension) are left to the caller's existing secondary ranking (fps, bitrate, codec).
- The four sites call `SelectByCap` to choose the SIZE, then apply their existing secondary ranking within that size only. YouTube keeps its codec order (av01 > vp9 > avc1) and fps preference; Twitch's `SelectBestVariant` ranks the chosen size by codec AV1 > HEVC > H.264 (R2; it already parses `CODECS` since sweep-2 Arc T), then source, then bandwidth. The YouTube live HLS hard error and the Twitch over-cap fallthrough both disappear: every site now returns the closest-above rendition when nothing fits.
- Config: validation floor becomes 0 (`0` = unbounded) in `config.Validate`, the Web PUT validator and the TUI validator; the TUI hint becomes "shorter edge in pixels; 0 = unbounded (e.g. 1080, 2160)"; the Web help text and the setup wizard's say the same. Both UIs gain the picker: the Web settings field and the wizard field become a `<sl-select>` with the presets 480p, 720p, 1080p, 1440p, 4K (2160), 8K (4320), Unbounded (0) and a Custom entry that reveals the numeric input; the TUI settings row becomes a cycle field (the same presets, Custom keeps the number entry). A value that matches no preset shows as Custom with its number. The wire value stays the integer.
- Docs: `SPEC.md`'s downloader section, `docs/spec/platform-services.md` (Twitch cap paragraph), `data-and-storage.md` config table, `user-interfaces.md` settings rows; release-note line.

**Testing.** Table tests on `SelectByCap` (landscape, portrait, square, single-dimension, nothing-below picks closest-above, unbounded, empty); each of the four sites gains rows: a 3840×2160 source under cap 2160 is chosen; a 2160×3840 portrait source under cap 2160 is chosen; cap 1080 with only 1440p and 2160p available picks 1440p; cap 0 picks the largest; Twitch codec tie at the chosen size picks AV1 then HEVC then H.264 (mutants: long-edge restored; closest-above replaced by largest; codec order reversed). UI: node tests for the picker mapping in both the settings and setup modules (preset → number, Custom round trip, 0 → Unbounded); a TUI settings test for the cycle field and the validator floor. The live Twitch gate (`MOOMBOX_LIVE_TWITCH_TEST=1`) must still select a variant on a real channel.

**Files:** `internal/utils/resolution.go` (+test), `internal/youtube/format_selector.go` (+test), `internal/worker/format_utils.go`, `strategy_youtube_hls.go` (+tests), `internal/twitch/hls.go` (+test), `internal/config/config.go` (validation), `internal/web/routes/config_routes.go`, `internal/tui/settings.go` (+test), `web/public/index.html`, `web/public/modules/settings.js`, `setup.js`, `web/tests/*.test.mjs`, docs.

### Arc B — reorder-buffer budget (branch `followup-b-buffers`) — wave 1

**Rulings:** R3, R3 defaults.

**Where it lives today.** `catchUpBufferBytes = 256 << 20` in `internal/engine/downloader.go`; `reorderBuffer` in `downloader_parallel.go` (`admit` blocks a non-head segment once `bytes >= limit`; the head is always admitted; `take` frees; `release` disables the ceiling at teardown); two call sites, `runHlsVodParallel` (`downloader_hls.go`) and `runParallelCatchUp` (`downloader_parallel.go`), each with a test-only override field. Nothing in the repo reads `runtime.GOARCH`; `config.Defaults()` is a flat literal with no platform branch.

**Design.**
- Two new config keys on `DownloaderConfig`: `reorder_buffer_mb` (per job) and `reorder_budget_mb` (process-wide, shared by every reorder buffer alive). `0` on either means unbounded. Validation: non-negative integers; when both are non-zero, a per-job value above the process budget is clamped to it at read time with one Warn at boot.
- Platform defaults: a new `config.platformDefaults(goarch string) (perJobMB, budgetMB int)` seam — `arm64` → 256 / 1024; everything else → 1024 / 4096 — called from `Defaults()` with `runtime.GOARCH`; the function takes the arch as a parameter so tests cover both branches on one host. This is the first platform-conditional default in the config package; the doc comment says so and names the rule ("arm-motivated caps apply only on arm64").
- Engine: a package-level `reorderBudget` object (`internal/engine/reorder_budget.go`): `ConfigureReorder(perJobBytes, totalBytes int)` sets both values under a mutex; `reserve(n int) bool` / `free(n int)` account the process-wide total. `reorderBuffer.admit` keeps its per-buffer rule and additionally waits on the shared budget for a non-head segment (the head is ALWAYS admitted on both levels, so the invariant that the writer never starves holds). `take` and `release` free both levels. The two override fields stay for tests. `cmd/moombox/services.go` calls `engine.ConfigureReorder` once at boot and again from the config hot-reload hook, so the strategies and `DownloaderOptions` are untouched.
- Docs: `SPEC.md` §engine, `architecture.md` (the reorder-buffer paragraph), `data-and-storage.md` config table (both keys, both platforms' defaults), `config.example.toml`; the TUI settings overlay and the Web settings page gain both keys (number fields; `0 = unbounded`), following the FlexDuration-era pattern for numeric fields.

**Testing.** `platformDefaults` both branches; validation rows incl. the clamp; engine: two buffers under one small budget — the second's non-head segment blocks until the first `take`s (mutant: the shared reservation dropped); the head is admitted with the budget exhausted (mutant: head gated → deadlock, caught by a timeout); `release` frees the budget; the existing HLS-VOD and DASH catch-up ceiling tests stay green; a `-race` run over the engine and worker packages; `ConfigureReorder` called twice (hot reload) reconfigures without leaking reservations.

**Files:** `internal/engine/reorder_budget.go` (+test), `downloader_parallel.go`, `downloader_hls.go`, `downloader.go`, `internal/config/types.go`, `config.go` (+tests), `cmd/moombox/services.go` (boot + hot-reload — a hunk beside the archive-slots resolver, disjoint from Arc R and Arc A), `internal/web/routes/config_routes.go`, `internal/tui/settings.go`, `web/public/index.html`, `settings.js`, docs. **Shared with Arc R:** `internal/config/config.go` (different validation hunks), `internal/tui/settings.go` and `web/public/index.html`/`settings.js` (different fields) — each arc merges main before its candidate.

### Arc A — set-aside recovery (branch `followup-a-asides`) — wave 1

**Ruling:** D-1.

**Where it lives today.** An aside is `<output><StagedRestartSuffix><unix>` with its `.resume.json` beside it (`internal/engine/downloader.go`). The worker already knows them: `stagedAsideRecordings(stagingDir)`, `groupStagedAsides`, `asideOutputPath` and `muxStagedAsides(ctx, jobCtx, outputDir, filenameBase)` in `internal/worker/orchestrator_mux.go` mux each group into its own sibling output and delete the aside on success — but only as part of a normal finalize. A job whose staging holds ONLY asides (or asides plus a kept chat sidecar from `keepOnlyChatCapture`) has no way to trigger that: `MuxJob` and `POST /api/jobs/{id}/mux` require `HasSegmentFiles`, the TUI `A M` chord requires the same plus a Cancelled/Error status, and the orphan sweep shields the directory forever (`jobNeedsStaging`'s aside shield). The global orphan browsers (`web/public/modules/files.js`, `internal/tui/files_dialog.go`) list `OrphanedEntry.Asides` in the JSON but the TUI's `OrphanedFileEntry` has no such field. Neither UI has a per-job Files tab; per-job detail is the Web job-details dialog (`job-details.js`, fed by `GET /api/jobs/{id}`) and the TUI details panel (`internal/tui/job_details.go`).

**Design.**
- Worker: `Asides(jobID) ([]Aside, error)` returns each aside group with its size, timestamp, whether a resume sidecar exists, and whether the staging dir also holds a kept chat sidecar (`chat.json` at any depth); `RecoverAsides(jobID) error` runs `muxStagedAsides` for the job's staging directory into the job's output directory (the same sibling naming as finalize), then, if a kept chat sidecar exists and no chat file sits beside the output yet, copies the sidecar beside the recovered output as `<recovered>.chat.json`; after a fully successful recovery the staging directory is cleaned by the existing `cleanupStagingAfterMux` rule. Runs in a `w.wg.Go` goroutine with the inline recover, like `MuxJob`; refuses with a typed error when a job is active or a mux is already running.
- API: `GET /api/jobs/{id}` gains `asides` (the list above) and `keptChatSidecar` (bool); `POST /api/jobs/{id}/recover-asides` triggers recovery (loopback and auth as `/mux`; 409 when refused; the route-table parity test and `user-interfaces.md` row in the same commit).
- Web: the job-details dialog gains a "Set-aside recordings" section listing each aside (time, size, sidecar yes/no) with one Recover button when the job is not active; the button disables while recovery runs and the job's log lines show progress, exactly as Mux does today. The global Files panel renders `Asides` for an orphaned entry (it already receives them) and the TUI `OrphanedFileEntry` gains the field so its overlay shows the count.
- TUI: `job_details.go` gains the same rows; a new chord `A R` (Recover set-aside recordings) in `buildMenuItems()` with a `dispatchAction` case, `NeedsConfirm`, enabled by a `JobFilter` that checks the job is not active and has asides (a probe on selection, not on open — the Arc C rule); the CLAUDE.md chord paragraph and the spec chord table gain the entry.
- The `A M` / `/mux` gates are NOT widened (they mean "mux the recording"); recovery is its own verb. `/retry` and `/resume` untouched.

**Testing.** Worker tests against a real staging layout: two aside groups + a kept chat sidecar → two sibling outputs, the chat file beside the first, staging cleaned (mutants: the chat copy dropped; the aside not deleted after success; an active job not refused); a failed mux of the second group keeps its aside and reports the error; the route test (200 / 409 / 404, the parity test); a jsdom test for the dialog section and the button state; a TUI test for the row and the chord gating (`buildMenuItems` stays the single table — the existing structural pins cover it); `internal/docs` green for the doc rows.

**Files:** `internal/worker/orchestrator_mux.go`, `worker.go`, `orphans.go` (+tests), `internal/web/routes/jobs.go` (+test), `web/public/modules/job-details.js`, `files.js`, `web/public/index.html`, `web/tests/*.test.mjs`, `internal/tui/job_details.go`, `app_actions.go`, `files_dialog.go` (+tests), `cmd/moombox/tui_wiring.go` (the `OnRecoverAsides` callback beside `OnOpenFolder`), `CLAUDE.md`, docs. Disjoint from Arc R (no selection file) and Arc B (no engine file, no config key); `cmd/moombox/services.go` untouched.

### Arc C — core fixes (branch `followup-c-core`) — wave 2

**Rulings:** W R-3, C L17, the worker flake, the status-bar cache.

**Folder-open quoting.** `openPathCommandFor(goos, target)` in `internal/web/server.go` builds `exec.Command("explorer.exe", target)`; only the TUI browser launch (`internal/tui/openbrowser_windows.go`) sets `SysProcAttr.CmdLine` with explicit quotes, because Go's default quoting leaves a bare `=` for explorer's legacy parser to split. Design: the Windows arm of `openPathCommandFor` sets the same `CmdLine` (`explorer.exe "<target>"`, embedded quotes stripped) — the browser launch already proves the shape; the helper stays the one site both the route and `O F` use. Test: a Windows-only assertion on the built command's `CmdLine` for a path containing `=` and no spaces (mutant: the quoting dropped), plus the existing five folder-open tests.

**Downgrade message.** `internal/database/migrations.go` formats the artifact names from the running binary: `exe := filepath.Base(os.Executable())` (fallback `moombox`), `<exe>.failed` and `<exe>.update-failed`; the `.old` clause is removed; the sentence becomes "restore the newer binary (an automatic rollback keeps it beside this executable as <exe>.failed and names the exact path in the <exe>.update-failed marker) or download it again". The suffixes are two unexported constants in `internal/database` mirrored from the launcher; a parity test in `cmd/moombox` (package main can read both) asserts they equal `failedBinarySuffix` and the marker suffix used by `writeAutoRollbackMarker`, so the two cannot drift (mutant: either suffix changed). No launcher file changes; the launcher old-tests differential from sweep 2 stays byte-identical.

**Worker flake.** `TestExecuteTwitchRegistersTheLiveChatDownloaderForItsWholeRun` (`internal/worker/twitch_chat_registry_test.go`) runs a real `twitch.ChatDownloader` on a pre-cancelled context; `ExecuteTwitch` waits for the chat goroutine through `resolveChatOutcome`, yet once under `-race` on Windows `t.TempDir` cleanup found the directory not empty. Design: diagnose first (systematic-debugging: `-race -count=200` on that test, with a scratch instrumented `ChatDownloader` that records when its `chat.json` handle closes relative to `Start` returning); fix at the root if `Start` can return before its deferred flush has closed the file (close before signalling), else make the test own the wait (a `t.Cleanup` that polls for the handle to release with a 5 s bound). Acceptance: `-race -count=200` green on Windows and Linux; the fix's mutant named.

**Status-bar cache.** `StatusBarModel.View()` in `internal/tui/status_bar.go` re-renders every frame and `tallyJobs` walks the job list each time — 70 of the cached frame's 100 allocations (`frame_cost_test.go`). Design: `SetJobs` computes the `barJobCounts` tally once on change and stores it; `View` builds a comparable `statusBarKey` (width, both cookie states, active platforms, the tally, disk figures, backfill fields, `ShowChordHint`, `SelectedCount`, `offline`, `sidecarDown`) and returns `renderCache` when the key is unchanged — the same shape as `taskListKey`. Every setter invalidates. Pin: the cached frame is re-measured and `maxCachedFrameAllocs` is reset to twice the new measurement (the count-first rule; the old 200 was twice the old 100), with the figure recorded in the test's comment; an unchanged status-bar `View` allocates ≤ 2 (mutant: the cache lookup deleted); the existing tier-monotonicity and cookie-glyph tests stay green.

**Files:** `internal/web/server.go` (+test), `internal/database/migrations.go` (+test), `cmd/moombox/launcher_names_parity_test.go` (new), `internal/worker/twitch_chat_registry_test.go` (+ possibly `internal/twitch/chat.go` close ordering), `internal/tui/status_bar.go` (+test), `internal/tui/frame_cost_test.go`, docs (`operations.md` for the message; `user-interfaces.md` for the folder note).

## 5. Rulings carried into every plan

- The cap semantics (§3 Arc R) replace FOUR divergent behaviours with one predicate; the plan pins each site's old behaviour as a named mutant so a site that keeps its long-edge compare or its nil/error/fallthrough is caught.
- The process-wide budget (§3 Arc B) is configured ONCE at boot and on hot-reload from `cmd/moombox/services.go`; the strategies and `engine.DownloaderOptions` do not change. The head-always-admitted invariant holds at both levels — a test proves no deadlock with the budget exhausted.
- `platformDefaults` takes the arch as a parameter; both branches are tested on every host. "arm-motivated caps apply only on arm64" is the documented rule for any future cap.
- Recovery (§3 Arc A) is its own verb (`A R`, `/recover-asides`); the mux gates are not widened; `/retry`/`/resume` untouched.
- The downgrade message (§3 Arc C) never imports the launcher (package main is unimportable); the parity test in `cmd/moombox` is the drift guard.
- The worker flake is diagnosed before it is fixed; a test-only wait is the fallback, not the first move.
- The status-bar cache keys on inputs, never on time; the ~60 Hz pipeline stays untouched (the status bar is not on the progress path).
- The module list is enumerated at execution time; `golang.org/x/sys` is skipped as current; the `charmbracelet/x/exp/slice` path is the real one.
- Any arm64 behaviour that cannot be exercised on this Windows host (the budget defaults, the `GOOS=linux GOARCH=arm64` build) is pinned by the parameterised seam and the cross-build; a real arm64 run is a field gate.
