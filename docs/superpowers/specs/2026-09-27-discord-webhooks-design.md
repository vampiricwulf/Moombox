# Discord webhooks — design (2026-09-27)

From the owner's 2026-09-26 ask ("look for improvements in the discord webhooks, things we can combine, things that lacked webhooks that should have them") and the audit that answered it (`.superpowers/sdd/2026-09-26-webhooks/audit.md`, gitignored: 36 send sites, 46 trigger rows, 26 event keys; 7 ADD gaps, 9 combine findings, 6 reliability findings). Four arcs under the standing chain rules (worktree per arc, SDD per task, Fable close review, one wave, `--no-ff` merge without asking, no push, no bump; each plan deletes itself in its last task). Base: main 1433f567.

## 0. Rulings

**Owner (2026-09-27, verbatim choices):**
- **Q1/Q2 Edit-in-place: opt-in per target, message ids persisted.** A per-webhook toggle (default off). Message ids stored per job per target in a `jobs` JSON column so a restart keeps editing the same message.
- **Q3 Batching: a 5 s window into one message of up to 10 embeds.** Found/added events within 5 s per target coalesce into one message; overflow rolls into the next message; nothing dropped.
- **Q5 Mentions: per-target `mention` + `mention_events`**, defaults `error`, `auth`, `disk_critical`, `update_failed`, `crash_recovered`, `sidecar_down`; editable in both UIs.
- **Q6 Dashboard link: `network.public_url`** (config + both Settings UIs, validated as an http(s) URL); the embed title links to the dashboard job and the platform link moves to the author line; unset → today's platform link.

**Controller (vetoable, each `what — why — cost if wrong`):**
- **Four arcs, N1 → (N2a ∥ N2b) → N3** — N1 rebuilds the delivery core and the test seam every other arc needs; N2a (producers) and N2b (config + batching + UI) touch disjoint Go files and separable sections of `settings.js`/`operations.md`; N3 needs both — cost: one extra merge-in.
- **`connectivity_pause` retired through the alias mechanism** — it is sent while the machine is offline and cannot deliver; the resume embed carries the pause; a filter listing the old key keeps receiving the resume embed for one release, and the UIs stop offering the key — cost: one alias entry to delete later.
- **`muxing` stays its own event** and the multi-part defect is fixed — the key is documented and in both UIs; retiring it is a filter-visible change nobody asked for — cost: two embeds per job for targets not in edit mode (as documented today).
- **Recovery events are new keys with aliases to their alert keys** (`sidecar_down` / `sidecar_restored` new; `disk_ok` → `disk_warning`; `channel_healthy` → `channel_unhealthy`) — a target filtering the alert keeps receiving its close without touching config, and a target can subscribe to the close alone — cost: four toggles in both UIs.
- **Sidecar down debounced at 60 s** — the supervisor's restart ladder handles the quick cases; the webhook is for the one it cannot fix — cost: a 60 s later alert.
- **Batching applies to separate-mode targets only** — an edit-mode target's found/added embed IS the job's lifecycle message; coalescing it would defeat one-message-per-job — cost: an edit-mode target sees a burst as N messages, which is what it asked for.
- **Shutdown: single-attempt sends, the 10 s cap kept, docs made truthful** — extending the force-exit for a slow Discord trades a hung shutdown for a lost embed — cost: an embed lost during a shutdown with a slow Discord.
- **Both UIs: an empty filter means ALL events and says so; a target is muted with `enabled = false`** — the docs already define empty = all; a real mute is a separate key — cost: one toggle.
- **Neutral titles, platform in the author line** ("Stream Found", "Job Added", "Job Cancelled", "Download Finished"), colour = severity — cost: readers who keyed on "Twitch …" titles re-read the author line.
- **The dead Twitch finished image is dropped** (preview URLs 404 after the stream ends); multipart thumbnail upload is a later option — cost: no image on Twitch finished embeds.
- **The dashboard deep link is `{public_url}/#job=<id>`** and the SPA opens that job's details on load — the SPA has no job route; a hash needs no server change — cost: ~20 lines of app.js + a jsdom pin.
- **Message ids are written with the silent single-column update** (`updateSingleColumnSilent`, the idiom `UpdateResumePosition` uses) — no `updated_at` bump, no subscriber fan-out, no UI frame for a column nobody displays; the DB layer's cadence ruling is untouched (one write per job per target, on the first successful POST only) — cost: one silent write.
- **Edit mode's terminal states:** on `error` / `cancelled` the lifecycle message is edited to its terminal look (colour, status line) AND the separate error/cancel embed is still posted (it carries the mention) — cost: two messages on failure, by design.

## 1. Arc N1 — delivery core (`internal/notifications` + the seam + four defects + docs truth)

**Today.** `Manager.Send` spawns one goroutine per (event × target) under a 16-slot semaphore: no queue, no ordering (a retried embed lands after a later one), the 17th send is dropped regardless of importance, sixteen concurrent posts to one webhook self-inflict 429s that each cost an attempt, `X-RateLimit-*` headers are never read. Nothing clamps to Discord's limits (a field over 1024 chars is a permanent 400); the description excerpt at `internal/worker/orchestrator_mux.go:1273` is cut by byte; stream titles are not markdown-escaped; `author` is never sent; the footer is "Moombox Go". Every producer holds `*notifications.Manager`, so 43 of 46 trigger rows have no test.

**Change.**
1. **The seam.** `type Sender interface { Send(title, description string, ntype NotificationType, fields []Field, opts SendOptions) }` in `internal/notifications`; `*Manager` satisfies it and `Send` on a nil `*Manager` stays a no-op. Every consumer field/parameter that holds `*notifications.Manager` (`internal/worker/{orchestrator.go,stream_processor.go,trim.go,worker.go}`, `internal/web/routes/jobs.go`, `cmd/moombox/{helpers.go,runstate.go}`) becomes `notifications.Sender`. New package `internal/notifications/notificationtest` with `Recorder` (implements `Sender`; records `Call{Title, Description, Type, Fields, Opts}`; `Calls()`, `ByEvent(e)`, `Reset()`; safe for concurrent use).
2. **`SendOptions` grows:** `Author *Author` (`Name`, `IconURL`, `URL`), `Platform string`, `JobID string` (footer "Moombox · {platform} · {job id}" when set, "Moombox" otherwise; `JobID` is also the edit-mode key N3 reads), `Tier Tier` (`TierLow` for found/added/scheduled/rescheduled, default `TierNormal`; the manager derives it from `Event` when unset), `Mention string` + `MentionAllowed` (filled by N2b; N1 defines the fields and the payload shape: `content` + `allowed_mentions`). `Image` is removed from Twitch finished sends (ruling).
3. **Payload hardening in `buildPayload`:** clamp on rune boundaries to Discord's limits — title 256, description 4096, field name 256, field value 1024, footer 2048, author name 256, 25 fields, 6000 total (drop trailing fields first, then trim the description, never the title) — with a "…" marker; `EscapeMarkdown(s string) string` exported for producers (escapes `\ * _ ~ | \` < >` and leading `#`/`-`/`>`; applied by producers to job-supplied strings — titles, error text, paths — never to the static titles or to fields that carry `<t:…>` markup on purpose); the byte cut at `orchestrator_mux.go:1273` becomes a rune cut through the same helper. Accept `discordapp.com` in `parseTarget`. Fix the two stale comments (`manager.go:133` example event, `:141` "30 req/min").
4. **Per-target FIFO delivery.** One sender goroutine per target with a bounded queue (256 entries): items are delivered in order, retries happen in place (never reordering), the sender reads `X-RateLimit-Remaining` / `X-RateLimit-Reset-After` and sleeps pre-emptively before the bucket empties, a 429's `Retry-After` is honoured (≤ 30 s, else the item is dropped with a Warn), transport errors and 5xx back off 2 s / 5 s (three attempts), other 4xx are permanent. Overflow drops the OLDEST `TierLow` entry (a Warn names the event and title); if none is low-tier, the newest is dropped. `Reload` starts goroutines for new targets and lets a removed target's goroutine finish its in-flight item and exit (its queue is discarded with one Warn naming the count). `Wait` drains every queue up to the shutdown budget; a `Manager` told it is shutting down (`BeginShutdown()`) sends single-attempt. The 16-slot semaphore is deleted.
5. **Four defects at their sites.** (a) `muxing` for multi-part jobs: the "Muxing Starting" send moves above the branch at `orchestrator_mux.go:675` so both finalize paths fire it. (b) "YouTube Start Time Confirmed" fires only for `IsUpcoming && !IsLive` (`stream_processor.go:574`). (c) "Authentication Recovered" fires on the `OnAuthRecovered` edge whenever a failure was notified for that platform, not only when `resumed > 0` (`cmd/moombox/monitor_callbacks.go:378-379`; the description says "N jobs resumed" or "no jobs were parked"). (d) `connectivity_pause`: the send is removed; the pause instant is stamped where `offlineCancelled` is consumed (`orchestrator_twitch.go`) and the resume embed says "Paused <t:x:R> · resumed after {duration} · part N"; the key leaves `EventGroups`, stays accepted as a legacy filter entry through `eventAliases["connectivity_resume"] = "connectivity_pause"`, and `KnownEvents` includes alias values so a config listing it does not warn; the UIs strip it on save. Also `orchestrator.go:656` "Trim Failed" uses `IDLabel`.
6. **Tests.** Package: FIFO order under a retried first item; overflow drops the oldest low-tier and never `error`/`auth`/System; the pre-emptive sleep from `X-RateLimit-Remaining: 0`; 429 with/without `Retry-After`; `Reload` mid-queue; `Wait` with the budget; `BeginShutdown` single attempt; every limit clamped on a rune boundary (a Japanese title/description/field); `EscapeMarkdown` table; `discordapp.com`; the alias-known rule; the footer/author payload shape; the mention payload shape. Consumers: with `Recorder`, one test per defect site (a multi-part job records `muxing`; a first-seen-live stream records no `scheduled`; a recovery with zero parked jobs records the all-clear; a Twitch outage records one resume embed carrying the pause and no pause embed).
7. **Docs truth:** `docs/spec/operations.md` §Notifications (delivery model, drop policy, shutdown cap, the three rows the audit found overstated: `muxing`, `scheduled`, `connectivity_pause` → retired), `README.md` (Discord only — no Slack/ntfy; the event list replaced by a pointer to the operations table; no `live`), `SPEC.md:885` (all keys), the `moombox-settings` skill if it lists notification fields.

**Constraints.** DB layer untouched; the update path untouched; every event key that exists today keeps its meaning except `connectivity_pause` (retired, aliased); no new config keys in N1; the TUI import fence; LF; the citation gate.

## 2. Arc N2a — producers (truth, unification, recovery halves)

**Change.**
1. **Finished/Error truth** (same `finished`/`error` sends, no new keys): `incomplete_tail` → Warning colour + field "Tail: incomplete — Resume appends the rest"; `chat_status = incomplete` → field "Chat: incomplete"; `ScanAsides` non-empty at finalize (Finished or Error) → field "Set-aside recordings: N — Recover to mux them"; "Job Failed" gains "Stage: mux | download" (from the error prefix the orchestrator already writes) and "Staging: preserved — Resume available" when staging survives, "Staging: removed" otherwise.
2. **One builder per family** in a new `internal/notifications/builders.go` (pure functions returning `(title, description, type, fields, opts)` from a small `JobFacts` struct the producers fill — no database import in the package): `JobAdded`, `StreamFound`, `JobCancelled`, `DownloadFinished([]Part)` (len 1 = the single-part shape; the multi-part shape also carries Description and Format; "Parts: N" only when N > 1), `TrimCreated`. All four "Video Added" sites (routes YouTube/Twitch, CLI ×2 — the CLI sites gain thumbnail + channel), both "Stream Found" sites, both "Cancelled" sites, both "Download Finished" builders and both "Trim Created" sites call them. Neutral titles; every job send sets `Platform`, `JobID`, `URL` = the video's platform page, and `Author` = channel name + `ChannelAvatarURL` + the channel page (N2b's manager rewrites `URL`/`Author.URL` when `public_url` is set; the builders never read config).
3. **Recovery halves.** `sidecar_down` / `sidecar_restored` (new keys in the System group): a `sidecar.SubscribeHealth` subscriber in `cmd/moombox` beside the TUI's (the second subscriber); `sidecar_down` fires when unhealthy persists ≥ 60 s (Error, mention-eligible, "restarts: N" from the health snapshot), `sidecar_restored` when healthy again after a down was sent (Success). `disk_ok` (alias → `disk_warning`; Success) where `main.go` resets `lastDiskLevel` to ok after a warning/critical was sent, and "Disk Monitoring Recovered" where `diskReadFailing` clears after a failure was sent. `channel_healthy` (alias → `channel_unhealthy`; Success): `healthTracker` gains `onHealthy`, fired from `recordSuccess` only when `notified` was true, wired beside `unhealthyNotify` in `monitor_callbacks.go`. The vocabulary mirror in `settings.js` and the operations table gain the four keys; the TUI derives.
4. **Tests** with `Recorder`: each truth field with the job state that triggers it; each builder's output per platform and entry point (table tests); the sidecar debounce (a fake clock: unhealthy for 59 s → nothing; 60 s → one `sidecar_down`; healthy → one `sidecar_restored`; a flap under 60 s → nothing); disk ok after warning; channel healthy only after an unhealthy was notified; the Go ↔ `settings.js` vocabulary parity test (parse the ids from the JS file).
5. **Docs:** operations table rows for the new keys and the unified titles; `user-interfaces.md` if it names embed titles.

**Constraints.** No manager/discord changes (N1 owns them); no config keys (N2b owns them); the builders package imports nothing from `internal/worker` or `internal/database`.

## 3. Arc N2b — config, batching, both UIs

**Change.**
1. **Config keys** (`internal/config/types.go`, defaults, `validateOrNormalize`, `config.example.toml` commented, `docs/spec/data-and-storage.md` table, the `moombox-settings` skill checklist): `network.public_url` (string; empty = unset; must parse as an absolute http(s) URL with no query/fragment; trailing slash trimmed; hot-reloadable — read at send time); per-target `enabled` (bool, default true; false = the target is kept but skipped, `NewManager` logs it), `mention` (string; `<@&id>`, `<@id>`, `@everyone` or `@here`, validated), `mention_events` (`[]string` validated against the vocabulary incl. aliases; when `mention` is set and the key is absent, the ruling's default list applies; an explicit empty list means never), `mode` is reserved for N3 (not added here). Unknown event keys are stripped server-side on a web save (`validateConfigUpdates`), as the TUI already does.
2. **Mentions in the payload:** for a target whose `mention` is set and whose `mention_events` contains the event, the message carries `content: <mention>` and the matching `allowed_mentions` (`roles: [id]` / `users: [id]` / `parse: ["everyone"]`); embeds never mention on their own. A batched message carries the mention once if any member is mention-eligible.
3. **Dashboard link:** when `public_url` is set, the manager rewrites every send that carries a `JobID` at send time (from the live config, so a hot-reload applies): the title URL becomes `{public_url}/#job={id}` and the video's platform page (the builder's `URL`) moves to `Author.URL`, replacing the channel page; when unset, nothing is rewritten. The SPA: on load (after `initial_state`) and on `hashchange`, `#job=<id>` opens that job's details dialog if the job is known, then clears the hash; unknown id → a toast "Job not found". jsdom pin in the app harness.
4. **Batching** (`internal/notifications`, separate-mode targets only): per target, `found`, `added` and the per-job "Authentication Required" (`auth`) coalesce for 5 s from the first queued item into one message of ≤ 10 embeds (Discord's limit), overflow rolling into further messages in order; `error`, `cancelled`, `trim_*`, System and every other key never batch; filters apply before coalescing; the batch is one queue item in the FIFO (so ordering and the drop policy hold); a batch counts as `TierLow` only if every member is. `Wait`/`BeginShutdown` flush open windows immediately.
5. **Both UIs' target editors** (`web/public/modules/settings.js` + `internal/web/routes/config_routes.go`; `internal/tui/settings_notifications.go`): `enabled` toggle, `mention` text, `mention_events` chips/toggles (defaulting from the ruling when a mention is first set), an "All events" label when the filter is empty (web and TUI agree; the TUI no longer refuses an empty filter), the Network section's `public_url` row (both UIs; hot-reload, no restart badge). Test-send unchanged.
6. **Tests:** validators (each key's accept/reject table); the mention payload per form; the default-list rule; batching (window, 10-embed split, order, mixed tiers, filters before coalescing, flush on shutdown, never for the excluded keys); the deep-link (SPA jsdom); both editors' round-trips (web jsdom; TUI a `tea` test); README recount.
7. **Docs:** operations.md (mentions, batching, `enabled`, `public_url`), user-interfaces.md (the editors, the deep link), data-and-storage.md (keys), README (a short "Mentions and dashboard links" paragraph).

**Constraints.** No producer changes (N2a); the config-file-only key class untouched; `PUT /api/config` merges per key as today; the restart-required list unchanged (all three keys hot-reload).

## 4. Arc N3 — edit-in-place lifecycle messages (opt-in, persisted)

**Change.**
1. **Per-target `mode`** (`"separate"` default | `"edit"`; config + validator + both editors + docs).
2. **Lifecycle set:** `found`, `added`, `scheduled`, `rescheduled`, `downloading`, `quality_split`, `gap_split`, `connectivity_resume`, `connectivity_split`, `muxing`, `finished` are lifecycle events; `error`, `cancelled`, `auth`, `trim_*` and System are always separate posts. For an edit-mode target, the first ALLOWED lifecycle event of a job POSTs with `?wait=true` and stores the returned message id; every later allowed lifecycle event PATCHes that message (`PATCH /webhooks/{id}/{token}/messages/{message_id}`) with the embed rewritten: colour + a "Status" field for the current state + a "History" field of appended lines (`<t:x:R> Scheduled`, `<t:x:R> Downloading`, `<t:x:R> Muxing`, …, clamped to the field limit by dropping the oldest lines). `finished` is the last edit. On `error`/`cancelled` the message is edited to its terminal look AND the separate embed is posted (ruling). No progress edits ever.
3. **Persistence:** `jobs.notification_msgs TEXT` (nullable JSON: `{"<resolved webhook URL sha256 prefix>": "<message id>"}`), schema 19 → 20 via the migrations skill's idiom; written once per (job, target) on the first successful POST with the silent single-column update (ruling); read once when a job's first lifecycle send arrives after boot. A PATCH answered 404 (`Unknown Message`) → POST a new message and overwrite the id. Ids are keyed on the resolved URL (the dedupe key `buildTargets` already uses); a removed target's ids are ignored; a new target starts at its next allowed event. Job deletion drops the row (and the ids with it); no DELETE calls to Discord.
4. **Ordering and budget:** edits ride the same per-target FIFO (N1) so a job's states never reorder; PATCH shares the webhook's bucket (per Discord API docs) and the same rate-limit handling applies. `SendOptions.JobID` (N1) is the key; a lifecycle send without a `JobID` is treated as separate.
5. **Tests:** the state machine (a fake Discord recording POST/PATCH bodies: first allowed event POSTs, later ones PATCH, filters skip without creating, 404 re-POSTs and re-stores, restart resumes from the stored id, a removed target is ignored, a job with no id in a fresh process POSTs); the History clamp; the terminal edit + separate post on error; the migration up/down on a fixture DB; both editors' `mode` round-trip; `Recorder` unchanged for producers.
6. **Docs:** operations.md (the edit model, what persists, the 404 fallback, "edits share the rate bucket"), data-and-storage.md (the column, schema 20), user-interfaces.md (the toggle), README (one paragraph).

**Constraints.** Producers unchanged (they already pass `JobID`); the silent write is the only DB write; batching stays separate-mode only; every N1/N2 test still green.
