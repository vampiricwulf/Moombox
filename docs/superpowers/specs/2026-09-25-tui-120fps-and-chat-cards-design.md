Two independent arcs from the owner's 2026-09-25 rulings, run under the standing chain rules (worktree per arc, SDD per task, Fable close review, one wave, `--no-ff` merge without asking, no push, no bump, no `RELEASE_NOTES.md`; each plan deletes itself in its last task). Base: main aa91c748.

## 0. The owner's rulings (verbatim intent)

- **F1 — "I want the 120 fps."** The TUI renderer runs at 120 frames per second and the engine's progress-report gate becomes configurable: *"Renderer 120 fps + engine gate configurable — the engine gate stays 16 ms by default but becomes a config key so you can try 8 ms on your machine without a rebuild."* The standing rule stays: updates get cheaper or more frequent, never rarer.
- **K1 — YouTube Super Chats: "YouTube-faithful two-part card."** A self-contained rounded card like YouTube's: a header strip in the tier's header colour with the author name, badge and amount; a body in the tier's body colour with the message text; light or dark text picked per tier. Super Stickers get the same card with a "Super Sticker" label in place of the image (sticker images are not archived).
- **K2 — YouTube memberships: "Yes, green member cards."** New-member and milestone messages get a self-contained card in YouTube's member green with the author, the milestone text and any message; gifted-membership notices get the same card.
- **K3 — Twitch: "Twitch-like notices + cheer scale."** Sub, resub, gift and raid notices become a highlighted block: purple accent, tinted background, the system line (e.g. "X subscribed with Prime", "X is gifting 5 subs", "Y is raiding with 120 viewers") above any message. Bits messages get a cheer chip whose colour follows Twitch's amount scale: gray under 100, purple 100+, green 1,000+, blue 5,000+, red 10,000+.
- **K4 — Scope: "Sidebar only."** The cards and notices live in the sidebar chat. The video overlay keeps its current plain scrolling text, with announcements still coloured as today.
- **Not a change (verified 2026-09-25):** Twitch enhanced broadcasts (HEVC/AV1) are already always requested (`platform=web`, `supported_codecs=av1,h265,h264` on every usher request) and ranked AV1 > HEVC > H.264 at the chosen size; there is no opt-in setting. The owner-report wording is corrected; no code moves.

## 1. Arc F — TUI 120 fps

**Today.** `tea.NewProgram(app)` (`internal/tui/app_commands.go:675`) takes no options, so bubbletea's default 60 fps applies (max 120). The TUI's own fast progress tick is `progressFastInterval = 16 ms` while a download is active (`internal/tui/app.go` ~:979-999), 500 ms idle. The engine reports progress at most once per `progressUpdateInterval = 16 ms` per job (`internal/worker/progress.go:15`, gate at `:483`), each report writing `UpdateJobFields` and fanning out to the WebSocket hub and the TUI. Every change reaches the screen (a full DB→TUI channel replays a snapshot); the two 16 ms stages are the only latency.

**Change.**
1. The renderer: `tea.WithFPS(120)` on the one `tea.NewProgram` call. Pin: a seam or a source-text test that the program is built with the 120 option (the planner picks the cheapest shape that cannot silently regress).
2. The TUI fast tick: `progressFastInterval` 16 ms → 8 ms (the idle 500 ms and the 1 Hz clock tick unchanged). The per-second details gate (`SetProgress` skips a rebuild on the same pointer in the same second) makes the extra ticks free when nothing changed; the FrameCost pins (60 cached frame / 2 status bar; measured 30 / 0) must hold — a no-change frame costs the same at 120 as at 60.
3. The engine gate: a new config key `downloader.progress_interval_ms` (integer milliseconds; default 16; minimum 1; no maximum) read by `NewProgressTracker` (or the worker's snapshot the tracker is built from) so a tracker created after a config save uses the new value — no restart, no entry in the restart-required list; a running tracker keeps the interval it started with (documented). Validation: `config.Validate` (< 1 → the default, with the usual `fail` line). **Ruling: a config-file key with no Settings row in either UI**, like `cookies.dpapi_profile_dir` — why: the owner asked for a knob to try on one machine, and a UI row costs two settings tables, three validators and jsdom/README churn for a value almost nobody changes — cost if wrong: one later task adds the rows. Documented in `config.example.toml` (commented, with the 8 ms example and the CPU/DB cost sentence) and `docs/spec/data-and-storage.md`'s config table; `docs/spec/user-interfaces.md` states the 120 fps renderer and the 8 ms tick; `SPEC.md`'s "~60 Hz" sentences become "the configured progress interval (16 ms by default)".
4. Tests: a tracker with an 8 ms interval accepts ≥ 2× the reports of a 16 ms tracker over the same synthetic burst (a deterministic clock seam if one exists; otherwise a bounded wall-clock test with a generous margin); `progress_interval_ms = 0` and negative → default; the config round-trip through `config.Save`.

**Constraints.** DB layer untouched (the write cadence is the tracker's gate, not the DB's); the WebSocket hub stays unthrottled; the ~60 Hz sentences in the docs are corrected, not the rule ("cheaper or more often, never rarer"); the TUI import fence; the FrameCost pins; the 8 ms tick must not add work to a no-change frame.

## 2. Arc K — player sidebar chat cards

**Today.** `_buildChatMessageEl` (`web/public/modules/player.js` ~:1105-1163) builds `<div class="chat-msg …">` with a time span, an optional bold amount span, the author span and the content span. `msg.superchat` only adds `.superchat` (one amber left border) and the amount; `tier`, `kind`, `headerColor`, `bodyColor` and `isMembership` are never read. Twitch: only `messageType === "announcement"` is styled (`.announcement.announcement-<color>` with a `--announcement-accent` custom property); `bits`, `sub`, `resub`, `subgift`, `raid` render as plain text although `bits`, `subPlan`, `giftRecipient`, `viewerCount` and `systemMsg` are in the file.

**The archive's fields.** YouTube (`internal/chat/types.go`): `superchat{amount, currency, color, tier 1-7 (0 unknown), kind "message"|"sticker", headerColor, bodyColor as #RRGGBB}`, `isMembership`, `authorBadges`, `message[]` parts. Twitch (`internal/twitch/types.go`): `messageType` in `chat|bits|sub|resub|subgift|raid|announcement|system`, `bits`, `systemMsg`, `subPlan` ("1000"/"2000"/"3000"/"Prime"), `giftRecipient`, `viewerCount`, `announcementColor`, `authorColor`, `authorBadges`.

**Change (UI only unless §2.1 finds a capture gap).**
1. **YouTube Super Chat / Super Sticker card.** A `.chat-card.superchat` element replacing the flat row: header (`.chat-card-header`: author name with its badge class, then the amount + currency as archived) in `headerColor`; body (`.chat-card-body`: the message parts through the existing `appendChatContent`) in `bodyColor`; the time stays in its span at the card's top-right. Text colour per tier: YouTube uses dark text on tiers 2-4 (cyan, green, yellow) and white on 1, 5, 6, 7; the implementation derives it from the body colour's luminance (WCAG relative luminance, threshold 0.5) so an unmapped archived colour still reads. Colours are applied as CSS custom properties from JS (`el.style.setProperty("--card-header", …)`) — CSP-safe (CSSOM writes are not inline styles); the stylesheet consumes the properties. Fallback when `headerColor`/`bodyColor` are absent (old files): the tier palette table in CSS (`[data-tier="1"]` … `"7"`: YouTube's blue, cyan, green, yellow, orange, magenta, red pairs), and for tier 0 a neutral gray card. A sticker (`kind === "sticker"`) is the same card with the body reading "Super Sticker" in place of the (unarchived) image; an old file with no `kind` and an empty message is treated as a sticker.
2. **YouTube member card.** `isMembership` → `.chat-card.member` in YouTube's member green (header `#0F9D58`, body a lighter tint), the author in the header, the message parts in the body. Section 2.1 decides what text the archive carries.
3. **Twitch notices.** `messageType` in `sub|resub|subgift|raid` → `.chat-notice.twitch` block: purple left accent (`#9147ff`), tinted background (the accent at ~10% alpha), the `systemMsg` as the bold first line (built from the fields when `systemMsg` is empty: sub/resub → "<author> subscribed with <plan name>", subgift → "<author> gifted a sub to <giftRecipient>", raid → "<author> is raiding with <viewerCount> viewers"; plan names: 1000 Tier 1, 2000 Tier 2, 3000 Tier 3, Prime), then the message if any. `system` and `announcement` keep today's rendering.
4. **Twitch cheer chip.** `messageType === "bits"` (or `bits > 0`) → the ordinary row plus a `.cheer-chip` before the content showing "<bits> bits", coloured by Twitch's scale: `< 100` gray `#979797`, `≥ 100` purple `#9c3ee8`, `≥ 1000` green `#1db2a5`, `≥ 5000` blue `#0099fe`, `≥ 10000` red `#f43021` (the chip's text colour by the same luminance rule).
5. **Sidebar only.** `_buildNicoEl` (the overlay) is untouched; the divider, `active`/`future` and scroll logic keep working on the new elements (the card and notice elements carry the same `chat-msg` marker class the timeline code keys on, or the timeline code is taught the new class — the planner reads `player.js`'s selectors and pins whichever it chooses with the harness).
6. **Tests.** jsdom `player.test.mjs` (the player harness) fixtures: one message per shape (tier-3 Super Chat with archived colours; tier-7 without colours → palette; sticker; tier-0 gray; member; each Twitch notice kind with and without `systemMsg`; bits at each scale boundary 99/100/999/1000/4999/5000/9999/10000; a plain message unchanged). Each asserts the class, the custom properties, the header/body text and the luminance-derived text class; `web/tests/README.md` recounted from live runs.
7. **Docs.** `docs/spec/user-interfaces.md`'s player section: the card and notice shapes, the palette fallback, the luminance rule, "sidebar only".
