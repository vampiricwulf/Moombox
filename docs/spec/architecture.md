# Architecture

## Scope

This document provides a comprehensive technical reference for Moombox's internal architecture: the process model, service initialization, package structure, data flow, download pipeline, concurrency model, error handling, and key type definitions. It is the deepest and most detailed document in the specification suite, intended to give an LLM or developer full context for understanding how the system works at every level. Read this before making changes to core infrastructure, the download pipeline, or cross-cutting service wiring.

## Rules and Constraints

These are hard requirements that must be followed in all code changes:

- **Launcher/supervisor pattern via `_MOOMBOX_CHILD` env var.** The binary operates in two modes. Without the env var it acts as a launcher that spawns itself as a child. With `_MOOMBOX_CHILD=1` it runs the full application. Exit code 42 (`exitCodeRestart`) signals the launcher to respawn. This enables seamless restarts for config changes and binary updates.
- **All goroutines MUST have panic recovery.** Every `go func()` must include an inline `defer func() { if r := recover(); ... }()`. No exceptions. HTTP handlers use `RecoveryMiddleware`. Database callbacks use `safeCallJobUpdate`/`safeCallJobsChange`. Monitor callbacks wrap `OnVideoFound`/`OnStreamFound` with deferred recovery.
- **Logger interface is anonymous per-struct -- NEVER extract to a named interface.** Each struct that needs logging declares its own anonymous `logger interface { Debug/Info/Warn/Error }` field. This is intentional for loose coupling. Do not create a shared `Logger` type or named interface in a common package. The one exception is `internal/bgutils/sidecar`, which declares a package-level `Logger` interface of the same four-method shape so the sidecar can be constructed without that package naming a logger type.
- **Database partial updates use `UpdateJobFields()` with dynamic SET clauses.** Pass a `map[string]any` of field names to values. The method dynamically builds the SQL SET clause, auto-updates `updated_at`, and triggers `OnJobUpdate` subscribers. Never write raw UPDATE SQL for job fields outside this pattern.
- **Callback closures for cross-cutting service wiring, NOT interfaces.** Services are wired together in `main.go` using function closures (`OnVideoFound`, `OnStreamFound`, `OnSchedule`, `OnCookieRefreshNeeded`, etc.) and struct-based dependency injection. There are no service registry patterns or interface-based DI containers.
- **JobStatus is `type JobStatus string`.** Timestamps are ISO 8601 strings (RFC3339). Optional numeric fields (sequence numbers, dimensions, file sizes) use pointers (`*int`, `*int64`, `*float64`) where nil means "not set." Boolean fields in the database use integer 0/1 but are exposed as Go `bool` in the `Job` struct.
- **Cross-platform via build tags.** Windows x64, Linux x64, and Linux arm64 are supported. Platform-specific behavior is isolated in per-package `_windows.go` / `_unix.go` files: `createNoWindow = 0x08000000` (launcher, Windows only), kernel32 disk queries (`internal/disk/disk_windows.go` vs `disk_unix.go` via statfs), flock-based single-instance locking (`single_instance_unix.go`), and the ping-based `.exe~` cleanup (`launcher_windows.go`). The connectivity monitor (`internal/connectivity`) needs no split: it dials TCP through a plain `net.Dialer`, so its three files carry no build tags. Linux stubs produce correct no-op or functional fallback behavior; Windows-only features degrade with clear UI messaging.

## Process Model

### Launcher/Supervisor Pattern

Moombox uses a two-process model controlled by the `_MOOMBOX_CHILD` environment variable:

**Launcher process** (no `_MOOMBOX_CHILD`):
- Executes `launchAndSupervise()` in `cmd/moombox/launcher.go`
- Catches Ctrl+C (SIGINT), SIGTERM and, on Unix, a hangup (SIGHUP) instead of dying from them, and forwards each to the child (`forwardStop`; on Windows the console event already reached the child, so it only records the stop); a hangup inherited as ignored (`nohup`) stays ignored
- Spawns itself as a child with `_MOOMBOX_CHILD=1` added to the environment
- Passes through stdin/stdout/stderr so the child's TUI renders in the launcher's console
- When the child exits with code 42 (`exitCodeRestart`), the launcher respawns — unless it forwarded a stop to that child, which ends supervision with exit 0. This picks up any new binary (for self-updates via the swap: current kept at `.old`, `.new` -> current)
- Any other exit is decided by `classifyChildExit` (operations.md §Launcher/Supervisor Pattern has the rules in order): code 0, a stop the launcher forwarded, 130/143 and 3 (`exitCodeStartupError`) end the launcher with the same code, and so does any other non-zero exit within 60 s of a fresh launch; a failed first boot after an update is rolled back to the previous binary; any other non-zero exit is a crash, respawned after 1/2/4/8/16 s until the launcher gives up after 5 in a row
- On respawn, cleans up `.old` binary by renaming to `.exe~` (freeing the `.old` name for future updates)
- On final exit, spawns a detached `cmd /C ping ... & del` process to delete the `.exe~` file after the launcher releases its lock

**Application process** (with `_MOOMBOX_CHILD=1`):
- Runs the full service stack via `run()`
- Handles SIGINT, SIGTERM and, on Unix, SIGHUP for graceful shutdown (`catchStopSignals`), catching every later one too, so a repeated signal mid-shutdown is harmless; the TUI quits when the run's context ends, and after a hangup nothing more is written to the gone terminal
- Returns `true` from `run()` to signal a restart request, causing `main()` to `os.Exit(42)` — unless a stop signal arrived, which overrides a restart requested before it or after (`restartPending`)

**Restart mechanism:**
```
triggerRestart(source string) {
    restartRequested.Store(true)  // atomic bool
    webServer.StartDrain()        // 503 for new requests from here on
    after 5s:                     // let in-flight setup/save requests finish
        cancel()                  // cancel the main context
        quitTUI()                 // if TUI is running, unblock tea.Program.Run()
}
```
Called from: `routes.SetupRoutes` (setup wizard completion), `routes.UpdateRoutes` (after applying update), `routes.RestartRoute` (manual API restart), and the TUI (settings save, update apply, setup wizard — `cmd/moombox/tui_wiring.go`).

**Shutdown sequence** (`shutdown()` in `cmd/moombox/shutdown.go`; every stop is wrapped in `stopService` panic isolation, and SPEC.md's Shutdown Sequence section carries the same list):
1. Context cancellation propagates to all services; the TUI quits (if running)
2. A 15-second force-exit timer (`forceExitAfter` — the worker's 12-second stop budget, `worker.StopBudget`, plus a 3-second margin, out of which the trim service's stop ahead of the worker can take up to 2 seconds, `worker.TrimStopWait`) is armed FIRST — if graceful shutdown stalls it closes the rate limiters, database and log itself and exits (code 42 when a restart was requested, else 0, so the launcher does not treat a slow quit as a crash)
3. Notifications switch to single-attempt mode
4. Monitors stop (Twitch, DECAPI, Feed), then the trim service (`TrimService.Stop`: cancels every trim it runs — a dashboard's, a TUI's, a finished job's post-download one — and waits up to 2 seconds for each to remove its partial file)
5. Download worker stops (waits up to 10 seconds for in-flight jobs to save state, then cancels in-flight muxes and gives FFmpeg 2 seconds to die). The force-exit must outlast this whole budget: its clock starts first, and a backstop not longer than the worker's wait would exit before `CancelMuxes` ran
6. In-flight notifications are flushed
7. Cookie refresh and auto-cookie services stop (the auto-cookie service cancels its periodic refresh and boot seed and waits up to 2 seconds, `cookies.AutoCookieStopWait`, for a pass in flight — and the auth re-check after it, which runs under the same context — to return)
8. PotProvider is cleaned up and the BotGuard sidecar is stopped (when running)
9. Web server shuts down
10. Log forwarder and DB event subscribers are unsubscribed
11. Database closes (final WAL checkpoint)
12. `shutdown()` returns the restart flag to `run()`, whose deferred `closeLog` flushes the log file

### Subcommands and Flags

Before the launcher/child split, `main` parses the flags and dispatches a subcommand:

- `moombox [-config path] add [--] <video_id_or_url>` -- CLI mode that adds a video to the database and exits (`cmd/moombox/addvideo.go`). Flags are parsed first and the subcommand is the first argument after them, so `-config` may come before `add` or after it; without one, `add` runs the same config search as the daemon. A last argument that begins with `-` and that `utils.ExtractMediaID` accepts is the target, not a flag (`addTarget`) — about one YouTube video ID in 64 begins with `-`, so `moombox add -XyZ123abcd` is not an undefined flag — unless it is the value of a `-config` before it; `--` ends add's flags for any argument. Any other positional argument is refused with the usage text (which `-h` prints too). It does not talk to the web API: it opens the daemon's SQLite file directly with `database.Open` — after a `FileSchemaVersion` check that refuses a database whose schema does not match the binary, rather than migrating the live file from a second process — inserts the row with `AddJob`, and the running daemon's `pollForJobs` safety net (every 60 seconds) picks it up. Which file is the daemon's comes from the **daemon record** (`cmd/moombox/daemon_record.go`; [operations.md](operations.md) § Launcher/Supervisor Pattern), `moombox-daemon.json` beside the single-instance lock, trusted only while that lock is held (`findRunningDaemon`).

  While a daemon runs, `add` writes to the database it recorded and refuses, naming both files, a config whose `database_path` resolves elsewhere (`resolveAddDatabase`): a relative one resolves against the daemon's working directory when the config is the file the daemon loaded — so `moombox -config <the daemon's config> add` works from any directory — and against `add`'s own otherwise, so a second install's config with the same `./moombox.db` is refused rather than read as the running one's. A daemon that holds the lock but has recorded nothing is refused too (`noDaemonRecordRefusal`): mostly it is still starting, and the refusal says to retry in a moment, or — when the record stays missing, as under a supervisor from before the version handshake — to stop Moombox and start it again, since a Restart from the dashboard or the TUI respawns the child under the same supervisor. With no daemon running, a relative `database_path` resolves against `add`'s working directory and is refused, naming the absolute path tried, when no database is there.

  Either way `database_path` resolves to the file `database.Open` would open from that directory (`databaseFileUnder`): joined as the OS joins it — lexically on Windows, and on Unix uncleaned, since a `..` after a symlinked working directory climbs out of the symlink's target — then through `database.ResolveFile`, which keeps an earlier release's file for a path that release read another way (`//localhost/<abs>` is `<abs>`), and compared with the record by `os.SameFile`. A lexical join and `filepath.Clean` would send the daemon's own `../db/moombox.db` from a symlinked directory to a file beside the symlink, and `//localhost/<abs>` to `/localhost/<abs>`. Opened as given, `database_path` would find nothing when run from another directory than the daemon's ("Start the Moombox daemon first." while the daemon ran) or write the job into a stray `moombox.db` there, print "Added", exit 0 and send Job Added for a video the daemon never saw. The lock is per user (`%LOCALAPPDATA%\moombox\` on Windows, `~/.local/share/moombox/` on Linux), so a daemon another account runs is invisible to `add`, which takes the no-daemon rule for it.
- `-version` -- Prints version and commit hash, exits immediately.
- `-headless` / `-no-tui` -- Runs web-only mode (no BubbleTea TUI). Also activated by `MOOMBOX_NO_TUI=1` env var.
- `-log-level <LEVEL>` -- Overrides the log level for this run only (DEBUG, INFO, WARN, ERROR). It reaches the logger and nothing else: `effectiveLogLevel` in `cmd/moombox/helpers.go` picks it over the configured level when building the logger, and `cfg.Logs.LogLevel` is left as the file has it, so the boot auto-persist, the password auto-hash and every later settings save keep writing the CONFIGURED level. A settings save from either UI re-applies the configured level to the running logger only when that level changed (`applyConfiguredLogLevel`, `cmd/moombox/tui_wiring.go`) — an explicit level choice ends the override, a save of any other setting keeps it.
- `-config <path>` -- Specifies the config file. An explicit path is AUTHORITATIVE: that file is the only one considered, and if it does not exist Moombox starts from defaults and a later save creates it there — it never falls through to another location. Without the flag the search order is `./config.toml`, `./config/config.toml`, `~/.config/moombox/config.toml`, then defaults.

TTY detection uses `go-isatty` on both stdin and stdout. If either is not a terminal, TUI is disabled automatically.

## Service Initialization Order

The `run()` function in `cmd/moombox/main.go` initializes services in this exact order. The order matters because later services depend on earlier ones.

### 1. Config
Load TOML configuration via `config.Load(configPath)`. An explicit `-config` path is the only file considered; only when the flag is absent does it search `./config.toml`, `./config/config.toml`, `~/.config/moombox/config.toml`. If no config file exists — either the named one or, searching, any of the three — defaults are used and the setup wizard will be triggered via the web UI; the path that was asked for stays the save target, so the first write creates the file exactly where it was named.

Auto-converts plaintext password to scrypt hash if detected (one-time migration on first run after setting a password).

### 2. Logger
`logger.New()` creates an slog-based logger with:
- File rotation (configurable max size and file count)
- Ring buffer for recent log lines (served to web UI and TUI)
- Pub/sub subscription system (log lines broadcast to WebSocket clients)
- Level filtering (DEBUG/INFO/WARN/ERROR, changeable at runtime)

### 3. Updater
`updater.New()` creates the GitHub release checker. Its `CleanupOldBinary()` sweep of the previous update's `.old` (and `.failed`) binary does not run here but at the first-successful-boot milestone in `run()`, after the database opened and the web bind resolved, so a boot-crashing update still has its rollback artifact. Performs Ed25519 signature verification before applying binary swaps.

### 4. Database
`database.Open()` opens SQLite with WAL mode, 5-second busy timeout, foreign keys enabled, single-writer connection pool (`MaxOpenConns=1`). Runs schema migrations (`migrate()`, up to `schemaVersion` in `internal/database/migrations.go`, whose current value `appendix-metrics.md` tracks). Prepares the hot-path `GetJob` statement (`prepareStatements`). Starts no goroutine: every job write is a synchronous `UpdateJobFields` call.

### 5. Cookie Jar
`cookies.NewCookieJar()` creates the cookie container. If `cfg.Cookies.CookieFile` is set, loads cookies from the Netscape-format file. Auto-detects platforms (YouTube/Twitch) from cookie domains if not explicitly configured.

### 6. YouTube Service
`youtube.NewService(jar, log)` creates the YouTube service. `Init(ctx)` fetches the YouTube homepage to extract visitor data and the Innertube API key. These are needed for all subsequent API calls.

### 7. Twitch Service
`twitch.NewService(jar, log)` creates the Twitch service. Initializes GQL API authentication from cookies (looks for `auth-token` cookie). Logs auth status at startup.

### 8. PO Token Provider + BotGuard Sidecar
`bgutils.NewPotProvider()` creates the BotGuard PO token provider with its triple-layer cache: session cache (6h TTL), minter cache (single-minter design, dynamic TTL from BotGuard response), and inflight dedup (concurrent requests share a single generation via channel synchronization). Immediately after, when `cfg.Bgutils.UseSidecar` is true (default), `sidecar.New(...)` constructs a `Sidecar` and `Start(ctx)` launches the embedded Node.js subprocess: extract the platform's `node-<goos>-<goarch>.gz` + `sidecar.tar.gz` from `go:embed` to `os.UserCacheDir()/Moombox/sidecar/`, apply user-only DACL, spawn `moombox-sidecar[.exe] src/server.js` pinned to a Windows Job Object, and wait for its `ready` event. `potProvider.SetSidecar(s)` attaches the handle before that first start, which puts `PotProvider` in sidecar mode: every mint goes to the sidecar, and while it is down a mint fails at once — the goja path mints no PO token in practice, so falling through to it only cost time. Failure to start the sidecar is non-fatal — Moombox logs a warning and the supervisor keeps retrying. The per-platform blob (`node-linux-amd64.gz`, `node-linux-arm64.gz`, `node-windows-amd64.gz`) is selected at build time by the `embed_<goos>_<goarch>.go` files; the extraction directory is `os.UserCacheDir()`'s (`%LOCALAPPDATA%` on Windows, `~/.cache` on Linux — `/data/.cache` in the Docker image, where `HOME=/data`).

### 9. Cipher Solver
`cipher.NewGojaResolver(cacheDir, log)` creates the goja cipher resolver (cache directory `%TEMP%/yt-cipher`, a 10-VM LRU keyed by `player.js` URL); `cipher.NewSidecarSolver` and `cipher.NewCompositeSolver` layer the BotGuard sidecar's V8 ejs in front of it, the composite keeping the sig specs it learns from the sidecar in the resolver's player cache so known players' signatures survive a sidecar outage. The resolver is wired to `ytService.PlayerAPI.SetCipherSolver()` for the signature timestamp, and the composite solver to the worker, which resolves each chosen format's URL after selection. Uses full AST parsing with regex fallback for extraction.

### 10. Notification Manager
`notifications.NewManager(cfg, log)` creates the notification dispatcher. Currently supports Discord webhooks. Sends notifications for: stream found, stream live, download starting, download finished, download error, auth required, trim created, update available. "Stream found" is sent for broadcasts and new VODs only — a backlog VOD is queued silently and announced by its "download starting" when the archive-slots scheduler admits it (`announcesJobFound`, `cmd/moombox/monitor_callbacks.go`), so a deep backfill does not send one notification per catalog VOD at once.

### 11. Trim Service
`worker.NewTrimService()` creates the FFmpeg-based clip creation service. Prevents concurrent trim operations on the same job via the `activeOps` map: a second trim of a job, of the same range or another, is refused (409) while the first runs. The TUI calls `CreateTrim`, which returns when the trim is done, and so does a finished job's post-download trim (`postDownloadTrim`, `internal/worker/orchestrator.go`, under the job's context) — through this same service, so it holds the job's slot too, shows in `RunningTrims` and `trim_status`, and `Stop` reaches it; a service of its own would let a dashboard trim of the range it was encoding start beside it, both writing one `.partial.mp4`. The dashboard's route calls `StartTrim`, which checks the request, starts the encode as the service's own task and returns the task at once. Every trim runs under the service's own context as well as its caller's — `Stop` (shutdown) cancels them all and waits briefly for each to clean up. The encode writes `<name>.partial.mp4` beside the finished name in `trim/` (`partialTrimPath`) and is moved into place only when whole, so a trim that fails or is stopped removes its partial file and none ever sits under a finished trim's name.

A trim across two or more parts of a quality-split job re-encodes each part into an intermediate first; those go in `<name>.partial.moombox-trim-<n>/` beside the partial file (`trimTempDirPattern`, `internal/engine/muxer_trim.go`), on the output volume the disk alerts watch — under the system temp directory they filled the container's `/tmp` in Docker (the host's `/var/lib/docker`) and RAM on a tmpfs `/tmp` — and inside the trim's stem claim, so the orphan sweep never offers one mid-encode. The directory is removed when the trim ends; what a hard abort leaves is removed at the next start once a day old (`worker.CleanupOldTrimTemp`: every job's trim directories, and the system temp directory older versions wrote to). Each trim's progress and outcome go to the hook `SetOnEvent` installs (the `trim_status` frame — progress at most every 250 ms), and `RunningTrims` lists the trims in flight with their latest progress for `initial_state`; a trim that broke — not a refusal, nor one a stop cut short — sends `trim_error`.

### 12. Download Worker
`worker.NewDownloadWorker()` creates the main job processing engine. Internally creates:
- `JobQueue` with configurable max parallel VOD downloads (default 10; broadcasts are never throttled by the pool) and 100 lifecycle slots, claimed at the download decision rather than at dequeue
- `Scheduler` that admits backlog (`Queued`) jobs at most `archive_slots` at a time per channel — the only path out of `Queued`
- `StreamProcessor` for probing stream status and waiting for live
- `DownloadOrchestrator` for the full download lifecycle

Dependencies injected via `DownloadWorkerDeps` struct: cipher solver, PO token provider, Twitch service, notification manager, and the trim service (§11, built ahead of the worker so it can be handed in): a finished job's post-download trim runs through it, never through a service of its own.

The `OnCookieRefreshNeeded(platform string) worker.CookieRefreshOutcome` callback is wired to `autoCookieSvc.RefreshCookiesDetailed()` for automatic cookie recovery on auth failures. It answers per platform (`RefreshResult.Verdict`), not per service: a healthy Twitch must not tell a YouTube job to retry into the same failure. It answers in five ways, not two, and only a real failure is called one. `CookieRefreshRestored` retries the job. `CookieRefreshNotRestored` — the platform's credentials were refused, there are none, or the pass declined to run (`RefreshResult.Ran` false: setup in progress, a refresh already in flight, nothing to refresh) or errored — leaves it parked and logs `auto cookie refresh failed — the cookie file has to be replaced by hand` (Warn), naming the file.

The other three leave it parked without that advice, because nothing judged the cookies: `CookieRefreshSkipped` — a browser holds the profile (`cookies.ErrProfileInUse`), which the callback has already logged as a skip — logs that the job stays parked (Info); `CookieRefreshUnconfirmed` — the pass ran and could not establish whether the cookies work (`cookies.RefreshUnknown` with `Ran` true) — logs `auto cookie refresh could not confirm the cookies — the job stays parked; R C / Recheck will tell` (Info); and `CookieRefreshOff` — `cookies.auto_enabled` is off, so nothing was attempted (`jobCookieRefreshDisabled`) — logs `automatic cookie refresh is off — replace the cookie file or turn it on in Settings` (Warn), naming the file. The closure's tail, which logs the outcome and picks the answer, is `jobCookieRefreshOutcome` (`cmd/moombox/services.go`).

### 13. Feed Monitor (YouTube RSS + members-only)
`monitor.NewFeedMonitor()` polls YouTube RSS feeds (`https://www.youtube.com/feeds/videos.xml?channel_id=...`) for new videos. Default interval from config. Immediate first check on startup, then timer-based with jitter. When `membership_discovery` is enabled (default) and YouTube auth cookies are present, `checkChannel` additionally fetches the channel's authenticated `/membership` tab (`youtube.FetchMembershipVideos`) — the only discovery source for members-only content, which RSS/DECAPI never list. `membershipConfirmedNonMember` (`cmd/moombox/monitor_callbacks.go`) collapses that fetch's session verdict and access bit into a single confirmed-non-member flag ONLY for a recognised `SessionAuthLoggedIn` session that also denies channel access; an unrecognised or ambiguous verdict, or a fetch error, answers neither question and is never memoized. A confirmed non-member is memoized for `membershipMemoTTL` (`internal/monitor/feed.go`, 6 h) and its authenticated fetch skipped until the horizon passes; a member is never memoized, because their tab is the only place a members-only live stream is ever listed.

Every cycle still owes the session at least one membership fetch that RETURNS: `armMembershipLiveness` (`internal/monitor/feed.go`) nominates the memoized channel with the earliest horizon, rotating, and fails over to another memoized channel within the same cycle when the nominee's fetch errors, bounded by `membershipLivenessMaxTries` (`internal/monitor/feed.go`, 2 attempts) so a cycle where every fetch fails cannot walk the whole channel list — only nomination-driven fetches spend that budget. That fetch carries the YouTube login verdict the cookie health signal reads (`routeLivenessVerdict` in `cmd/moombox/monitor_callbacks.go`), so a cycle that fetched nothing would observe nothing; the nomination guarantees only a fetch that returns, not a verdict, so the cookie subsystem's tier-2 `FallbackLiveness` probe remains the backstop when no fetch has recently landed a conclusive observation. A repaired YouTube session or a changed account identity clears every non-member memo (`clearYouTubeMembershipMemo` in `cmd/moombox/monitor_callbacks.go`, wired to both `OnAuthRecovered` and `OnCredentialsChanged`) so members-only discovery does not wait out the TTL.

Members-only candidates are probed with the authenticated `ProbeVideoAuth` closure so a members VOD classifies correctly instead of misfiring as "upcoming". A membership fetch failure is logged, writes no memo, and never marks the RSS feed unhealthy (independent signals).

`checkChannel` runs four steps per channel per cycle:

- **FETCH**: RSS + membership, independently fallible.
- **STORE**: upsert every listed item into the persistent `feed_items` table, tracking which IDs are new this cycle.
- **WALK**: a serial probe pass over the store's archive scope — everything published within `archive_window_days`, default 3 and per-channel overridable, plus ALL upcoming/live rows regardless of age and the still-unresolved ones (`assumed`-dated rows, and RSS rows first seen inside the window, whose `<published>` is only the announcement time) — applying `HasActiveJob` dedup, term filtering, and probe-status rules, with per-source early exit once a date-ordered source falls entirely outside the window. The probe-status rules:
  - A probe whose broadcast has ended — `BroadcastEnded`, see platform-services.md — reads `post_live` and is stored `vod`, so an ended stream leaves the upcoming arm whatever formats the probe saw.
  - `probeAndClassify` in `internal/monitor/utils.go` decides a refusal first, so a members-only, sign-in or private refusal stays denied.
  - An end read off weak signals alone is confirmed first by one signed-in WEB call, and one it cannot confirm makes no job and is stored `vod` with its re-check scheduled — after 1 h, then 6 h, then daily (`feed_items.recheck_at`) — rather than never probed again, so a stream that turns out live or upcoming is still found; the restart carve-out's every-cycle probe of an ended stream with no job goes on while a re-check is pending.
  - A status probe that cannot tell — a refusal that said nothing about the broadcast, its one escalation settling nothing either (`*youtube.StatusProbeInconclusiveError`) — is an errored probe, so nothing is written, and the row is held — probed again after 1 h, then 6 h, then daily, by the walk and the archive's refresh alike, until a probe answers (`FeedMonitor.noteProbeOutcome`, in process; a newly listed video is still probed at once, and a transient failure is retried next cycle).
  - The first cycle after the v24 upgrade resets the channel's in-scope `not_a_stream` rows to `unknown` before it walks, so each row so misfiled is probed once under the new rule (`ResetMisfiledFeedItems`, data-and-storage.md § Tables, `feed_reprobe_owed`).
  - A row whose probes keep failing warns once a spell, Debug after (`FeedMonitor.inFailureSpell`).
- **ARCHIVE**: re-read the scope and decide job creation per row.

ARCHIVE assigns each job a disposition: broadcasts (live/upcoming) and VODs first inserted this cycle — or by a cycle within the last 24 hours (`newVODCarry`, `internal/monitor/feed.go`) that has not jobbed them yet, so one failed first probe does not demote new content to the backlog; the carry is in-process, and a restart in between still does — are admitted immediately (`queue_priority` 0), while backlog VODs already known to the store are created as `Queued` (`queue_priority` 1) and paced by the worker's per-channel `archive_slots` scheduler — a backlog sweep never delays new or live content.

A companion `monitor.NewBackfillWorker()` owns the full-catalog backfill (channel add, window widening, or a manual `R B` / `POST /api/backfill/rescan` re-run): it scans the channel's `videos`, `streams`, and (when membership is active) `membership` tabs to window depth via YouTube's `/browse` continuation API, upserting into the same store. Scans are strictly serial across channels on a single consumer goroutine, globally paced at 1 tab page/second, resumable via a cursor persisted in `channel_state.backfill_state`, and report progress to both UIs. The cursor records the window its finished tabs were judged against, since a tab that stopped at the window's edge is finished only for that window: a retry at a wider one — the config widened between an interrupted scan and its retry, or while the process was down — scans from page 1, while a narrower one resumes it. The sweep that queues scans rides the feed-monitor cycle, so startup and `kickMonitors()` both trigger it. The scan runs on the worker's goroutine, so the rows it writes land after the cycle whose sweep queued it has already walked the channel; a scan that COMPLETED and INSERTED at least one row the store did not have reports it (`OnNewRows`, called once with the count), and the host kicks the feed monitor (`CheckNow`) so those rows are probed and jobbed now rather than a `feed_check_interval` later.

A kick that lands mid-cycle is latched and re-run right after (`runCycle`'s `pendingKick`), so several scans completing in a row cost one extra cycle. An incomplete scan reports nothing although it wrote rows: the kicked cycle sweeps again, and the sweep re-queues a channel whose scan ended short, so a tab failing every other page would cost a whole feed cycle per page of progress — its rows wait for the sweep-retry's own cycle. A completed scan that only re-sighted rows already present (a forced re-scan of a settled channel) reports nothing either. Without the kick, an upcoming stream the backfill alone found (RSS down, DECAPI showing a newer video) would get its job minutes after the scan that found it.

**Disabling a channel pauses its scan**: the next sweep drops a scan still queued for it and cancels one running (`pauseLocked`, `internal/monitor/backfill.go`), and a queued scan is checked against the live config once more as it reaches the consumer (`ChannelEnabled`, wired to `liveChannelEnabled` in `cmd/moombox/services.go`), since that sweep runs only at the start of the next cycle. Unlike the cancel a widened window makes, a pause keeps the cursor, so enabling the channel again resumes the scan where it stopped.

**Removing a channel** deletes none of its jobs by itself (owner decision, W25-09). The sweep that finds a channel gone from the config — however it left: the Remove action, `PUT /api/config`, a hand-edited `config.toml`, a TUI save — cancels its scan and deletes its feed history alone (`CancelAndPrune`, `internal/monitor/backfill.go`: `feed_items` and `channel_state`), so a channel added back later rescans from page 1. It does not delete the channel's `Queued`, `Upcoming` and `COOKIES?` rows: a `COOKIES?` row can be a live capture whose cookies died mid-stream, parked with its segments staged for Resume, and deleting it would leave the footage with no job to resume or mux it from, and the Files cleanup would offer it as a deletable orphan. The kept jobs keep working. An `Upcoming` broadcast is still recorded when it goes live (nothing in the worker reads the channel's config entry; the row carries its own output directory and quality). A `Queued` backlog VOD is still admitted: `NextQueuedJobs` (`internal/database/database_jobs.go`) LEFT-JOINs `feed_items`, ordering a row whose partner the prune deleted after the dated ones, and a channel with no config entry gets the global `monitors.archive_slots` from the resolver.

A parked one resumes to `Queued` like any backlog row (`CookieResumeStatus`). A Twitch channel's jobs — which carry no channel ID, and which the confirmation counts by the login their URL names (`worker.TwitchJobLogin`) — are kept by either choice. A manual add waiting for the channel to go live still records it (it polls the channel itself, `waitForTwitchLive`); what stops with the channel is the Twitch monitor's two automatic ways out of `Error`, which only a configured channel's poll drives: the offline auto-retry, and the automatic mux of a capture parked as `twitch_end_unconfirmed` (`dispatchEndedBroadcasts`, `internal/monitor/twitch.go`). Retry and the Mux action still do either by hand. Deleting them is the operator's choice, made in the removal itself (`worker.DeletePendingChannelJobs`, `internal/worker/channel_removal.go`): the channel's `Queued`, `Upcoming` and `COOKIES?` rows go together with their history rows — an orphaned history row would block the video's re-archive — except a row whose staging directory holds anything (`HasStagingFiles`), which is kept and named, and nothing active, finished or failed is touched.

Re-adding the channel neither duplicates a kept job nor loses one: its video ID is still taken (`AddJob` keys on it), its history row is still there, and the walk's `HasActiveJob` gate skips a row still pending. A monitor cycle already under way when the channel goes cannot recreate the rows a removal just deleted: it took its channel list as it started, so `createYouTubeJob` (`cmd/moombox/monitor_callbacks.go`) asks the live config (`liveChannelEnabled`) before it creates any job.

### 14. DECAPI Monitor
`monitor.NewDecapiMonitor()` uses the DECAPI API to find the latest video for YouTube channels. Rate-limited to 60 requests/minute (reads rate limit headers from responses). Stagger of 1 second between per-channel requests. The request and the classification hold separate deadlines: `fetchLatestVideo` (`internal/monitor/decapi.go`) owns the 15-second request timeout and releases it as soon as the body is read, and the probe then runs under `decapiProbeBudget` (`internal/monitor/decapi.go`, 60 s) derived from the cycle context — so a slow DECAPI answer never shortens the probe. Because DECAPI reports a channel's NEWEST video, a dormant channel would otherwise re-probe the same finished VOD every cycle; a per-channel memo skips the probe when the video ID is unchanged, its last classification was terminal (`isTerminalFeedStatus` in `internal/monitor/feed_status.go` — `vod` or `not_a_stream`, the set the feed walk's `settledTerminal` reads too), and the reason it was not jobbed still holds: the processing history holds it (it was jobbed — clearing the history row re-opens the video on the next cycle), it was judged outside the same archive window, or it was skipped because the channel does not archive VODs and still does not.

A `post_live` newest video — a broadcast the probe found over — is recorded as the `vod` it is (`feedStatusFor`, `internal/monitor/feed_status.go`, the mapping the feed walk's `applyProbe` stores) and settles the same way: recorded raw it was never terminal, and a channel whose newest video was an ended stream without formats (age-gated, its recording not available, formats withheld) was probed every 15 s for good, with a WEB date fetch each cycle on a channel archiving VODs. An end that rests on weak signals the shared end check (`ConfirmEnd`, [platform-services.md](platform-services.md) § Stream Status Classification) could not confirm makes no job and is held by the memo for the feed's re-check backoff — 1 h, 6 h, then daily, an errored re-check resuming where it was — never every cycle and never for good; a re-check that finds the stream live or upcoming announces it as a broadcast. The memo is in-process, so a restart re-checks at once. A status probe that cannot tell (`*youtube.StatusProbeInconclusiveError`) is an errored probe and memoises no classification, so the bot wall's `not_a_stream` is never memoised as terminal.

The newest video is therefore probed again every cycle for as long as the probe stays inconclusive — three requests a probe signed out, ANDROID_VR plus the escalation's embed page and `web_embedded` call — and its failure is logged at Warn on that video's first sighting and at Debug on every repeat (`ProbeClassifyParams.Repeat`), not at Warn every 15 s. DECAPI writes no history itself: a skipped or given-up video is not a created job, and both monitors gate VODs on history, so a history row written after three failed probes, or on that skip, would keep the video from ever being archived, even once the probe recovered or `include_non_live_content` was turned on.

### 15. Twitch Monitor
`monitor.NewTwitchMonitor()` polls Twitch GQL for live streams. Default 15-second interval. Channels are batched into GQL requests of up to 30 logins, with a 500 ms stagger between chunks — including after a chunk whose whole request failed (`checkChunk` in `internal/monitor/twitch.go`), since a 429 or 5xx is exactly when pacing matters. Uses the Twitch service's GQL client for stream info queries. A batch Twitch refuses because of the saved `auth-token` — `ErrTwitchAuthExpired`, a 401/403 to a request that carried it — is sent once more without the token by `twitch.Service`'s `streamInfo` (`internal/twitch/service.go`; G21, owner decision D19), and the monitor classifies the signed-out answer like any other; the refusal is reported through `Service.SetOnAuthLoss` — wired by `initServices` to the same `twitchAuthLossHook` the worker's downgrade reports use — as `status-check-token-refused`, so the platform still reads as needing a login. As a whole-batch failure, a dead token would stop live detection for every Twitch channel until cookies.txt was replaced.

Only a repeat that is answered proves the token was the problem: one refused too returns the original refusal, unreported. A capture still mints its playback token with the login and parks in `COOKIES?`. A live channel creates no job while a manually added job has claimed the broadcast (`manualJobClaims`, `internal/monitor/twitch.go`, over `ManualTwitchJobs`, `internal/database/database_jobs.go`): one waiting in `waitForTwitchLive` takes whatever goes live next, and one downloading has claimed the broadcast its `stream_start_time` names. A manual add for an offline channel is `tw_manual_<login>_<ns>` and carries no stream ID, so the stream-ID dedupe never matches it, and without the claim the monitor would record the broadcast a second time beside it. A manual job parked in `COOKIES?` or muxing an earlier broadcast claims nothing — standing aside for those would block every later broadcast on the channel. A Twitch channel with `twitch_archive_clips` on also has its new clips listed, once an hour on a goroutine of its own that the poll never waits on, and each clip it has made no job for queued as a paced `Queued` row ([platform-services.md](platform-services.md) § Twitch Clips).

The Twitch VOD backlog (owner decision D18) is a separate, opt-in loop: `monitor.TwitchBacklog` (`internal/monitor/twitch_backlog.go`) lists each enabled channel with `twitch_vod_backlog` set every hour — one page of `FilterableVideoTower_Videos`, every type, newest first — and queues each video no job has had (history) as a `Queued` backlog VOD (`worker.QueueTwitchVideos`), skipping the archive of a broadcast a live job of the channel captured (published within ten minutes of its `stream_start_time`, `twitch.ArchiveVodStartTolerance`) — a live job counting as a capture only when it holds footage (an archive file, recorded parts or staged media), was Cancelled, already has a gap-fill plan, is still capturing (Upcoming, Live, Downloading, Muxing), or is an Error row the Twitch monitor will re-initialise when the broadcast is live again (`jobstate.TwitchAutoRetryPending`: an offline or unreachable stop before the first segment, retries left — queuing the VOD beside it would record the broadcast twice), so the archive of a broadcast whose capture failed or parked in `COOKIES?` before its first segment is queued (owner decision PR-M4; a skip is logged once per process, naming the job it deferred to) — and every video whose title the channel's `terms` do not match (`MatchesTerms`, as for its live broadcasts), then wakes the Backlog Scheduler.

A pasted channel video list (`/<ch>/videos[?filter=…][&sort=…]`) or collection (`/collections/<id>`) queues the same rows from every add path (`POST /api/jobs` with `twitchType: "listing"`, `moombox add`): the list is read with `broadcastType` null and the filter applied to each video (`twitch.API.ListChannelVideos`, VideoMetadata classifying a node that carries no type), since yt-dlp's tests record the server-side filter returning no entries; a page after the first that fails ends the list with what was read, as upstream's `fatal=False` paging does. A collection node that names no owner takes VideoMetadata's (`CollectionVideos`), and one still without is refused rather than created `Queued` with no `channel_id` the scheduler could admit it under; each VOD not queued is logged at Warn by ID with why, and the add's answer always carries `failed`, 0 included (purpose review M9). Both kinds of row carry the owner's login (or the configured channel's ID) as `channel_id`, which is what the scheduler paces them by; a pasted listing's rows are also `manually_added`, and removing the channel never deletes them, while the backlog's are deleted with its pending jobs (owner decision PR-D1, `worker.DeletePendingChannelJobs`).

### Twitch Archive-VOD Gap-Fill

Owner decision D17 and its four follow-ups; the capture's half is `internal/worker/twitch_gapfill_plan.go`, the fill's `internal/worker/twitch_gapfill.go`, the plans are table `twitch_gap_fills` (schema v25). Beyond upstream: yt-dlp's answer to a late join is to record the archive VOD instead of the live stream (`--live-from-start`, `TwitchStreamIE._real_extract`, twitch.py b77c9304e); Moombox keeps the live capture and fills only what it lacks.

- **Coverage.** Every live part's downloader reports each written segment's program date-time and duration (`engine.DownloaderOptions.OnSegmentWritten`); `coverageRecorder` keeps the part's first start and last end in `twitch_coverage.json`, written at the first segment, at most 30 s behind after it, and in full when the part closes. A resumed part keeps what its file held; a discarded short part forgets it. A part whose file already holds footage when its recorder is made, with no coverage file to say since when (a capture resumed across the upgrade to this build), is marked `startUnknown`.
- **Ad breaks.** With `twitch_gap_fill_ad_breaks` the engine returns `ErrAdBreakEnded` at the first content segment after a stitched-ad break (`SplitOnAdBreak`), and `ExecuteTwitch` closes the part there, marked `endedAtAdBreak`, and continues on the same variant at that segment. Without it a break stays an inline timestamp jump inside its part and is not filled.
- **Plan.** At finalize `gapSpansFor` turns the parts' coverage into spans: the opening when the first frame is more than `gapFillLateStartAfter` (1 min) after `stream_start_time`; each hole between consecutive parts wider than `gapFillMinGap` (3 s), an ad break's however short; and the tail after the last part when the broadcast ended during an outage. A part with footage and no coverage, or a `startUnknown` one, makes no plan at all: any span around it could be footage it already holds. A plan is kept only once the job is Finished, and is looked at at once: storing it wakes the gap-fill sweep (`gapFillKick`), so a VOD Twitch has already completed is filled without waiting; one not ready yet falls to the backoff (10 min doubling to 3 h). A live capture muxed instead of finalized — any Mux of an Error or Cancelled live row (owner decision FE-25): `twitchEndedOfflineErrMsg`, `park_reason` `twitch_end_unconfirmed` (by the Mux action or `AutoMuxEndedBroadcast`), any other error, or the operator's Cancel — gets its plan from `twitchMuxGapFillPlan` in `muxJob`, from the coverage still in staging.

  A Cancelled row's tail is closed (`twitchMuxTailOpen`, owner decision FQ-2): the operator's Cancel says the recording ends where it stopped, so whenever it landed — while Downloading, `stream_end_time` still empty, as while Muxing — and whatever marker it left on the row (CancelJob writes the status alone), its Mux fills only its late start and gap splits. A Mux of the Cancelled row that fails rewrites it to Error, so `MuxJob`'s failure writes carry the close on as `park_reason` `mux_after_cancel` (`ParkReasonMuxAfterCancel`), kept through every later Mux that fails too; only a Retry or Reinitialize, which writes another status and clears `park_reason`, ends it, and the row failing again is read by the rules that follow. Otherwise its tail is open for the two markers and for any row whose `stream_end_time` is empty, the capture cut off mid-broadcast; a row that reached ExecuteTwitch's finalize (which writes `stream_end_time` just before `muxAndFinalize`) and then failed its mux holds the broadcast to its end, so its tail is closed and only its late start and gap splits are filled — an open tail would cut the VOD's last segments again as a duplicate part.

  The fill still only adds parts beside the archive and never touches the recorded footage. A clip or VOD row, a boot re-mux of a Muxing row (its own finalize planned it) and a staging without placeable coverage get none.
- **Fill.** `twitchGapFiller.step` drops a plan whose job is gone or no longer Finished, and settles one past its deadline (24 h after the plan was made — the capture's finalize, or the Mux) as kept, with one Info line naming the last reason. Otherwise it finds the VOD (`ArchiveVodBetween`: of the videos published within `ArchiveVodStartTolerance`, 10 min, of the broadcast's start on either side and before end, the one closest to the start that VideoMetadata confirms is an ARCHIVE — owner decision PR-M3: with this broadcast's archive gone, a later broadcast's is never taken, and one published a little before `createdAt` is still found; no query returns a video's stream ID to match on instead), waits while VideoMetadata says it is recording or its playlist lacks ENDLIST, or while the output volume is at disk_critical (the reading the Backlog Scheduler's gate closes on). Refuses a VOD more than a minute shorter than the stretch the capture covered (its timeline cannot be the broadcast's wall clock), keeping the archive as recorded.

  Where the plan knows the broadcast's end (`EndKnown`: ExecuteTwitch's finalize without an outage, or `twitchMuxEndKnown` — a Mux of an Error row whose tail is closed), compares the VOD's length with the broadcast's span, `createdAt` to the last part's end, logs the drift with every fill, and past `gapFillDriftLimit` (5 s) keeps the archive as recorded with the drift as the reason (owner decision PR-R6). Takes the rendition the capture recorded (by name, else the same selection), maps each span with `vodSegmentOffsets`/`vodSegmentRange` (1 s pad, the intersecting segments), fetches and muxes each into `{base} - recoveredN.mp4` beside the archive, and commits: `ReplaceJobSegmentsIf` with every part in time order (the recorded ones keyed by their coverage), applied only while the job is still Finished, checked in its own transaction, then the job's `output_file` (kept on the first recorded part — a recovered part is never the main file, owner decision PR-R5), `length_seconds` and `file_size` through `UpdateJobFieldsIf` on Finished.

  A span the VOD does not reach stays a gap. A segment still answered 403, 404 or 410 after its three tries is left out of the span and logged — on Twitch's VOD CDN that is a muted part no tool can fetch, and yt-dlp's `skip_unavailable_fragments` skips a fragment that fails every retry — and a span whose every segment is refused stays a gap; any other fetch or mux failure removes every file the attempt wrote and reschedules on `gapFillBackoff` (10 min doubling, 3 h cap). Each plan's look recovers its own panic and settles the plan as kept, so the sweep outlives it.
- **Shown** (owner decision PR-R5). A plan that ends — filled, or the archive kept as recorded — stays on its row with its outcome (`gapFillOutcome`), no longer a plan to run: the row is looked at weekly (`gapFillOutcomeRecheck`) only to drop it once the job is gone, and a later capture of the job that plans nothing drops it. `worker.TwitchGapFillStateOf` reads it for a Finished live Twitch job as `{state: pending|filled|kept, spans, until, reason}`, the `gapFill` field of `GET /api/jobs/{id}` that job details render as "Gap-fill pending: N spans, until <time>", "Filled N spans" or "Kept as recorded: <reason>". Each look tracks the job for per-job log routing while it runs (`TrackJobForLogs`, then `restoreJobLogRouting`), so its lines reach the job's own log.

### 16. Cookie Refresh Service
`cookies.NewRefreshService()` validates cookies and checks auth status periodically — every 30 minutes (`defaultRefreshInterval`, `internal/cookies/refresh.go`); the `cookies.refresh_interval` setting (6h by default) drives only the separate browser-refresh timer in `AutoCookieService`. Detects auth loss by comparing current status against expected platforms. Triggers `OnRecoveryNeeded` callback when auth is lost, which attempts auto-cookie recovery.

### 17. Auto-Cookie Service
`cookies.NewAutoCookieService()` extracts cookies directly from Firefox/Chromium browser profiles. Handles the full flow: find browser profile, decrypt cookies, verify auth via API callbacks (`VerifyYouTubeAuth`, `VerifyTwitchAuth`), write to cookie file, persist verified platforms to config.

### 18. Web Server
`web.NewServer()` creates the chi-based HTTP server with:
- WebSocket hub for real-time updates
- Auth middleware (session-based with scrypt password hashing)
- Rate limiters (API: 20/min, PO token: 10/min, login: 5/min, password change: 3/min)
- CSRF protection (Origin/Referer validation)
- Static file serving (embedded via `go:embed`)
- SPA fallback routing

Route registration happens in `main.go` by calling `routes.*Routes()` functions, each receiving their specific dependencies.

### 19. TUI
If TTY is detected and `--headless` is not set, creates and runs the BubbleTea terminal UI. The TUI receives updates via channels and database pub/sub callbacks.

### Event Wiring

After all services are created, `main.go` wires the event callbacks:

- `feedMon.OnVideoFound` / `decapiMon.OnVideoFound` -> creates YouTube job in database per the callback's `JobDisposition` (broadcasts and new VODs enqueue in the worker immediately; backlog VODs are created `Queued` for the scheduler), broadcasts via WebSocket
- `feedMon.BackfillSweep` -> queues backfill scans for channels needing one; `s.backfillRescan` (TUI `R B` chord + `POST /api/backfill/rescan`) forces the same sweep for every channel
- `twitchMon.OnStreamFound` -> creates Twitch job, enqueues, broadcasts
- `feedMon.OnSchedule` / `decapiMon.OnSchedule` / `twitchMon.OnSchedule` -> broadcasts all three monitor timer values via WebSocket
- `db.OnJobChange` -> `wsHub.BroadcastJobProgress()` for a progress-only write, otherwise `wsHub.BroadcastJobUpdate()` (per-job WebSocket messages); re-syncs per-job log routing on a status write
- `db.OnJobAdded` / `db.OnTrimsChanged` -> `wsHub.BroadcastJobUpdate()` for the one job; `db.OnJobDeleted` -> `onJobDeleted` (clear the job's log buffer + `BroadcastJobDeleted`)
- `db.OnJobsChange` (the two bulk writers only) -> `wsHub.BroadcastJobsUpdate()` (full job list) and the notifier's `RetainJobs`; per-job log routing is left alone (the channel prune drops its deleted rows' logs itself, under the write lock)
- `log.SetLineRouter(db.RouteLogToJobs)` (per-job log buffers) — synchronous, inside every log call, so a line logged before a status write is routed before the write can untrack its job — and `log.SubscribeLines()` -> `wsHub.BroadcastLog(text, seq)` (`wireLogForwarding`), each frame numbered as the logger's ring numbered the line
- `cookieRefresh.OnRecoveryNeeded` -> `runCookieRecovery()` in a background goroutine: `autoCookieSvc.RefreshCookiesDetailed()`, then notifies on the triggering platform's own verdict (OK / Failed / Unknown)

All monitor `OnVideoFound`/`OnStreamFound` callbacks are wrapped with `defer func() { if r := recover() }()` for panic isolation.

## Download Pipeline

### StreamProcessor

The `StreamProcessor` is the first stage of job processing. It determines what a video is (live, VOD, upcoming, not a stream) and whether it should be downloaded.

**Entry point:** `Process(ctx, job) -> (StreamProcessResult, error)`

**YouTube path:**
1. Performs a full multi-client fetch via `yt.GetVideoInfo()` (WEB + TV clients for accurate playability and complete metadata)
2. Updates job metadata in the database (title, channel, thumbnail, description, scheduled start time, length) — unless the run was cancelled during the fetch, which can still succeed on a cancelled context: a run that did not take an owed "Stream Found" (`found` in operations.md) stops there, writing and sending nothing, when its context is cancelled or its row reads `Cancelled` or is gone (an operator's Cancel writes the row and a delete removes it before either cancels the run, and a channel removal's bulk delete of its pending jobs cancels none)
3. Checks playability (members-only, login required, age restricted, etc.). A rate limit or a captcha (`rate_limited`) is the one refusal of the session rather than of the video: on an extraction with no formats it is returned marked `ErrRateLimited`, for `processJob` to wait out (*A YouTube rate limit is not an error*, under Transition Rules), and a run it refuses — or one whose whole cascade was answered 429 — does not take an owed "Stream Found": the fetch that answers announces, with what it learned. An extraction that came back with formats is downloaded whatever the verdict says, as upstream words the refusal only `if not formats:`
4. Routes based on `StreamStatus`:
   - `StreamLive` -> Updates status to Live, returns `ShouldDownload=true, IsVod=false`. The write applies only to a row with no outcome (`UpdateJobFieldsUnlessTerminal`): an operator's Cancel writes the row before it cancels the run, so one that lands after `Process` read the row — after the take of an owed "Stream Found", or on the run's own metadata write — is not written over with Live; a write refused for the row's outcome stops the run as a cancelled one (`cancelledResult`). A write that failed on a row with none — another process holding the database's write lock past `busy_timeout`, an I/O error; the conditional write reports false for both — is not a Cancel: `writeUnlessOutcome` re-reads the row and stops only on a terminal or missing one, so the stream is still recorded, as it was while the write was unconditional
   - `StreamVOD` / `StreamPostLive` -> Writes `is_vod` and no status (the download-slot wait is still ahead; the orchestrator writes Downloading once the download starts), returns `ShouldDownload=true, IsVod=true`
   - `StreamNotAStream` -> Downloads as VOD only if `ManuallyAdded` or `AllowNonStream` is true
   - `StreamUpcoming` -> Enters `waitForLive()` polling loop

**waitForLive() loop:**
1. Updates job status to `Upcoming`, unless the row already holds an outcome (`UpdateJobFieldsUnlessTerminal`): an operator's Cancel that landed after `Process` read the row stays `Cancelled`, and the loop's first check (a cancelled context, or a row that reads `Cancelled` or is gone) stops the run
2. If chat download is enabled, attempts to start an early chat downloader (`tryStartEarlyChat()`) to capture pre-stream chat messages. Each probe re-evaluates the decision through `earlyChatNeedsRestart(chatDl, finished, lastRestart, now)` (`internal/worker/stream_processor_youtube.go`), which restarts when there is no downloader OR when the current one's run has ENDED and the previous start is at least `earlyChatMinRestartInterval` (5 min) behind — a run that dies immediately on dead cookies would otherwise cost one full watch-page fetch per probe for the rest of the wait, while the ~50-minute stale-exhaustion case the restart exists for is never delayed — YouTube resets a waiting-room chat after a period of inactivity, and the resulting downloader stays non-nil, so the old `chatDl == nil` gate left the waiting room uncaptured for the rest of the wait. `finished` is recorded by the run goroutine's own `defer` (`runEarlyChat`, called as the `go` statement in `tryStartEarlyChat`) once `Start` has returned by any route, never from `ChatDownloader.OnFinish` — `Start`'s recovery defer returns before `OnFinish` is reached, so a run that PANICKED would never be restarted — and never from `IsRunning()`, which is also false between `NewChatDownloader` and the goroutine reaching `Start`. A `Stop` that lands in that same gap (`stopEarlyChat`) is not lost: with no run in flight `chat.ChatDownloader.Stop` latches `stopBeforeRun`, and the `Start` it reaches returns at once without its `OnStart`, so no chat_status "downloading" is written over the caller's settle. Each run's own state is one `chatRun` that `Start` replaces whole (`internal/chat/downloader.go`).

   The replaced downloader is untracked before the new one starts, and the new run picks up the chat file through the chat downloader's completion + adoption rules (platform-services.md) rather than overwriting it
3. Calculates probe interval based on time until scheduled start:
   - More than 1 hour away: 10-minute interval (`probeIntervalDistant`)
   - 5 minutes to 1 hour: 5-minute interval (`probeIntervalNear`)
   - Less than 5 minutes: 30-second interval (`probeIntervalImminent`)
   - No scheduled start time: the 30-second "imminent" interval, since the stream can go live at any moment
   - Plus random jitter up to 30 seconds
4. Polls via lightweight `ProbeVideoStatus()` (ANDROID_VR client for speed). A probe that cannot tell — ANDROID_VR's refusal said nothing about the broadcast and its one escalation settled nothing either (`*youtube.StatusProbeInconclusiveError`, [platform-services.md](platform-services.md) § The Status Probe's Blind Refusals) — is network-class to the loop: it keeps waiting and the error never counts toward its give-up. It is waited through, not out blind: the rest of the tick runs on a stand-in that says only "still waiting", so the periodic full fetch — the authority that gives up on a stream made private or removed, whose refusal is as blind as the bot wall's: on a verdict the keyword rules place, or on an ERROR refusal whose reason they cannot place and which states no broadcast (`fullFetchSaysRemoved`) — and the schedule probe, which can see the stream begin while ANDROID_VR cannot, keep their cadence; a probe that did not reach YouTube at all still skips its tick. Read as `not_a_stream`, it would end the job on the first poll through the switch's default arm.

   Persists metadata from each probe (title, thumbnail, description, etc.) using change detection — only writes to DB when values actually differ, at zero additional network cost since the probe already returns this data. The probe carries NO scheduled start: neither ANDROID_VR nor TV returns the `microformat` the schedule lives in (verified against live YouTube, 2026-10-14). A full multi-client fetch (`GetVideoInfo`) every 30 minutes (`fullFetchInterval`) refreshes everything the probe cannot see; on its own it would see a reschedule late — a start pushed back at the scheduled time, the usual reschedule, would stay stale past the new one.

   A separate **schedule probe** (`youtube.ProbeVideoSchedule`: one WEB-family player call carrying the jar's cookies, no watch page, no STS, no PO token — the `ProbeVideoDate` shape, read for `liveBroadcastDetails.startTimestamp`) runs while the probe still says upcoming, on a cadence that tapers with the time left to the start (`scheduleProbeInterval`): a twelfth of it, so an hour out is every 5 minutes and three hours out every 15, clamped between 2 minutes (`scheduleProbeMin`, which a start already past probes at) and 30 minutes (`scheduleProbeMax`, the full fetch's own interval — and since the full fetch resets the probe's clock, a start six hours or more away costs no call the full fetch was not already making: the loop asks the probe after the full fetch, so on the tick the fetch comes due a fetch that succeeds has reset it already, and one that fails leaves it due and the probe asks in its place. Asked first, as it was, the probe read the schedule on every full-fetch tick just before the fetch read it again). It writes the schedule alone through the same change detection, and only while its own answer still says upcoming — a stream that has just begun carries its actual start in the same field, which is the go-live path's to write.

   An answer that says the stream has begun (live, or already over — `scheduleProbeOvertakes`, an allow-list) stands in for the status probe's in the loop's switch: the WEB view can run ahead of ANDROID_VR, whose waiting-room slate can read as upcoming for a while after go-live, and the live and VOD arms confirm with a full fetch and keep polling when it disagrees, so a wrong answer costs one full fetch per probe (which the status probe itself can already cost every 30 s). Never any other answer: a refused WEB call reads `not_a_stream`, and the switch's default arm ends the job on that. The periodic full fetch's own answer is handed over the same way when it says the stream has begun: on its tick it takes the probe's place, so without that the hand-off would wait for the next probe. A probe that fails, or answers with no schedule (refused, or none set), changes nothing
5. Chat surge detection: if 30+ new messages arrive within a 15-second window, triggers an immediate probe (the stream may have gone live early)
6. Members-only detection: if the probe returns an auth-walled verdict (`PlayabilityMembersOnly`, `PlayabilityLoginRequired` or `PlayabilityAgeRestricted`), or an answer its signed-in TV escalation gave in ANDROID_VR's place (`VideoInfo.StatusProbeEscalation`), and auth cookies are available, switches to authenticated probing (`waitingRoomAuthFlip`). An answer that probe cannot read reaches neither the periodic full fetch nor the schedule probe, which run only on an upcoming one, so the switch's default arm does their work at its own cadence. A full fetch runs on the first answer of a spell of unclear ones (one the probe can read ends the spell), every `fullFetchInterval` after it, failed or not, and whenever the schedule probe says the stream has begun, which is the go-live confirmation. It gives up on a stream made private or removed exactly as the periodic full fetch does (`fullFetchSaysGone`), and otherwise writes what it learned to the row, since nothing else can. Every other poll makes one schedule probe, which is what sees a go-live on those polls: its error ends the poll unless a fetch is due, an upcoming answer updates the schedule, and only the full fetch may give up. A go-live that probe is refused too, which only the full fetch's other clients can read, waits for the next fetch due, up to `fullFetchInterval` late, and without DVR that much of the stream's start is lost. The arm used to make a full fetch on every poll, and a stream made private was fetched that way for 31 hours until its operator cancelled it
7. On transition to `StreamLive`: performs full multi-client fetch, updates metadata, sends notification, passes pre-started chat downloader to the orchestrator. `completeStreamTransition`'s write — Live, or `is_vod` alone for a stream the fetch finds already over — applies only to a row with no outcome (`UpdateJobFieldsUnlessTerminal`); a Cancel that landed after the loop's last check is not written over, and the run stops as a cancelled one, its early chat stopped with it. A write that failed on a row with no outcome does not stop it (`writeUnlessOutcome`). A confirming fetch that says the stream is private with no formats never gets this far, in any arm (`confirmationSaysPrivate`, the default arm's `fullFetchSaysGone`): neither Live nor `is_vod` is written, and it ends as the waiting loop's other full fetches end on a private verdict (`endGoneWait`), parked in `COOKIES?` when the cookies look dead and otherwise given up on. One with formats goes on to its download in the live and VOD arms.

   A confirmation YouTube refused for a rate limit with nothing to download (`rateLimitedFetch`, `internal/worker/rate_limit.go`), or with a 429 on the whole cascade, the limit's HTTP form (`noteFetchErr`, which does not read it as a blip and confirm again on the next probe), is no answer at all, and the broadcast stays in its loop (`loopRateLimit`): the early chat runs on, the status probe keeps polling, and the next confirmation is held off on a taper — made again 2, 5, 10 and 20 minutes after the spell's first refused confirmation, then every `rateLimitRetryInterval` (30 min) after the last (`rateLimitConfirmTaper`, `confirmationHoldAfter`; the owner's reading after FA, counted from the first refusal, not as gaps between refusals) — and made at the hold's end, the probe timer cut to it, under the wait's progress line, a 429's `Retry-After` the floor of each hold, capped at the hour, a confirmation it pushed past one instant of the taper waiting for the next one still ahead. The same holds the full fetch the switch's default arm makes while the cookied probe cannot read the stream (`probeAuthenticated`, once B1 has switched to it) when its schedule probe says on that poll that the stream has begun, and the schedule probe waits with it: left out, a refusal there that read live wrote Live and went on to a download with nothing to download. The arm's routine fetches, the first of a spell and each one due every `fullFetchInterval`, confirm nothing and are noted as the periodic fetch is (`noteFetch` with `confirmation` false): a refusal starts its spell and backlog hold but holds nothing off, so the schedule probe keeps running and the stream keeps waiting. While confirmations are being refused and the stream still reads begun, the schedule probe is asked before a fetch that is due (`confirmationsRefused`): past the taper a hold is as long as `fullFetchInterval`, so the fetch is always due on the poll that hold ends, and made as a routine one it was followed 30 s later by the confirmation, two cascades per half hour and past any `Retry-After`. If the probe says begun, that fetch is the confirmation. If it says otherwise or fails, the due fetch still goes out. A flat half hour lost a stream that had just gone live whatever it aired while a limit that lifted in minutes was waited out.

   A fetch that answers, the periodic one included, ends the spell and starts the taper over. The probe timer is cut only to a hold's end still ahead, so a failing probe, which leaves a hold that ran out standing, does not spin the loop, and a Cancel during a hold ends the loop on its next probe, the line cleared. A day of counted refused full fetches, at least three of them (`rateLimitCapRefusals`), ends the job in Error as `processJob`'s cap does, its waiting-room chat stopped (*A YouTube rate limit is not an error*); only a refusal that counted can end it (`outlasted`). A refusal counts once the stream has begun (owner decisions on FA and on a stream the cookied probe cannot read): every go-live confirmation's, and any other full fetch's, the periodic one's or the default arm's routine one's, only while the status probe's last conclusive answer — or the schedule probe's, when it overtook it or the status probe cannot read the stream — says live or over (`loopRateLimit.noteStatus`, `counts`); while it still says upcoming, or cannot tell after an upcoming, the broadcast keeps waiting however long those fetches are refused — a premiere days out under a captcha nobody solved does not end in Error before it aired. That holds after a go-live that did not hold (a test broadcast, a slate that flipped): the confirmations refused during it stay counted until a fetch is answered, but the refusals after it do not count, so none of them ends the job. A later go-live's refused confirmation does count, and is read against that standing count.

   Read as an answer, the refusal would either write Live and go on to a download with nothing to download, or — classified upcoming — be confirmed again with the whole cascade on every 30 s probe; and handed back to `processJob` instead, it would stop the waiting-room chat and leave the job half an hour with no probe. That refusal, and one the loop's periodic full fetch meets — its verdict or a 429 — holds the backlog as `processJob`'s do (`onRateLimited`)
8. If the scheduled start time changes — as the schedule probe or the full fetch sees it — sends a "Schedule Changed" notification (event: `rescheduled`), once per move: the comparison is by instant, so the watch page's `+00:00` spelling of a start the offline slate spelt `Z` is no move (`sameInstant`, `internal/worker/notify_facts.go`). Only for an answer that still says upcoming (`VideoInfo.NotYetLive`, `internal/youtube/types.go`, the gate the `scheduled` confirmation has): a stream that has begun, or is already over (post_live, VOD), carries its ACTUAL start in the same field, which the row takes and nothing announces — the periodic full fetch that finds a stream ended, or the go-live transition's write after it, must not send that start as a new time
9. Maximum 10 consecutive probe errors before giving up
10. A failed probe (and a failed periodic full fetch, `reportFetchOutcome`) gets two separate verdicts (`internal/worker/probe_classify.go`). `classifyProbeErr` decides whether it counts toward that give-up: a transport failure or a transient answer — a 429, a 401/403, a 5xx, a substitution — never does. `probeVote` decides what the connectivity monitor's passive tracker is told: only a failure to reach the service at all — a transport error in the chain, a request deadline, a connection cut mid-response, or their tokens in a flattened wrap — votes "down"; an HTTP status in the error's head, a Twitch GQL-level error and a YouTube substitution are answers from the service and vote "up"; anything else votes nothing. As one switch, every transient answer would be reported as the network being down, and a few waiting rooms answering 429 or 403 plus one unrelated transport blip would meet the passive threshold (5 failures, 2 tags, 30 s) and take the whole process offline with the internet reachable.

    The Twitch wait loop (`waitForTwitchLive`) feeds the oracle the same way. The monitor's own poll (`Monitor.poll`, `internal/connectivity/monitor.go`) ranks its active probe above the passive tracker: a probe that reaches its targets clears the passive latch and the failures behind it (`PassiveTracker.Clear`), so a passive verdict lasts until the next passing poll at most, rather than until its failures age out of the window however often the probe gets through. A real outage fails the probe too and leaves the latch alone

**Twitch path (`processTwitch()`):**
- VOD jobs (video ID prefix `tw_v`): fetches VOD info and HLS playlist, selects best variant, optionally creates VOD chat downloader
- Clip jobs (job ID `tw_clip_<slug>`, `jobfilter.IsClipJob` — the one clip predicate, which also drives type:clip and the [CLIP] tag; owner decision D26): routed before any login is read, to `processTwitchClip`, which reads the clip through `ShareClipRenderStatus` and picks its rendition by `twitch.SelectClipQuality` (the VOD rule under the job's `quality_preference`, `max_video_resolution` and `prefer_60fps`, the best rendition when nothing fits; owner decision FE-29); `ExecuteTwitchClip` downloads it as one whole file and finalizes it, with no chat ([platform-services.md](platform-services.md) § Twitch Clips)
- Live jobs: checks if channel is live via GQL. If offline and manually added, enters `waitForTwitchLive()` polling loop (15s interval + 5s jitter), whose first write (Upcoming, "Waiting for stream...") applies only to a row with no outcome, as `waitForLive()`'s does. Its poll is the not-found-aware `LookupStreamInfo` (through `twitchStreamLookup`), and `twitchNotFoundGiveUp` (10) "does not exist" answers in a row fail the job with an error that names the login, wrapped `ErrNonActionable` (G53): read as offline, GQL's `user:null` would leave a typo'd, renamed or deleted login waiting forever. Only answers count — any that resolves the login restarts the count, a failed poll leaves it as it was — and yt-dlp, which raises `<channel> does not exist` on the first, is given a few minutes' grace beside it because the wait can run for days. A not-found answer is Twitch answering: it resets the probe-error budget, is reported to the connectivity oracle as a success, and `probeVote`/`classifyProbeErr` (`internal/worker/probe_classify.go`) read `twitch.ErrChannelNotFound` by name ahead of their text rules, so a give-up whose login holds "eof", "tls" or "timeout" is not taken for a transport failure and parked as `twitch_unreachable`.

  If live, fetches HLS master playlist, selects best variant — the write that records it and sets Live (`startTwitchVariant`) applies only to a row with no outcome, and one refused for an outcome stops the run as a cancelled one (one that failed on a row with none does not, `writeUnlessOutcome`) — and constructs the IRC chat downloader (`chat_status = pending`); `ExecuteTwitch` starts it once the download begins

### DownloadOrchestrator

The `DownloadOrchestrator` manages the complete download lifecycle for a single job after the `StreamProcessor` has determined it should be downloaded.

**Entry point:** `ExecuteWithChat(ctx, jobCtx, videoInfo, isVod, existingChat) -> error`

**Sequence:**
1. Subscribe to database job updates for cancellation detection
2. Update status to `Downloading`, record `download_started_at` — on a row with no outcome only (`writeUnlessOutcome`, `internal/worker/stream_processor.go`). The run was decided on `processJob`'s read of the row, and an operator's Cancel writes the row before it cancels the run, so a Cancel that landed after the stream processor's go-live write, or after `processJob`'s last ctx check, is in the row and not yet in ctx. A refusal for the row's outcome (Cancelled, or the row gone) stops the pre-started chat and returns `ErrCancelled`, which `processJob` sends to `handleCancellation`: nothing is announced, staged or downloaded. The pre-check that stood ahead of the subscription read the row and stopped on Cancelled, and a Cancel that landed between that read and the write was still written over. A write that failed on a row with no outcome does not stop the run. `ExecuteTwitch`'s own `Downloading` write follows the same rule, after its listener
3. Send "Download Starting" notification
4. Create staging directory
5. Select download strategy (see below)
6. Set up progress tracking via `ProgressTracker`
7. Start chat downloader in parallel (or adopt pre-started one from `StreamProcessor`)
8. Execute download:
   - VOD: `runVodDownloadWithRefresh()` — wraps `runDownloaders()` (one-shot via `errgroup`) in a bounded re-extraction loop for YouTube jobs that finalize behind head (see below)
   - Live: `runLiveStreamDownload()` (loop with stream-end verification and quality monitoring); returns the final `*DownloadResult`, since a quality refresh/split reassigns the downloader pair inside the loop and the caller's original pointer would otherwise go stale
9. After download completes: finalize progress, sync total sequence counts. Both branches write `Muxing` here, ahead of the chat wait, so a restart inside that wait re-muxes from staging (`muxOnRestart`) instead of re-downloading a complete recording — the live branch at `streamEnded`, the VOD branch with its final progress write. Each write applies only to a row with no outcome (`writeUnlessOutcome`): an operator's Cancel whose row write landed before the run's listener heard it (a slower subscriber ahead of it holds the notification chain) was written over, and the finalize ran on. A refusal returns `ErrCancelled` with nothing muxed and staging kept
10. Signal chat to finish and wait for it. A live job waits `chatWaitTimeout` (2 minutes) — a live chat stops when the broadcast does. A VOD goes through `resolveVodChatOutcome` in `internal/worker/orchestrator_chat.go`, which releases the download slot FIRST and only then waits `vodChatWaitTimeout`: the video's own length, floored at 30 minutes and capped at 6 hours (owner decision O-A), because a VOD's comment pager is still paging long after the video finished downloading
11. Release download slot (muxing is CPU-bound, not a download) — already released, and therefore a no-op, for a VOD that came through the chat wait above
12. Mux and finalize (FFmpeg combines video + audio + metadata, ffprobe extracts dimensions/duration). Every stream copy of staged media — the archive's here, a part's (`muxSegment`) and a set-aside recording's sibling (`muxStagedAsides`), and so the boot re-mux and the Mux action, which reach this through `MuxJob` — goes through `copyStaged` (`internal/worker/mux_repair.go`), and its ENGINE-9 check runs on the copy under FFmpeg's temporary name (`verifiedCopy`). Each staged input is walked first (`engine.WalkFMP4`, `internal/engine/fmp4.go`): a fragmented MP4 — a live DASH `video_stream`/`audio_stream`, a Twitch fMP4 capture (the EXT-X-MAP init, then fragments carrying a video and an audio traf), a whole-file DASH download — has its boxes read without FFmpeg, every moof parsed and every mdat seeked over. A fragment that cannot be read — zeroed, torn, an HTML error body served with 200 — stops `-c copy` with exit 0, and a check that measured the INPUT with ffprobe's same mov demuxer would agree with the short copy; with two inputs, comparing format durations, which the intact track carries, would pass a video cut at a third (W30-A11).

    The walk resyncs on the next fragment that parses (an mfhd and a traf of a track the init declares, then an mdat), starting inside the box it last went past by its declared size when the damage sits right where that box claims to end — the previous fragment's mdat, or the moof (or a box leading it) of the fragment being read, whose trun table a cut leaves parsing on into the next fragment's bytes — so a torn fragment whose mdat or moof swallowed the start of the next one is dropped and the next one kept. A damaged input is muxed from a repaired copy written beside it in staging (`<file>.moombox-repair`, `engine.WriteFMP4Repair`: the stream without the unreadable bytes, its sidx/mfra renamed free; refused, staging kept, when the staging volume lacks its size plus 64 MB — an out-of-disk failure, which sends a backlog VOD back to `Queued` like any other (`repairNoSpaceError`); removed after the copy, and one a killed mux left is removed before the next repair of the file counts the free space, by the job's staging cleanup and by the boot sweep — `removeStaleRepairedCopies`) and the job finishes with a short gap where the damage was, logged at Warn with its time and byte range before the Finished write.

    The copy is then judged TRACK BY TRACK: each video and audio track's span — its first readable fragment's decode time to the end of its last, a repaired gap included — against the copy's stream of that type, on the tolerance (20 s) and floor (60 s) the check has always used, and a copy missing such a track is short (`verifyAgainstStaging`). A copy of two inputs — a DASH capture's `video_stream` and `audio_stream`, a restart's pair of asides, a whole-file download's pair — one of which loses its first fragment(s) to the repair is placed on the timeline the two share (`alignStagedInputs`): FFmpeg starts each input file at its own first timestamp, so the cut half's content from 2 s played at 0 s against the other's from 0 s, out of step for the whole archive, and the per-track check, measuring each track from its own first readable fragment, passed it. Each input is delayed (`engine.InputOffsets`, FFmpeg's `-itsoffset`) by how far after the earlier one its first readable fragment's decode time sits — ffprobe's start time for a half the walk cannot read; a half nothing can place refuses the copy, staging kept — so the archive keeps a gap at the start of the cut track instead, logged with its length, and the check wants each half's track to start in the copy where its offset put it, within 0.5 s (`verifyAlignedStarts`).

    A copy whose inputs kept their starts, and a copy of one input, are muxed without offsets. Inputs the walk has no business with — MPEG-TS (Twitch, YouTube HLS), WebM, a progressive MP4 — keep the probe-based check (`verifyMuxedDuration`: the longest input's span against the copy's format duration); so does a fragmented MP4 the walk cannot read, or whose decode times run backwards, which is never repaired and, since nothing independent of FFmpeg vouches for its copy, has its staging kept. A last fragment the end of the file cuts (a capture stopped mid-write) is a torn tail, not damage. Whatever keeps staging is recorded beside the input before FFmpeg runs (`<file>.mux-gaps.json`, `writeMuxGapRecord`) — the staging-cleanup shield of step 14. `muxAndFinalize` writes `Muxing` once, for both finalize shapes, ahead of everything it muxes and of its "Muxing Starting" announcement — and `muxFromStaging` makes the same write first, ahead of its own unrecorded-part recovery and of the announcement on its direct arm for a post-split job with no root media — on a row with no outcome only; a refusal returns `ErrCancelled` with nothing announced or muxed.

    Recovering the parts a mid-capture mux never recorded (`muxUnrecordedSegments`) before that write would let a refused finalize of split staging stream-copy them into the output directory and record their rows on the Cancelled or Finished row. `finalizeMultiSegmentJob` writes no status of its own before its Finished
13. Post-download trim if job has `StartTime`/`EndTime` set
14. Clean up staging directory (`cleanupStagingAfterMux`, on `decideStagingCleanup`'s shields, which the boot sweep applies too: a set-aside recording, an unmuxed part, an unused root recording, a recording a mux could not carry whole — a mux-gap record that holds, `stagedMuxGaps` — then an incomplete tail and an incomplete chat capture; each kept dir's Warn, which the job's own log carries, names the shield)

**Strategy selection logic** (`selectDownloadStrategy`, `internal/worker/strategies.go`; "split" is `HasManifestlessDashFormats`: a video-only and an audio-only format, both with a URL and no contentLength):
```
if isVod AND post_live AND split:
    DownloadManifestlessDash()  -- &sq=N from sq=0, even beside a manifest (a post-live one covers ~2 h)
elif isVod AND split among the formats carrying targetDurationSec AND no whole-file video-only + audio-only pair:
    DownloadManifestlessDash()  -- live adaptive formats, whatever the status says (a pool with a whole-file pair too is yt-dlp's was_live, and falls through)
elif isVod AND not_a_stream AND DASH manifest AND a segmented (OTF / live adaptive) format:
    DownloadDash()     -- yt-dlp's route for OTF: the manifest
elif isVod AND (not_a_stream OR no DASH manifest) AND formats exist:
    DownloadVod()      -- direct whole-file download, ~5MB chunked Range requests (each drawn from 95-100% of 5MB), segmented formats left out
elif not isVod AND split:
    DownloadManifestlessDash()  -- the primary live path
elif DASH manifest exists:
    DownloadDash()     -- sequential DASH segment download
elif HLS manifest exists:
    DownloadHls()      -- HLS playlist polling
elif formats exist:
    DownloadVod()      -- fallback: direct download
else:
    error: no download strategy available
```

The status this reads is the extraction's: a TV answer in the post-live DVR window (no microformat, `videoDetails.isPostLiveDvr`, live adaptive formats, no manifest) is `post_live` (see platform-services.md, Stream Status Classification), so a Resume of an `incomplete_tail` job in that window continues its capture on the manifest-free path instead of handing it to `DownloadVod`, which set the capture aside and fetched one fragment.

A setup that fails because the player's JS challenges cannot be solved at all — the cipher sidecar down or disabled, a player ejs cannot solve or none could fetch, an unsolved n, no player URL — is not the end of the job (`setupWithFallback`, `internal/worker/challenge_free.go`): a live capture on either DASH path records from the start on the formats that need no player JS (visionos's split live formats, one cookieless re-extract) and, only when those hold no pair, the live HLS playlist instead (from the oldest segment its window still holds), a post-live manifest-free one runs again on the formats that need no player JS, and `DownloadVod` drops to those itself; a live capture whose mid-stream refresh fails the same way switches path in a new part — the no-JS path, else HLS, each at most once a run, the one it is on given back by the run's one switch back to the from-start path once the challenges can be solved again (owner decision PE-3) — its current part kept and muxed as its own file (`switchLivePath`; platform-services.md § The Challenge-Free Fallback). A live from-start setup left with no GVS token to record with (`errMissingPot`) takes the same site to its HLS playlist (`missingPotFallback`), so both causes set an earlier capture of the other shape in the part aside first, and a VOD that meets both degrades selects a copy that needs neither, over one cookieless re-extract (platform-services.md § Which URLs carry a GVS token).

A live capture on either DASH path of a broadcast live longer than YouTube keeps segments — 118 h, two short of yt-dlp's `MAX_DURATION` (432000 s), read from the row's `stream_start_time`, which for a live stream is `liveBroadcastDetails.startTimestamp` — never tries from the start: its sq 0, and with it a manifest-free capture's only init, is gone. `setupWithFallback` runs the live HLS setup first (`marathonLiveEdge`, `setupMarathonOr`, `internal/worker/marathon_live_edge.go`; owner decision 10), with the Warn `[Live] the stream has been live longer than YouTube keeps its segments (~120 h) — recording from the start cannot run; recording the live HLS playlist instead, from the live edge` (`jobID`, `strategy`, `liveFor`, `streamStartTime`), as yt-dlp records a live stream by default. A part that already holds a DASH capture (a restart resumed into it, appending from the position it reached) carries on in place, and an HLS setup that fails leaves the from-start setup and its fallbacks to run. Post-live runs are untouched: there is no live HLS to fall to, and starting at the oldest kept segment is the gated Phase D.

**Live stream download loop (`runLiveStreamDownload`):**
1. Starts quality monitor (30-second probe interval) if user hasn't manually selected itags. Every tick starts with one cheap player call (`probeVideoInfo`, `internal/worker/orchestrator_youtube.go`): `ProbeVideoStatus` (ANDROID_VR, cookieless, no POT, no watch page) for public streams, and `ProbeVideoStatusAuthenticated` (TV_SAMSUNG with cookies, no watch page, no STS, no POT) for members-only / age-restricted / login-required ones, where the cookieless probe would 401. When the cookieless probe comes back with nothing selectable and the install has cookies, one TV-with-cookies call is tried next — O-H's "recovery streams" half, gated on `HasAuthCookies` because a cookieless TV call is bot-walled. (A cookieless refusal that says nothing about the broadcast has already been escalated to that same call inside `ProbeVideoStatus` on a signed-in install, so after a TV escalation, answered or not, the hop is not asked again — `tvEscalationAsked`.) Only if nothing cheaper produced a `DashManifestURL` or a split-adaptive format pool does the tick fall back, ONCE, to the full `GetVideoInfo` cascade — including when a probe errored, so one 403 never ends a tick that the cascade's three-to-seven clients could still answer.

   TWO errors buy nothing there and end the tick where they were seen: a cancelled context, and a substituted video (`*youtube.VideoIDMismatchError`) — a substitution is IP-level, so every client is substituted alike and the cascade would only re-ask a blocking server seven more times, nine player calls per 30 s tick for as long as the block lasts. Before owner decision O-H that cascade was the FIRST call on the auth-walled branch and ran on EVERY tick: a 1-5 MB cookied watch page plus three to seven player calls, ~120 pages/hour/job.
2. Runs segment downloaders in a goroutine
3. Simultaneously listens for quality change signals on `qualityChangeCh`
4. When quality changes mid-stream:
   - Ignores if segment is shorter than 10 seconds (`minSegmentDuration`)
   - A split that cannot wait (the stream lost the quality, a still-live stall refresh came back at another one) closes a span shorter than that without making it a part: the span's media is set aside (`setAsideShortSpan`, `internal/worker/staging_shapes.go`; the `.restart-<ts>` convention), muxed into its own file beside the archive at finalize and recoverable by `A S`, and the next part reuses its index and dir. It was deleted until owner decision PR-R9: "short" is wall-clock time, and a from-start capture catching up through a backlog can gather far more than ten seconds in it. A set-aside that fails closes the span as a regular part. Twitch's quality split does the same (`advanceToNewPart`).
   - A refresh that comes back at the download's own quality (and itags) continues in place; the monitor is re-baselined to the download's quality so an early refresh is retried on the next signal — until the SAME probed quality has been answered "unchanged" three times running (`sameQualityStrikeLimit`), when the probe and the download disagree for good (an HLS download beside the probe's DASH ladder) and the monitor takes the probe's reading as its baseline instead (`ReconcileSameQuality`, `internal/worker/quality_monitor.go`); before that bound, such a job cancelled and rebuilt its downloaders every 30 s for the rest of the broadcast
   - Cancels current downloaders
   - Muxes the current segment in a background goroutine parented by the orchestrator's mux root (`launchBackgroundSegmentMux` in `internal/worker/quality_split_common.go`), not `context.Background()`
   - Records segment metadata in database
   - Re-fetches video info with new format selection
   - Creates new downloaders at the new quality
   - Continues download loop
5. When download ends naturally (stream ended, quality lost, or error):
   - Verifies stream has actually ended via YouTube API (up to 6 checks, 5-minute intervals). A look that fails (a bot wall, a 429, a 5xx) is not a verdict: it spends the same 6-check budget, and the capture is only given up once that budget is spent and no segment has arrived for `streamSegmentTimeout` (`unreadableStatusEndsCapture`) — before, one failed look after the engine's `maximum_timeout` finalize ended the job, since both default to ten minutes
   - If stream is still live, re-fetches formats and restarts download. The refresh is judged before it is adopted: a stream that comes back from the stall at a different quality (an encoder restart) — or at the same size in a different rendition, a video or audio itag the DASH strategies record (`VideoItag`/`AudioItag`, compared by `streamIdentityChanged` in `internal/worker/orchestrator.go`, which the VOD refresh guard `refreshFormatMatches` applies too) — takes the same split step 4 does (`splitPart`, `internal/worker/orchestrator_youtube.go`), because the refreshed downloaders continue the current part — through its sidecar, or from the stopped downloaders' position, which the still-live refresh forces so a sidecar the engine already cleared cannot leave it to a stale DB seq — and would otherwise append the new rendition under the old init segment
   - Before that refresh, a capture still live whose downloaders wrote nothing from a start the CDN has evicted — `diagnoseEvictedStart` confirms it: zero bytes, a head past the eviction floor, the bisection's oldest served segment above sq 0 — records the live HLS playlist into its part at once — a start at or near sq 0 only, inside the first-segment hunt's window; a resume seeded at a deeper evicted position is not diagnosed and still ends with zero bytes — (`evictedStartToLiveEdge`, `internal/worker/marathon_live_edge.go`), its empty DASH files set aside, with the Warn `[Live] the capture's start is gone from YouTube's ~120 h window — recording from the start cannot run; recording the live HLS playlist instead, from the live edge` (`err` the diagnosis). Without the switch it would spend the six still-live checks re-seeding each refreshed downloader at the same evicted position and end with zero bytes, the retention error never raised. Anything short of a confirmed eviction, or an HLS setup that fails, leaves the checks to run.
   - `ErrQualityLost` triggers format re-fetch and restart at available quality. A refresh there — or the one a quality split makes for its new part — that fails while YouTube still reports the stream live is retried (`refreshWhileLive`, `internal/worker/orchestrator_youtube.go`) on the verify cadence and within its 6-check budget, re-reading the stream status before each attempt, rather than ending the recording on one transient manifest or cipher fetch; only a stream no longer reported live or a spent budget ends it
   - Same-seq rebuild cap (`sameSeqRebuildCap`, 3, `internal/worker/refused_segment.go`; owner decision D8, G15): each `ErrQualityLost` rebuild is counted per stream at the sequence its downloader stopped at (`sameSeqRebuilds`; per stream, because the sibling of a stuck stream keeps moving), and a stream that moved starts its count again. Only a stall the refused-segment rule could take is counted: a DASH stream stopped more than two below its tracked head (`StoppedWellBehindHead`), and whose rule did not decline the hole. A decline (`WholeStreamRefused`: the rule's probe past the hole was not served, or the head SERVED segments report stands within two of it) is a refusal of the whole stream — a GVS, PO-token or bot-detection outage — or a stall at the edge the stream has served, which refusals' `X-Head-Seqnum` and the head probes make read as well behind the tracked head; the rebuild after it ends the count instead (owner decision PR-M2), so a capture YouTube still calls live is rebuilt for as long as it is live, and the rule probes again every third rebuild.

     Counted, the fourth rebuild of such an outage would pass the cap and the stream-end verify would finalize the capture after six still-live checks, about 35 minutes in. An HLS result and a stall at the live edge — a broadcast interrupted while YouTube still calls it live — reset the count and are rebuilt without limit, since the verify branch's 6-check budget would end such a capture in half an hour. Before, a segment YouTube refused for good drove a `GetVideoInfo`, a mint, a cipher re-resolve and a rebuild at the same sequence every ten to twenty seconds for the rest of the broadcast. The rebuild that reaches the cap arms its downloaders (`NoteRebuildsExhausted`, with the time of the run's first rebuild), which apply the engine's refused-segment rule (below) where they would hand the sequence back again; one the rule cannot take yet comes back once more, and past the cap the loop does not rebuild but falls through to the stream-end verification of step 5
   - `engine.ErrSegmentRefused` — a segment refused through fresh credentials while a later one is served and the head that served segment reports is more than two past it — closes the current part at the hole, whatever quality the look-refresh came back at: the streams stopped at the hole start the next part one past it (`pastRefusedSegment`; a sibling stopped on the same sequence steps over it too, a sibling elsewhere keeps its position, as a quality split keeps it), each stream that steps over it gets a gap row (`noteRefusedHole`), and `splitPart` muxes the closed part (never discarded as short) without a quality-split notification. Every DASH downloader the live loop attaches carries `SplitOnRefusedSegment`.
6. Stream-end verification prevents premature termination from transient network issues. It is not entered for a failure to write the staged recording (`engine.ErrLocalWrite` — opening the output file or appending a segment: a full disk, a permission, a vanished staging dir): the live loop stops with that error, so the job lands in Error with staging and the resume sidecar kept, instead of re-verifying a stream it cannot write for up to an hour and then finishing as if it had ended

**VOD-branch bounded refresh loop (`runVodDownloadWithRefresh`):** googlevideo URLs live ~6h; a post-live download whose wall clock outlives that grant finalizes with `FinalizedBehindHead()` true on the video and/or audio downloader instead of erroring outright. The live branch recovers from URL expiry via `ErrQualityLost` -> `refreshDownload`, and so does the VOD branch, which does not run `runDownloaders()` just once. It re-extracts via `GetVideoInfo`, seeds `VideoStartSeq`/`AudioStartSeq` from the last written sequence, and rebuilds through the same `refreshDownload` — provided the prior attempt actually made progress and the fresh extraction still offers manifestless DASH formats (a stream that finished processing into a true VOD is left to the incomplete-tail flag + manual retry instead). "Finished processing" is any client's: once the fresh extraction's verdict is not post-live, its dedup lets a live adaptive copy of a stream lose to any client's whole file of it (see platform-services.md, The Whole-File VOD Path), so a refresh in that window stops the loop, and a credential refresh mid-download keeps its current URL (`formatBecameWholeFile`), so tv's `&sq` copy does not win on its AuthLevel and keep the tail refreshing. That is upstream's `was_live`, which downloads the files; a Resume of the `incomplete_tail` job then takes them whole.

Bounded by `maxVodRefreshAttempts` (4, ~24h of wall clock); past that, or on no progress, the loop stops and returns whatever was captured.

**Eviction diagnosis (`diagnoseEvictedStart`):** both branches run this check after a nil download error. If a YouTube manifestless download finished having written zero bytes and its `HeadSeq()` is implausibly deep (past `evictionHeadFloor`: ~28h of segments in the selected format's own `targetDurationSec`, `minEvictionHead` = 100,000 at 1 s and kept when no format advertises a duration — 20,000 for a 5 s stream, as yt-dlp converts its 120 h window with `MAX_DURATION // fragment_duration`), an ordinary failed start is an unlikely explanation — YouTube's ~120h retention window may have scrolled segment 0 out from under a marathon stream. The check bisects `[0, head]` for the oldest segment the CDN still serves (`engine.FindOldestAvailableSeq`), fetches that boundary segment, and inspects its box structure (`engine.InspectSegment`) to log a full diagnosis. A confirmed eviction (oldest available segment > 0) fails the job with a precise "exceeds YouTube's retention window" error instead of the generic empty-download failure; a dead-URL bisection or an oldest of 0 leaves the ordinary failure path to run unchanged. Diagnosis only — no download jump; that is gated future work (docs/plans/2026-08-05-incomplete-tail-and-marathon-streams.md Phase D).

**Interruption resume — finalize deferral (`stallForPossibleResume`, `internal/engine/downloader.go`):** a live YouTube `SegmentDownloader`'s `MayResume` callback, when installed, gates both of the DASH loop's MaxTimeout-backstop finalizes — `handleGoneError`'s gone-burst verification path and `handleHTTPError`'s no-segment maximum-timeout backstop (both `internal/engine/downloader_dash.go`) — but never a confirmed-ended verdict (`streamEndVerified` always finalizes immediately, MayResume unconsulted). The first `MayResume()==true` observation for a stall latches a per-episode clock (`interruptionStallStart`); `downloader.interruption_timeout` (config minutes, default 120 — see the config table in data-and-storage.md) bounds how long deferral continues, retrying every `interruptionStallRetryDelay` (5s). When `MayResume` flips false or the ceiling expires, `finalizedDuringInterruption` latches and the finalize proceeds recording `finishInterrupted`, a reason that does not clear the sidecar (`finishReason.clearsSidecar`) — mirroring the existing behind-head-tail contract — so the resume sidecar (`.resume.json`) survives for a later in-place continuation instead of being cleared.

**Run outcome and the resume sidecar (`finishReason`, `internal/engine/downloader_finish.go`):** every clean exit of `runDashLoop` and `runHlsLoop` records one unexported `finishReason`, and the loop's exit defer clears the resume sidecar only when it is a confirmed, complete end (`finishConfirmed` — DASH's gone path, every HLS confirmed end — or the HLS media-sequence restart). Every other exit keeps it: behind-head, Tier-2 interruption, the MaxTimeout backstop, an exhausted first-segment hunt (nothing written, so no sidecar), `EndSeq`, and an error or cancel (no reason). The DASH end that `handleHTTPError`'s status check confirms (`finishConfirmedViaHTTP`) also KEEPS it, unlike the gone path — owner ruling R-G1: staging is wiped after a successful finish anyway. `TestRunExitSidecarOutcome` pins each exit. The DASH handlers' answers (nil retry, `errSegmentSkipped`, `errStreamDone`, any other error) are mapped onto the loop by one `dispatch`, matched with `errors.Is`. The worker-visible latches `FinalizedBehindHead` and `FinalizedDuringInterruption` are unchanged and separate.

`InterruptionTimeout == InterruptionNoStall` (a `-1` sentinel, distinct from the ordinary `0` = "no ceiling"/unbounded meaning) is a third mode: consult `MayResume` exactly once, latch `finalizedDuringInterruption` when it's true, and always return `false` — finalize proceeds on that same call, with no stall and no clock. The worker maps its own `interruption_timeout=0` ("stall disabled" per the config contract) onto this sentinel (`engineInterruptionTimeout`, `internal/worker/interruption.go`) rather than passing `0` straight through, so a disabled-stall job still latches Tier 2 evidence without ever blocking finalize. This Tier 1 engine-level stall is DASH-only — the HLS live strategy (`runHlsLoop`) has no `stallForPossibleResume` call site at all, so an HLS live YouTube download gets only the worker-level Tier 2/3 preservation described below, not this deferral.

**Interruption resume — auto-resume valve (`shouldWaitForResume`, `resumeOnRedetect`):** on the worker side, an `interruptionSignal` (`internal/worker/interruption.go`) tracks the last time a player-response fetch showed the broadcast-interrupted signature (StreamStatus live with zero formats), observed at `refreshGvsCredentials`'s re-fetch, the live loop's own post-exit refetches (`orchestrator_youtube.go`), and each YouTube strategy's `CheckStreamStatus` closure via `observeYouTubeStatusProbe` — the only site that fires while the engine is still internally stalling. `buildMayResume` reports resume-plausible when that signal is fresh (90s) OR the job's chat downloader still has its live continuation open.

`runLiveStreamDownload` feeds that evidence into `noteRefreshFailure`, which splits it into two independent questions: `resumeEvidence` (does the evidence hold at all) always latches the finalize-scoped `resumeWaitLatch` when it does, while `shouldWaitForResume` (evidence AND `interruptionTimeout > 0`) is the PERMISSION gate deciding whether the loop actually waits instead of finalizing immediately — for up to `interruption_timeout`, one episode (`waitDeadline`) shared by the quality-loss branch, which waits once, and the stream-end verify branch the cancelled downloaders bring every later look to, which asks the same episode and refunds the live check it spent while the wait goes on (a look whose status fetch fails is a wait tick there too, not a spent check), its still-live sleep labelled `ActivityWaitingResume` rather than `ActivityVerifyingEnd`. `maxConsecutiveLiveChecks` (6) bounds only that branch's retries outside a wait; it does not end a wait after about half an hour, whatever `interruption_timeout` says. So a `interruption_timeout=0` job never actually waits, but a genuinely-interrupted one still latches `resumeWaitLatch`, which ORs into `incomplete_tail` (`finalizeIncompleteTail`) even on a run where the engine itself never latched `FinalizedDuringInterruption`.

If the ceiling (when enabled) is still reached, the job finalizes Finished with staging preserved; a later live re-detection of that same video ID reopens the valve from outside the download loop entirely — `resumeOnRedetect` (`cmd/moombox/monitor_callbacks.go`) calls `DownloadWorker.ResumeJob` when the re-detected job is Finished with `incomplete_tail` set and its staging files still exist on disk, coalesced to at most one auto-resume attempt per 5 minutes per job and never for a job a human Cancelled.

**Interruption resume — part merge (`mergeSameFormatParts`, `internal/worker/part_merge.go`):** `finalizeMultiSegmentJob` runs `mergeSameFormatParts` (Tier 4) before deciding the finalize shape — including the single-part-takes-the-plain-name rename — so a job whose parts all losslessly recombine ends up named exactly like a never-split job. It probes each part via ffprobe, groups contiguous runs of identical stream parameters, and concat-copies each run (`Muxer.ConcatCopy`, whose list names every part by its absolute path: FFmpeg's concat demuxer resolves a relative entry against the list file's own temp directory, not the working directory, so under the default relative `./output` — whose part rows are relative to the working directory — every merge would fail); any probe, concat, or db-replace failure leaves that run's segments untouched, since the merge is opportunistic and never a finalize gate. A chat-merge failure aborts that run specifically — video included, not just chat — leaving its parts/rows/chat files exactly as they were while other runs in the same finalize still merge.

No production run reaches the chat merge today: `finalizeMultiSegmentJob` merges YouTube jobs only (Twitch parts never merge), and only Twitch live IRC chat rolls per part, so no merged run carries a `ChatFile`; the rule stands so a future per-part chat cannot be dropped by a merge. A successful run commits every segment row — merged and untouched alike — in one `database.ReplaceJobSegments` call, then best-effort renames the merged output onto the run's first part's original name and removes the superseded later parts' output/chat files and their pre-mux `seg_N` staging directories. Those directories are tombstoned (`mergeTombstoneFile`) BEFORE the commit and the tombstones taken back if it fails, so a crash between the commit and the removal cannot leave row-less media that the next finalize re-muxes as a new part and merges a second time; a tombstone on a still-recorded part's dir changes nothing. A superseded dir that still holds a set-aside recording is kept rather than removed — an aside is never merged content — and the aside scan (`stagedAsideRecordings`) looks inside tombstoned dirs, so the finalize's recovery and every staging shield still see it.

**A split job that comes back as a VOD (`claimStagingRootForVod`, `supersedePartsWithVod`, `internal/worker/vod_supersede.go`):** a live capture that quality-split, was interrupted, and is restarted after the broadcast ended is re-classified VOD, and a VOD run records from the start into the staging ROOT — restart part-discovery is live-only. The root is part 0 unless `seg_0` exists, so the multi-segment finalize ignored the complete download once part 0 was recorded, finished the job as the partial live parts, and the staging cleanup deleted it. Now the run claims the root first: part 0's live capture (and sidecar) moves into `seg_0`, created even when empty because it is what stops every later finalize reading the root as part 0 (a root span the split skipped as too short, when `seg_0` already exists, is set aside by the `.restart-` convention instead), and a `vodRootMarkerFile` in the root records the run's state — `downloading`, then `complete` once the download ends with nothing missing (`markVodRootComplete`, called by `settleVodDownload` from the same verdict that sets `incomplete_tail`, and written before the `Muxing` status so a restart mux sees it too).

A `complete` root makes the finalize supersede the parts after `muxUnrecordedSegments` has recorded any still unmuxed: each part's file and per-part chat move beside the archive as `<stem>.restart-<part start>.mp4` siblings (`asideOutputPath`), which the output sweep folds under the archive's stem rather than offering as strays, every recorded part's `seg_N` dir is tombstoned (`mergeTombstoneFile`) — `seg_0` included, which still keeps the root from reading as part 0, because that rule (`rootIsPartZero`, `internal/worker/orchestrator_mux.go`, consulted by `muxUnrecordedSegments` and `hasUnmuxedSegmentParts`) asks whether the dir exists, not whether it is a live part: read through the tombstone-skipping part list, a part dir left with no row (an empty `seg_N` from an interrupted split, or one whose media FFmpeg cannot read) made the complete download an unmuxed part 0 again, kept staging for it and let each Mux write the whole VOD out as one more full-length sibling — and `ClearJobSegmentsAndGaps` drops the rows — then the single-file path muxes the download as the archive.

Nothing is deleted, because a live part is not guaranteed to be inside the VOD (YouTube trims very long archives, and a creator can edit one). It runs before the archive mux, since a part an earlier finalize renamed to the plain name sits exactly where the archive is about to be written, and it is re-entrant: a part whose file already moved is skipped. A download that ended incomplete leaves the parts as the archive and Resume comes back for the tail. Whatever root recording a finalize did not use, `cleanupStagingAfterMux` keeps the staging dir for (`unusedRootRecording`, `internal/worker/vod_supersede.go`), naming it in its Warn: beside a job that finalized as parts, a claimed root or the whole-file `video.mp4`/`audio.m4a` pair no part is ever made from; beside a single-file finalize, a whole-file download (`video.mp4` or `audio.m4a`) sharing the root with any live-shape capture (`video_stream`, `audio_stream` or `video.ts` — an audio-only job's stale `audio_stream` outranks its complete `audio.m4a` in discovery just as `video_stream` outranks `video.mp4`) — the layout `setAsideLiveShapesForVod` prevents, which an older staging dir can still hold. The orphan sweep's `jobNeedsStaging` (`internal/worker/orphans.go`) applies the same shield, with no age rule, so the Files tab never offers that dir for deletion either.

### SegmentDownloader

The `SegmentDownloader` in `internal/engine/downloader.go` handles the actual byte-level downloading. It supports four modes:

**DASH sequential mode (`runDashLoop`):**
- Downloads video/audio segments sequentially by sequence number
- Never reads a DRM-protected Representation: `ParseDash` (`internal/engine/manifest.go`) leaves out one that carries `ContentProtection`, or whose `AdaptationSet` does (`isDRMProtected` — yt-dlp's `is_drm_protected` sets `has_drm` either way, `extractor/common.py`, and the format is dropped), and a manifest with nothing else left is `ErrDRMProtected` in the format list's "DRM-protected" wording. `ParseDashDRM` also says which kind the skip emptied (`DashDRM`): a manifest whose every video (or audio) Representation is protected beside clear streams of the other kind parses, and `DownloadDash` fails with `ErrDRMProtected` when the kind the job needs is the lost one (an `audio_only` job beside a protected video set records its audio). Owner decision FE-1: that setup falls to the extraction's HLS manifest when it lists one (`drmHlsFallback`, `internal/worker/drm_fallback.go`, from `setupOrFallback`), as yt-dlp drops the `has_drm` formats and takes whatever playable format remains (`YoutubeDL.py`); with no HLS manifest, or an HLS playlist the engine refuses as encrypted too (below — at setup, mid-stream in the live loop, which stops on it rather than verify a stream end, and in the VOD branch), the job's error leads with "DRM-protected; Moombox cannot record it" (`errDRMUnrecordable`).

  An HLS fallback that fails for any other reason reports both causes without that claim. It took every Representation, so a protected manifest — the tv-client DRM experiment's, should YouTube mark it (yt-dlp #12563) — would have been recorded as ciphertext.
- Constructs segment URLs by appending `&sq={seq}` to the base URL
- Detects stream end via HTTP 404 with retry backoff
- Performs HEAD probes every 5 seconds to discover the head sequence number
- Saves resume state every 50 segments (`ResumeSeqInterval`)
- An empty 2xx body is a failed fetch of that sequence, never a segment: the sequential loop routes it through `handleHTTPError` (below the head the transient retry, at or past it the at-edge backoff, head re-probe, `CheckStreamStatus` and `MaxTimeout` backstop), and `fetchSegmentWithRetry` — catch-up, and the HLS VOD and init fetches — retries it like a 5xx. Written as a segment it advanced `currentSeq` and refreshed the no-segment clock, so an edge answering empty 200s past the end of a stream (moonarchive's `_dash.py` meets them when the replay goes unlisted at the end) kept the loop running at request speed forever, and inside catch-up it was flushed as nothing with no gap recorded. yt-dlp's HttpFD fails such a fetch too ("Did not get any data blocks", `downloader/http.py`).
- Refused segment (`refuseSegment`, `internal/engine/downloader_dash.go`; 2026-10-31 audit G15, owner decision D8): once data is in the file, a 403 on the sequence that failed before a credential refresh was installed (`credentialRenewals` moved on since its first failure) — or, for a downloader the live loop armed with `NoteRebuildsExhausted`, the point where it would hand that sequence back as `ErrQualityLost` again (`handBackForRebuild`: a 403 or a 410 at once, a 5xx or an empty body only once it has kept failing for `unservedSegmentPersistence`, ten minutes, since the run of rebuilds began — a server error is not a refusal, and the cap's three rebuilds take about two minutes) — is considered when `SplitOnRefusedSegment` is set, the sequence is not sq=0 and the tracked head is more than two past it (`refusable`). Before it gives anything up it probes the segment just below that head (`laterSegmentServed`): only when it is served, and the head that served response reports (`servedHeadSeq`, the X-Head-Seqnum of 2xx answers alone) is more than two past the hole, is the segment given up — moonarchive's `max_seq - 2 > cur_seq`, whose `max_seq` is only ever a served fragment's header.

  The probe goes beyond moonarchive, which skips on its bound alone: a refusal of every segment (a PO token or an address YouTube stopped accepting) is not one segment's, and the capture holds at the hole (`errNotRefused`) instead of dropping a segment per refresh. This is moonarchive's rule (`_dash.py`: "It's very rare, but there are instances when YouTube repeatedly responds with a 403 on a fragment that should be valid … Skip it") and yt-dlp's `skip_unavailable_fragments` (`downloader/fragment.py`; `downloader/dash.py` makes only fragment 0 fatal). Moombox goes beyond both in what it does with the hole: the download stops AT it with a `*SegmentRefusedError` for the live loop's split, so every part stays gapless. It skips in place — `OnGap` row, `currentSeq` past the hole, the file going on with each fragment's own tfdt — only when a new part could not open: the stream keeps its init only inline in sq=0 and sq=0 answers 410 (`newPartInitEvicted`, a probe of sq=0; a 403, a 5xx or a transport error is not eviction, and the split stands), or the file holds its init and no media yet (`holdsNoMedia`, read from the file's top-level boxes, so a part the live loop rebuilt in place is known too), where closing it would open one init-only part per refused sequence.

  After a skip the next sequence starts with fresh retry state and counts as already asked on fresh credentials (`afterSkip`, moonarchive's `last_seq_auth_expiry = cur_seq`), so a run of refused sequences is walked in one pass. FFmpeg's copy of such a file keeps the hole on the timeline. Without `SplitOnRefusedSegment` (post-live and VOD downloads) nothing changes.
- First-segment hunt (`handleGoneError`, before any byte is written): a 403/410 may step `currentSeq` past the refused sequence only below a known head, and never off sq=0 of a manifest-free start (`huntMayAdvance`, `internal/engine/downloader_dash.go`); anywhere else the same sequence is asked again, `singleGoneRetryDelay` apart, within the same `goneRetryBeforeFirstSegment` budget. A sq=0 held below a known head is a segment that exists, so a 403 there that outlives the cipher swap — `postBytes403CipherThreshold` (5) in a row, the same gate as the post-bytes refresh — is stale credentials, and the hold calls `refreshCredentials` (never for a 410, never at or past the head) rather than re-send the refused PO token for its whole budget and end with nothing written. yt-dlp never requests a sequence before `X-Head-Seqnum` says it exists (`_live_adaptive_fragments`, `8c1f07d81`, #16771, keeping the bound `adbc4ec4b`, #888, gave the manifest generator) and makes a DASH download's fragment 0 fatal (`is_fatal=lambda idx: idx == 0`, `814bba393`, #5274).

  The manifest-free strategy sets `InitInlineAtStart` on every start it does not force, because sq=0 holds that stream's only ftyp+moov: stepping past it — even after `OnCipherFailure` had repaired the refused URL — began the recording at sq=1 with no init, hours FFmpeg rejects with "moov atom not found". `ensureInlineInit` (`internal/engine/downloader_init.go`) backs the rule on the sequential write and catch-up's flush alike: an empty `InitInlineAtStart` file never takes media for a later sequence before sq=0's init, fetched from the current base, or the start fails with `ErrInitSegmentUnavailable`.
- Init segment (`downloadInitSegment`, `internal/engine/downloader.go`): a manifest `Initialization`, or the sq=0 a manifest-free part that force-starts past it (a quality split, restart discovery, the post-live refresh rebuild) takes its ftyp+moov from (`InitFromSegment`), is fetched through `fetchInitSegment` — `fetchSegmentWithRetry`'s ladder, plus `initForbiddenAttempts` (3) tries on a 403, each after `refreshCredentials` (the cooldown waited out, so each is a real refresh) and on the sq=0 URL rebuilt from the base that refresh installed; a 410 is evicted (`errSegmentGone`) and fails at once, never refreshed — and its failure is fatal: `Start` returns `ErrInitSegmentUnavailable` before any media. A live capture's re-verify then builds the part again from the same forced sequence; a post-live (VOD-branch) download fails the job with that error, rather than at mux time with "moov atom not found" after downloading everything. As one request whose failure was only logged, the part would record for hours into a file that could not be muxed, its empty start re-arming the first-segment hunt at the split sequence. A `Cancel()` while the init waits for its retry is returned as the bare cancellation, with no refresh spent on a retry that will never be sent.
- Catch-up mode (`runParallelCatchUp`): once `stayBehindSegments`+`CatchupThreshold` (40) segments behind the live head, hands off to a rolling window of `segment_workers` parallel fetches (default 12, configurable via `downloader.segment_workers`, no upper limit — see the config table in data-and-storage.md) instead of `ParallelDownloads`' historical fixed 6. Workers claim sequences continuously and flush completed segments in strict ascending order as they arrive — there is no per-batch barrier. See "Catch-up: rolling window and byte-bounded buffer" below for the buffer and damping mechanics.

**HLS live mode (`runHlsLoop`):**
- Polls the HLS playlist URL periodically
- Refuses an encrypted media playlist on the round that fetched it, before any segment or init is fetched or a byte written — and so before the VOD hand-off below: the first `#EXT-X-KEY` or `#EXT-X-SESSION-KEY` whose `METHOD` is not `NONE`, or an `#EXT-X-FAXS-CM` tag, is recorded by the parser (`HlsPlaylist.Encryption`, `parseHlsKey` in `internal/engine/manifest.go`), and the loop returns `ErrDRMProtected`, worded "DRM-protected" for the DRM systems yt-dlp's `HlsFD._has_drm` names (FairPlay by an `skd://` URI or its `KEYFORMAT`, PlayReady, Flash Access) and "encrypted" otherwise (`hlsEncryptionError`). The engine writes segments as fetched and decrypts none, so segments under a key were archived as ciphertext that failed only at mux time. yt-dlp decrypts AES-128 natively and hands other methods to ffmpeg (`downloader/hls.py`); neither Twitch nor YouTube encrypts HLS today, so a clear refusal — which fails the strategy and ends the job on that error — is the whole port (audit G32).
- Downloads new segments as they appear
- Skips a Twitch stitched-ad segment without fetching or writing it, advancing the position past it so the sliding window never reads as a gap. A segment is an ad (`HlsSegment.IsAd`, `parseMediaPlaylist` in `internal/engine/manifest.go`) by streamlink's two signals (`_is_segment_ad`, `plugins/twitch.py` a685512): its `#EXTINF` title contains `Amazon`, or its program date-time falls inside a bounded stitched-ad `#EXT-X-DATERANGE` (`collectAdDateRanges`). The title is read per segment — reset at each segment line, so it never carries onto a later segment without an EXTINF — and catches a break whose range this playlist does not bound, which would otherwise be recorded into the archive (and, in fMP4, split the part twice on the ad's own `EXT-X-MAP`). YouTube HLS sends empty titles and is never classified. yt-dlp filters no Twitch ads at all, so a missed ad is never worse than upstream.
- Follows the live edge (media sequence numbers); no parallel catch-up path — a stalled poller simply requests the next playlist snapshot, which already reflects whatever segments the CDN still has
- End verdict: the loop asks the stream-end question at six sites, and one shared helper, `consultEnd` in `internal/engine/downloader_hls.go` (`consultStreamEnd` is it over `CheckStreamStatus`), classifies the answer for all of them into `endVerdict` (NoCheck / Unknown / Ended / Live) and logs a Warn on a failed check; each site maps the four values with an exhaustive switch, tabulated on `endVerdict`. Three are playlist-failure sites — a playlist 404/410, the consecutive-fetch-failure escalation and the consecutive-parse-failure escalation. A confirmed `ended` finalizes cleanly from ANY of them (it records `finishConfirmed`, so the loop's exit defer clears the resume sidecar); a confirmed "still live" returns `ErrQualityLost` for the orchestrator's variant refresh. They differ only when no verdict comes back: a check ERROR at the 404/410 site defers — the 404 rejoins the consecutive-error retry budget and the next reload re-asks — while the two escalation sites have already spent that budget, so they exit with their fetch/parse failure and record no reason. An unwired check finalizes at the 404/410 site (the variant is gone and nothing can say otherwise) and keeps the failure at the escalations. The other three — three or more consecutive stuck skips (live, a failed check or no check continue), init-segment-fetch exhaustion (live and a failed check return `ErrQualityLost` for a variant refresh; no check is a terminal error) and the stale window (asks `CheckStaleEnd` when wired; anything but a confirmed end falls through to the seq-regression check) — likewise latch only on a confirmed `ended`.

  Same rule as the DASH gone-burst verification above (`internal/engine/downloader_hls.go`). What an exit that recorded no confirmed end then MEANS differs by platform: on YouTube the orchestrator finalizes what was captured and the resume sidecar survives for a later Resume; on Twitch, finalizing that exit Finished would delete the staging dir and the sidecar in it, so `ExecuteTwitch` in `internal/worker/orchestrator_twitch.go` re-verifies the broadcast once and, absent a confirmed end, returns the download error so the job lands in Error with its staging intact. That verdict comes from two `GetStreamInfo` samples ~5 s apart (`confirmTwitchLiveness` in `internal/worker/worker.go`), so one transient StreamMetadata flap cannot end a live recording at any of the six consult sites above.

**HLS VOD mode (`runHlsVodParallel`):**
- Reports in SEQUENCE space. `runHlsLoop` hands it only the segments not yet written, as a playlist whose `MediaSequence` is the first of them, so a gap is `MediaSequence+index` and a progress event's `Total` is the playlist's end in sequence space — the scale `Seq` and the live loop's gaps use, and the one the worker stores the job's gaps on. Reported as slice indexes, a resumed VOD (or a recording one finished here once ENDLIST appeared) recorded a hole at sequence S as `S-curSeq` and read about 100% from its first segment. yt-dlp's HlsFD numbers fragments over the whole playlist the same way (`downloader/hls.py`).
- The opposite shape to the live loop: a fixed worker pool fetches the whole playlist in parallel and a byte-bounded reorder buffer writes the segments in ascending order as they land (`runHlsVodParallel` in `internal/engine/downloader_hls.go`). The ceiling is the same operator-settable per-job ceiling the DASH catch-up path uses (`downloader.reorder_buffer_mb`; `catchUpBufferBytes` in `internal/engine/downloader.go` is only what applies before `ConfigureReorder` has run), and it is what stops the other workers holding the rest of the VOD in RAM while the head-of-order segment works through its retry ladder — a worker waits for room instead of buffering past it, and the head is always admitted so the flush position cannot deadlock. A segment or init an edge refuses with a 403 or 410 is asked three times before it is permanent (`headlessRefusalAttempts` — an HLS fetch knows no head; see platform-services.md), so one transient refusal is not a gap, nor on the fMP4 init the end of the VOD. Failed segments become nil gap sentinels so the consumer never wedges on an index that is not coming

**VOD direct download mode (`runDirectDownload`):**
- Probes total file size with a `Range: bytes=0-0` **GET** (`probeFileSize` in `internal/engine/downloader_fetch.go` — never a HEAD; a 200 answer means the origin ignored the Range header, and its body is dropped unread rather than pulled). The probe is retried up to three times with backoff before the caller gives up on Range support (`probeFileSizeWithRetry`), so one transient failure cannot route a resumable download into the streaming fallback
- Downloads in chunks of 95-100% of 5MB (`DownloadChunkSize`) using Range requests, each chunk's length drawn afresh — yt-dlp's `random.randint(int(chunk_size * 0.95), chunk_size)` per connection (`downloader/http.py`, youtube-dl b91a7a4e5) — rather than every request ending exactly 5 MiB past the last, a perfectly regular Range pattern (`directChunkSize` in `internal/engine/downloader_direct.go`; the draw is math/rand/v2's `Int64N`, and the `chunkJitter` field is a test seam production never sets). Each chunk still starts where the bytes written end, so the jitter moves where requests end, never what is stored.
- Per-chunk retry for a 5xx or a failure with no complete answer — no response at all, or a 206 whose body broke off mid-read (`fetchChunkWithRetry` in `internal/engine/downloader_fetch.go`): up to 11 attempts (`MaxChunkRetries` — the first and yt-dlp's ten retries, `--retries` default 10, `RetryManager` in `downloader/http.py`), 1, 2, 4, 8, 16 s and then 30 s apart (`directRetryBackoff`, capped at `directBackoffCapUnits`), 181 s in all. The budget was three attempts a second and two apart, so a burst of fast 503s ended a VOD job in three seconds where yt-dlp rides it out. yt-dlp retries at once by default; Moombox backs off on purpose, because a gateway answering 5xx for an origin it cannot reach and a flapping link both pass with time. The eleventh failure ends the download with its own cause.
- Two failures are not charged against those attempts, as on the segmented path. A 403 or 410 — a googlevideo URL lives about six hours, and a long transfer outlives it — asks `OnCredentialRefresh` for a fresh URL and token and retries the chunk on it, at most `directRefreshAttempts` (2) times per chunk; the fresh URL must carry the same fingerprint as the current one (`refreshDirectURL` in `internal/engine/downloader_direct.go`), so a refresh can never append another rendition to the partial. A failure while `IsOnline` reports the device offline waits for connectivity and retries; and before a failure with no complete answer is charged as the last attempt, the monitor is given three of its polls to call an outage (`awaitOutageVerdict`) — a reset, a refused connection or a DNS miss exhausted the three-attempt ladder in three seconds, long before the monitor's second failed poll, and the verdict wait stays as the last attempt's backstop on the eleven-attempt one. A cancel during that wait is returned as the cancel. Before this, an expired URL's 403 ended the job after one attempt and an outage longer than ~3 s did too. Any other 4xx still fails the chunk at once
- The size probe and the streaming fallback answer the same failures the same way. The probe (`probeFileSizeWithRetry`) refreshes on a 403 or 410, at most `directRefreshAttempts` times, and waits out a probe that got no answer, or a 5xx, while the device is offline — asking for the outage verdict before the last attempt of one with no answer — none of it charged against its three attempts; a refresh it cannot use, a URL still refused once the refreshes are spent, or a cancel ends the download as an error that keeps the sidecar. The fallback (`runDirectDownloadFallback`, each request in `streamDirectOnce`) has the chunked loop's ladder of its own: it refreshes on a 403 or 410, at most `directRefreshAttempts` times, and asks again after a 5xx or a request that got no complete answer — none at all, or a body that broke off — at most `MaxChunkRetries` times on the chunked loop's `directRetryBackoff` ladder (capped: uncapped doubling would wait nine minutes for the tenth attempt at eleven), each count kept only while the file gets no further than it has ever stood (a short 206 asked for the rest, below, takes it further too; a 200 that restarts it from byte 0 does not).

  A 5xx or a failure with no complete answer while the device is offline is waited out instead and not counted, and before the last count of a failure with no complete answer the monitor is given its verdict window. Either way it asks again from wherever the file stands, with the resume Range. With one request, a URL that expired before the first request would spend the probe's three attempts on its 403 and reach a fallback that ended the job on the same 403; an outage as the download started would do the same — a gateway answering 5xx for the unreachable origin included — and one connection dropped mid-stream would end a fallback transfer however much had streamed.
- A 416 or an empty 206 while the offset is still below the probed total is a short origin, not the end of the file: the loop returns an error (`directShortFileError` in `internal/engine/downloader_direct.go`) and keeps the resume sidecar, rather than break, clear the sidecar and hand a truncated file to a header-only validation. The streaming fallback reads a 416 at its resume offset as "already complete" only when no total it knows says otherwise — the one the 416 states (`bytes */<total>`) or the one the sidecar recorded; a total past the offset is the same short origin, and one naming another file restarts it (below). The fallback holds a 206 to a total too — the one it states, or failing that the recorded one, which is the probed total when a mid-download 200 handed the chunked loop's transfer over: a body that ends cleanly short of it is asked for the rest from where it ended (`errDirectRestToCome`), as the chunked loop asks for its next chunk after a short one, and one that brought nothing past the byte it was asked from — an empty one, or a head of the file labelled from byte 0, which discards the partial and writes the head again — is the short origin. Taking the body's end for the file's would finish a truncated file.
- An origin that stops fewer than 100 bytes short of the total (`directEndTolerance`) has delivered the whole file: a 416 or an empty 206 there completes the download — the sidecar cleared, an Info line naming the shortfall (`directEndsWithinTolerance` in `internal/engine/downloader_direct.go`) — on the chunked loop and on the streaming fallback alike, rather than the short origin above, an error on every Resume. It is yt-dlp's tolerance: HttpFD reads a 416 on resume as "already fully downloaded" when the file's length is within 100 bytes of the partial, strictly (`downloader/http.py`, "YouTube sometimes adds or removes a few bytes from the end of the file", youtube-dl #175). Upstream re-requests the file without a Range to read its length again; Moombox compares against the total its probe or the sidecar already states, without a request that would start streaming the whole file. A shortfall of 100 bytes or more is still the short origin. The same bound holds a resume's total (`differentFileReason`, below): a probe or a resume Range's answer stating a total fewer than 100 bytes from the one the sidecar recorded is the same file, and the partial is kept, logged and continued to the new total — provided it does not already overrun it — rather than discarding a multi-GB partial and fetching it again from byte 0 on any move.
- Falls back to streaming download if server doesn't support Range — one response for the whole file, bounded by the read-progress deadline alone, asked again after a refusal it refreshed, a failure it counted or an outage it waited out (above)
- Saves a resume sidecar every 50 MB (`directResumeInterval` in `internal/engine/downloader_direct.go`) on both the chunked and the streaming path; before Arc E the whole-file path wrote none at all, so an interrupted VOD restarted from byte 0 however far it had got. The 50 MB are counted from the last checkpoint (`checkpointDirect`), across every request the streaming fallback makes and across a mid-download 200's hand-off to it, and a discard starts the count over; the fallback counted from the start of each request, so one whose requests each moved less than 50 MB — a link that breaks every few minutes — wrote no sidecar however much it staged.
- The sidecar records the probed total (`totalSize`), and a resumed partial is held to it: when the resume's own probe answers a different total, or the partial is already longer than the file, the bytes are a prefix of a different file and the download starts over (`discardStagedMedia`) instead of appending (`differentFileReason` in `internal/engine/downloader_direct.go`). A resume whose probe failed reaches the streaming fallback instead, which holds the partial to the total its resume Range's 206 or 416 states (`parseContentRangeTotal`) and on a different file discards and streams from byte 0 (`restartDirectFallback`). A discard forgets the recorded total with the bytes. The YouTube VOD strategy also sets a per-stream `StreamID` (video, itag, `clen`), so a restart whose format selection moved never splices one rendition onto another (see The Whole-File VOD Path in platform-services.md)
- Progress reported as percentage

**Resume capability:**
- `.resume.json` file stores: `lastSeq`, `bytesWritten`, `timestamp`, `baseUrl`, `streamId`, and for a whole-file download `totalSize`
- On resume: validates IDENTITY via `resumeIdentityMismatch` (explicit StreamID first, then YouTube URL fingerprinting — a finished VOD's `id=o-…` URL by its itag and `clen`; opaque no-identity URLs are trusted — see data-and-storage.md), then file size vs saved bytes
- DB-level fallback: if resume file is lost but database has `last_video_seq`/`last_audio_seq`, uses file size as byte position
- The media file is fsync'd before every sidecar save (`syncMediaFile` in `internal/engine/downloader_resume.go`) and the sidecar itself is written fsync+rename, so neither durable position can lead the durable bytes after a power loss; a failed media fsync skips that one save rather than recording a position it cannot back
- With a usable sidecar the file is truncated to the saved byte position and the missing tail appended. With NO usable sidecar the engine never truncates non-empty staged media: `StopOnGap` callers (Twitch live) get `ErrGapDetected` and gap-split instead, and every other caller gets `ErrStagedMediaPresent` so the orchestrator decides. One deliberate exemption: a whole-file VOD download (`IsDirectURL`) is out of the guard's scope — its partial is not segmented staged media and is always re-fetchable from the same static URL, so restarting it costs bandwidth rather than footage (and the 50 MB sidecar cadence above bounds even that)
- The one caller that genuinely requires a file starting at sequence 0 — the manifest-free DASH restart, via `DiscardStaged` — cannot refuse, so it preserves instead: `preserveStagedRecording` in `internal/engine/downloader.go` renames the headed recording ASIDE as `<file>.restart-<unix ts>` (its sidecar follows as `.restart-<unix ts>.resume.json`) and opens the fresh file beside it. Only bytes carrying no container header are discarded
- The whole-file VOD download sets aside by the same convention, from the worker side: a job that comes back as a finished VOD after an earlier live or post-live attempt finds that attempt's `video_stream` / `audio_stream` / `video.ts` still in its staging dir, and `discoverStagingMedia` (`internal/worker/orchestrator_mux.go`) ranks those names above `video.mp4`, so without the set-aside the restart mux and the Mux action would archive the stale partial capture and delete the complete download with staging. `DownloadVod` (`internal/worker/strategy_youtube_vod.go`) therefore calls `setAsideLiveShapesForVod` (`internal/worker/staging_shapes.go`) once its formats are resolved: every live-shape file is renamed `<file>.restart-<unix ts>` under one stamp shared by the video and audio halves, its sidecar moved with it (`setAsideStagedMedia`) — a `video.ts` left by an HLS interlude in another session takes the same stamp, and is still its own recording, because the grouping keys on the recording a name belongs to as well as the stamp; an empty one is removed; a rename that fails fails the run rather than download beside a capture discovery would prefer. The dir then holds one current recording, and the earlier one is an ordinary aside — muxed to its own sibling at finalize, never into the archive. Ranking the shapes by mtime was the alternative and answers the wrong question: the newest file is not the complete one
- A capture that changes shape inside its part sets the earlier shape aside by the same convention: a job resumed after a restart records into the part it left unmuxed, and the live HLS fallback (`setupWithFallback`, `internal/worker/challenge_free.go`) changes the shape there, for either of its causes, the player's JS challenges or a GVS token none could be minted — HLS recorded into the part holding an earlier session's from-start `video_stream` / `audio_stream`, and DASH again, once the player can be solved or a token minted, beside the fallback's `video.ts`. The finalize muxed the one recording the setup named and the cleanup then deleted staging with the other one unmuxed in it (no part dirs, no whole-file pair: nothing `decideStagingCleanup` shields). Every setup that built its downloaders sets the other shape's staged media aside before they write (`setAsideOtherLiveShape`, `internal/worker/staging_shapes.go`) — the DASH pair under one stamp for an HLS capture, `video.ts` for any other — with a Warn naming the asides, and a rename that fails fails the setup; the shape a setup resumes is left in place
- An aside is recovered at finalize and never merged: it overlaps the fresh recording from sequence 0, so `muxStagedAsides` in `internal/worker/orchestrator_mux.go` muxes each restart's GROUP of asides into its own sibling file beside the archive (`{name}.restart-<ts>.mp4`) and records no segment row. One group per (staging dir, timestamp, recording): a DASH restart sets aside the video and audio halves together, normally under the same second, and `groupStagedAsides` recombines that pair into a single file rather than two. The recording a stem belongs to (`asideRecordingOf`) is part of the key because a stamp alone is not one recording: `video_stream`/`audio_stream` are one DASH capture and `video.mp4`/`audio.m4a` one whole-file download, while `video.ts` is always its own — grouped by the stamp alone, a `video.ts` set aside beside a DASH pair under the pair's stamp had no slot in the pair's group, and the finalize removed it with the pair without ever muxing it. Each half is stamped by its own downloader's clock read, so a restart that straddles a second boundary stamps them a second apart; `pairStraddledHalves` rejoins a video-only and an audio-only group of the same dir and recording one second apart (two separate restarts are never that close, and a `video.ts` is never an `audio_stream`'s other half).

  A recovered aside gets a `.recovered` marker beside it, holding the sibling's path (`asideRecoveredMarker`), once its copy is verified and BEFORE it is removed; the marker outlives the aside only when the removal fails (a Windows handle on it) or the process dies in between: every aside scan skips a marked aside, so the next finalize or recovery does not mux it again to `-2`, and `removeRecoveredAsides` retries the removal at the start of each `muxStagedAsides` pass. Until it is muxed it counts as an unmuxed part, which keeps the whole staging dir from being swept, and the orphan sweep (`internal/worker/orphans.go`) lists any it finds under that dir's asides. Neither shield ages an aside out — unlike the tail and chat keeps beside them, which expire on `incomplete_staging_expiry_days` — because finalize muxes every READABLE aside, so one still in staging is footage FFmpeg could not read — or could not copy whole: a sibling shorter than its aside fails the same ENGINE-9 duration check the main and part muxes apply (`verifyAgainstStaging`), the short copy is discarded and the aside kept, since it is deleted only once its sibling is verified — and that exists nowhere else.

  A sibling muxed from a repaired copy of a damaged aside (step 12) is written, and the aside marked recovered so no later pass muxes it again, but neither half of the restart is removed: the damaged one holds bytes the sibling lacks, the other is held with it by a record of its own (`keepRepairedAside`), and `removeRecoveredAsides`, the boot sweep and the staging cleanup all leave a marked aside alone while a mux-gap record beside it holds.

  Recovery is also reachable ON DEMAND, which is what a staging directory holding nothing BUT asides needs: `RecoverAsides` (`internal/worker/worker.go`) runs `recoverAsides` (`internal/worker/orchestrator_mux.go`) for one job — the same sibling naming, beside the job's recorded archive and under its stem when it has one (`recordedArchiveLocation`, the part base for a split job, where the finalize put any it recovered — re-resolving from the current title would send them to a stem no archive has, which the output sweep would then offer as strays; the sweep also knows a split job's part base as a stem), the fresh template name only for a job with no archive yet, the same best-effort-per-group behaviour, under the same mux root and the same download slot `MuxJob` (`internal/worker/worker.go`) takes — then copies the chat capture a preserved directory is still holding (`findKeptChatCapture`, `internal/worker/orchestrator_mux.go`, matched with `keepOnlyChatCapture`'s own rule in `internal/worker/worker.go`) beside the FIRST recovered file as `<stem>.chat.json` (`copyKeptChatSidecar`, `internal/worker/orchestrator_mux.go`), unless the job's own finalize already wrote that archive.

  A partial success is reported, never swallowed: a group FFmpeg could not read stays in staging, where the shield keeps it. **Staging is reclaimed only when it holds no recognised media (`discoverStagingMedia`, `internal/worker/orchestrator_mux.go`) and no unmuxed part** — and only once a fresh read of the job's row still finds it not active (`IsActiveJobStatus`, `internal/worker/orphans.go`), because a revival can hand that same directory to a new download before its first files take a name `discoverStagingMedia` recognises — `cleanupStagingAfterMux` (`internal/worker/worker.go`) is then left to apply its own incomplete-tail and chat-capture carve-outs, so a chat-incomplete job is pruned down to its chat rather than deleted. The guard is not belt-and-braces: with the asides consumed, none of that function's shields — set-aside recordings, an unmuxed part (`hasUnmuxedSegmentParts`), a root recording the finalize did not use (`unusedRootRecording`), the incomplete tail, the incomplete chat capture — covers a Cancelled job whose staging still holds the fresh recording beside the aside (`hasUnmuxedSegmentParts` is false with no `seg_N` dirs, and a single-file root holding one recording has none unused), and an unguarded reclaim would delete the very recording the Mux action exists to rescue.

  This is its OWN verb and not a widening of the Mux action: `HasSegmentFiles` (`internal/worker/staging.go`) deliberately does not know the suffix, so `MuxJob` and `POST /api/jobs/{id}/mux` still mean "mux the recording". It refuses on an active job (`IsActiveJobStatus`, `internal/worker/orphans.go`), on a job with nothing set aside, while another operation holds the job's staging — a per-job claim (`claimJobOperation`, `internal/worker/worker.go`) that `MuxJob` takes too, because both verbs reach `muxStagedAsides` with their own `asideOutputPath` (`internal/worker/orchestrator_mux.go`) collision map and would write the same name — and, looked at once it holds the claim, while the job's last run is still registered or a run of it is queued (`queuedOrRunning`, `internal/worker/worker.go`): the cancel route writes Cancelled before the run stops, and a recovery started there muxed out of staging the run was still writing. `MuxJob` and `ClaimChapterImport` (`internal/worker/chapter_import.go`) make the same check once they hold their claim, since a reset verb queues the job while it holds the claim and then lets go. A claim's release frees only the holding it was handed (`stagingClaimRelease`), so a stale or repeated release cannot drop a newer holder's claim. The claim is the job's one lease on its staging outside a queue run (`jobOp`, `StagingClaimHolder`): the chapter import and the boot cleanup take it as well, and the reset verbs — Resume, Reinitialize, auto-reinitialize, the cookie-refresh resume — hold it while they reset and queue the job. What starts a run without it skips a job whose claim is held: the heartbeat (`enqueueRunnable`) and the scheduler's admission (`Scheduler.stagingBusy`), which a recovery of a COOKIES? or Queued row would otherwise race once the credential sweep revives it; the claim's release wakes both, and the scheduler asks for as many rows more as there are claims held, so a claimed row it skips does not cost its channel a slot that sweep. Those verbs never run under another holder: the REST verbs answer 409 naming it (a reset verb's own claim excepted, which the worker answers as a pending verb) (`refuseWhileStagingClaimed`, `internal/web/routes/jobs.go`, owner ruling R-A2), and a verb that cannot be refused — the TUI's, the monitors' auto-resume and auto-reinitialize — waits for it with no cut-off, logging one line naming it (`afterJobExit`, `awaitStagingClaim`, `internal/worker/worker.go`, R-A1); a Reinitialize let through during a recovery used to delete the staging FFmpeg was reading. The automatic Twitch mux waits that way only for a chapter import; any other holder defers it to the monitor's next poll (`autoMuxNow`, `internal/worker/twitch_end_unconfirmed.go`). One verb waits per job: a different one meanwhile is refused with `ErrResetPending` ("reinitialize already pending" — 409 over REST, the same text as a red feedback line in the TUI, R-A3/R-A4), the same one again answers `ErrAlreadyPending` — a no-op, which REST and the TUI answer as success and the monitors, which offer their verb on every poll, as nothing new to log — and a verb whose row cannot be read is not accepted (`ErrJobNotFound`, 404 over REST; a failed read, 500). The one that waited applies only while the row still reads the status it read when the verb was accepted (`UpdateJobFieldsIf`, `acceptedStatus`), so an operator's Cancel during the wait wins — except that a Resume or Reinitialize accepted on a COOKIES? row applies over an Upcoming or Queued a cookie refresh wrote meanwhile — the run's own, whose enqueue stepped aside for it, or the credential sweep's — as long as no run of the job is queued or running (`queuedOrRunning`). The job's status is never written: recovery is not part of the job's lifecycle. That is also why the run brackets itself with `TrackJobForLogs` and `restoreLogRouting` (`internal/worker/worker.go`) — `RouteLogToJobs` (`internal/database/database_jobs.go`) scans only the tracked set and `SyncJobLogTracking` (`internal/database/database_jobs.go`) removes every terminal job from it, so without the bracket a verb that runs exclusively on terminal jobs would log into nothing. `ScanAsides` (`internal/worker/orchestrator_mux.go`) is the read side both UIs render

#### Catch-up: rolling window and byte-bounded buffer

Parallel catch-up (`runParallelCatchUp`, `internal/engine/downloader_parallel.go`) is a rolling window, not per-batch barriers: workers claim sequences continuously off a shared cursor and completed segments flush to disk in strict ascending order as they arrive, rather than waiting for an entire batch of `segment_workers` fetches to land before the next batch starts. A per-batch design pays a full HEAD-probe round trip between every batch; the synthetic-latency harness for this path measured a batched run at 4.888s against 0.84s for the same segment count under the rolling window.

- **Claim window width** (`maxCatchupBatch`, `catchUpBatchLimit`) — normally `8 * segmentWorkers()`, so a wider configured pool gets a proportionally deeper pipeline instead of starving against a fixed ceiling (the pre-`segment_workers` code had this fixed at 48, i.e. `8 * ParallelDownloads`). After a failure episode (`noteCatchUpFailureEpisode`, fired on 403/permanent-error bursts) the window damps to a floor of one full parallel wave — `segmentWorkers()` — and regrows by one segment per `catchUpRegrowInterval` (1s) back to the full width. The floor and 1s interval were tuned on field evidence (2026-08-15): a floor of 1 segment regrowing at 10s (moonarchive's heartbeat-driven damping) collapses catch-up throughput to 1-3 segments wide for the whole duration of a 403 storm, and refresh-and-retry (see "Mid-job re-mint" in platform-services.md) already answers 403 bursts directly, so the damp need not shoulder that job alone.
- **Reorder buffer ceilings** (`downloader.reorder_buffer_mb` per job, `downloader.reorder_budget_mb` process-wide; defaults 1024/4096 MB, or 256/1024 on arm64) — bound the buffers by bytes rather than segment count, because a wider `segment_workers` pool would otherwise scale buffered memory with a throughput setting (at 1080p60's 3.7-6.2 MB segments, sixteen workers on a count-bounded buffer held ~250 MB regardless of the count chosen). The per-job ceiling is what one download may hold; the process-wide budget is the sum across every live buffer, which nothing bounded before — at the per-job ceiling alone, N concurrent downloads could hold N ceilings. A worker blocks rather than buffering past either; the head-of-window segment is always admitted at BOTH levels so the flush position can never deadlock (nothing frees either ceiling without a flush, and nothing flushes without its head), and its bytes are still charged so a teardown frees exactly what it took; segments above the lowest known-failed sequence are dropped rather than held, since they cannot flush until that failure resolves.

  Resident memory per download is therefore roughly the per-job ceiling + `segment_workers` × segment size, and across the process roughly the budget + one head segment per download — not a function of the claim window width. Both values reach the engine through `ConfigureReorder` (`internal/engine/reorder_budget.go`), called once at boot and again on every config save; `0` means unbounded on either. The arm64-only defaults come from `platformDefaults` (`internal/config/config.go`), which is the config package's only platform-conditional default and states the rule for any future one: arm-motivated caps apply only on arm64.
- **Head freshness** — not solely the per-batch HEAD probe (`HeadProbeInterval`, 5s). Every segment response's `X-Head-Seqnum` is harvested opportunistically to update the known head, since the rolling window has no natural per-batch checkpoint to probe from; the interval probe still runs as a backstop.
- **HTTP transport ceiling** (`engineMaxIdleConnsPerHost`, 64, `downloader_fetch.go`) is a fixed idle-connection-pool size per host, not derived from `segment_workers`, because the HTTP client is a package-level singleton built before any worker count is known. A configured `segment_workers` comfortably above this (past `config.SegmentWorkersWarnThreshold`, 16) degrades to per-segment TCP+TLS handshakes instead of connection reuse rather than failing outright — the first place to look if throughput stops scaling with a higher `segment_workers` value.

### QualityMonitor

The `QualityMonitor` runs alongside a live stream download and detects resolution changes:

- Probes every 30 seconds (`qualityMonitorInterval`) via a format re-fetch
- Compares width and height against the current baseline
- FPS-only changes are intentionally ignored (splitting for framerate alone adds overhead without saving storage)
- Sends new `QualityInfo` to a channel when a change is detected
- Thread-safe baseline updates via mutex
- Probe errors are logged and skipped (never trigger false positives)

When a quality change is detected and the current segment has been running for at least 10 seconds, the orchestrator:
1. Cancels current downloaders
2. Re-fetches video info FIRST, to tell a real change from a transient blip. On YouTube (`qualityChangeInfo` in `internal/worker/orchestrator_youtube.go`) a failed fetch is retried every 5 minutes (`streamEndVerifyInterval`) until segments have been quiet for 10 (`streamSegmentTimeout`) — the verify branch's own clock — and only then ends the job in Error with staging intact; one transient API fault does not. Inside a resume wait that clock always reads too long (the downloaders are cancelled), so there the wait's own `interruption_timeout` deadline bounds the retries instead (`qualityChangeQuiet`)
3. If the refreshed quality matches, continues in the same staging directory with fresh downloaders — no split
4. Otherwise muxes the current segment in a goroutine parented by the orchestrator's mux root (`muxRoot` in `internal/worker/quality_split_common.go`), not `context.Background()`, and records it in the `segments` database table
5. Creates new downloaders at the new quality in the next part's staging directory
6. Updates the monitor baseline to the new quality

### JobQueue

The `JobQueue` implements a two-tier concurrency model:

**Lifecycle tier (100 slots):**
- Gates how many jobs can be in the DOWNLOAD half of the pipeline simultaneously — downloading plus muxing, which is exactly what `LifecycleCount()` reports
- The slot is claimed at the download decision, not at dequeue: `processJob` calls `AcquireLifecycleSlot` in `internal/worker/queue.go` only once `StreamProcessor.Process` has answered "should download", and every exit path from there releases it through the deferred `Complete` (owner decision O-F)
- Stream probing and the wait for a stream to go live therefore run slot-free. Holding a slot for the whole wait — hours to days for an `Upcoming` job or a manually-added offline Twitch channel — would mean that at 100 waiters a newly live stream never started at all
- A VOD takes its download slot FIRST and only then the lifecycle slot, so one queueing for the download pool holds no lifecycle slot. The other order let enough admitted backlog (Σ `archive_slots` across channels) fill the lifecycle pool with VODs that were merely waiting, and a live broadcast — which never waits on the download pool — blocked behind them and lost footage
- A wait that outlasts `lifecycleWaitWarnAfter` in `internal/worker/queue.go` (30 s) logs one line, once per wait, naming the job and the slots held: at the cap the symptom is a capture that simply does not start, and until that line existed nothing explained it

**Download tier (configurable, default 10 slots):**
- Gates how many VOD jobs can be actively downloading segments in parallel — VODs ONLY. Broadcasts pass through ungated (`acquireDownloadSlot` with `isVod=false` is a no-op): a missed slot on a VOD delays a file that already exists, a missed slot on a live broadcast loses footage. Peak concurrent downloads is therefore (live broadcasts) + `num_parallel_downloads`
- **Not the same knob as `downloader.segment_workers`.** `num_parallel_downloads` gates concurrent VOD **jobs**; `segment_workers` (default 12, no upper limit — see the constants table under SegmentDownloader below) gates concurrent **segment fetches within one download**, live or VOD. Because broadcasts bypass the download tier entirely, `num_parallel_downloads` has zero effect on a live stream's catch-up rate — confusing the two cost real debugging time when the owner had it set to 1000 with no observable change to catch-up throughput. Segment-level concurrency is what `segment_workers` controls.
- A VOD job acquires a download slot via `AcquireDownloadSlot()` after stream processing. It tries first (`TryAcquireDownloadSlot`), and only a VOD that actually has to queue shows it: its progress line reads `vodSlotWaitProgress` (`internal/worker/vod_slot_wait.go`) for the length of the wait and is cleared however the wait ends. Stream processing writes no status for a VOD (`vodStatusUpdates`, `internal/worker/stream_processor.go`; `processTwitchVod`, `internal/worker/stream_processor_twitch.go`, for a Twitch one) — the row keeps the one it came in with, Upcoming for a freshly classified VOD — and `ExecuteWithChat` (`ExecuteTwitch` for Twitch) writes Downloading once the slot is held; before, every queued VOD read Downloading through the whole wait, and a Twitch VOD went on doing so after a YouTube one had stopped
- The format URLs were extracted BEFORE both waits, and a googlevideo URL lives ~6 h, so a VOD that queued longer started a whole-file download on an expired URL and failed its first request with a 403 nothing retried. Once both slots are held, `processJob` re-extracts a stale extraction (`refreshStaleVodInfo` → `StreamProcessor.RefreshVodInfo`): one `vodInfoMaxAge` (1 h) old, or whose format URLs say through their own `expire=` (query or `/expire/<unix>/` path form) that they lapse within that hour (`vodInfoStale`). The re-extraction applies the same playability verdict as the first, and refuses a stream no longer classified as finished; either answer is returned marked as the verdict it is (`vodRefreshVerdict`, via `judgeRefreshedVodInfo`), so it ends the job where it sends it — `COOKIES?` or Error — as the same answer up front would. Stale is a precaution, not a verdict, though: a re-extraction that fails transiently (`classifyProbeErr`) while every format URL the extraction holds states an expiry still ahead (`vodURLsUnexpired`) leaves the extraction in place, and the download goes ahead on it — an expiry it then runs into is the downloader's to refresh (`OnCredentialRefresh`), as one partway through any long transfer is. Ending the run on such a failure would end a VOD whose URLs still worked in Error over a fetch it did not need. URLs already expired or carrying no expiry to read still take the failure
- Released via `ReleaseDownloadSlot()` after download completes but before muxing
- This allows muxing to proceed without blocking download slots (muxing is CPU-bound, not network-bound)

**Priority system:**
- `Live` = 1 (highest priority)
- everything else (`Upcoming`, `Downloading`) = 0 — every retry path writes one of those before it enqueues
- FIFO among jobs with equal priority

**Queue operations:**
- `Enqueue(jobID, status)`: Adds to pending queue. O(1) duplicate detection via `pendingSet`. Backlog limit of 100 pending jobs; drops with warning if full.
- `Dequeue(ctx) -> (jobID, jobCtx, ok)`: Blocks until a pending job exists — there is no lifecycle gate here. Returns a per-job cancellable context.
- `AcquireLifecycleSlot(ctx, jobID) -> bool`: Blocks until one of the 100 lifecycle slots is free, then claims it for the job. Returns false if context cancelled. Warns once per wait past 30 s.
- `AcquireDownloadSlot(ctx, jobID) -> bool`: Blocks until a download slot is free. Returns false if context cancelled.
- `TryAcquireDownloadSlot(jobID) -> bool`: Takes a free download slot without waiting; `AcquireDownloadSlot` is this in a loop. The slot is the key's: a key that already holds one is told so and nothing is counted again, matching the releases, which are keyed and idempotent, so a second acquire cannot leak one. A set-aside recovery takes its slot under a key of its own (`acquireRecoverySlot`), so a run of the same job overlapping it counts as a second FFmpeg instead of sharing — and being freed with — the recovery's.
- `ReleaseDownloadSlot(jobID)`: Frees the download slot. Signals waiting jobs.
- `ReleaseSlots(jobID)`: Frees the lifecycle and download slots (if held) without ending the run. `setJobError` and `handleCancellation` call it before their tails (notifications, an automatic cookie refresh), so the next download need not wait on them.
- `Complete(jobID)`: Ends the run — frees any slot still held, cancels the per-job context, unregisters it and closes its `Done` channel. Called once per run, by `processJob`'s defer, when the goroutine returns. An early call would unregister a run still in its tail, so a re-enqueue in that window would start a second run, which the first run's deferred `Complete` would then tear down; whatever re-enqueues a job from inside its own run (the automatic cookie refresh's resume, `AutoReinitializeJob`) waits for the exit through `afterJobExit`.
- `Cancel(jobID)`: User-initiated cancellation. Sets `cancelled` flag, cancels context, removes from pending queue. Returns whether it flagged a run — and a run that has settled its outcome is not flagged (`settle`, below), so its caller sends the Job Cancelled notification itself.
- `WasCancelled(jobID) -> bool`: Returns and clears the cancellation flag. Used to distinguish user cancellation from shutdown. Settles the run.
- `settle(jobID) -> bool`: The point past which a run no longer reports a Cancel. `setJobError`, the backlog requeue and a run's panic (`recordRunPanic`) call it as they record their outcome, and it reports whether a Cancel flagged the run first — the run then ends as a cancelled one (`handleCancellation`) and sends the Job Cancelled its canceller left to it. Otherwise the run is settled, and `Cancel` does not flag it. `settleRun` is the same, and also reports whether the run had settled already — `recordRunPanic` asks, and leaves the outcome a run recorded before its panic standing. The queue's lock decides which came first: checked and written apart, a failure written between `CancelJob`'s flag and its `Cancelled` write sent Job Failed for the operator's Cancel, and a Cancel that flagged a run already past reading the flag — a failure's tail, which an automatic cookie refresh can hold for minutes, or a requeue — was reported by nobody.

**Signaling:**
- `notify` channel (capacity 1): signals that a pending job is available
- `lifeNotify` channel (capacity 1): signals that a lifecycle slot is free
- `dlNotify` channel (capacity 1): signals that a download slot is available
- All three use non-blocking sends to avoid producer blocking. On the two SLOT channels (`lifeNotify`, `dlNotify`) each successful acquirer re-signals while capacity remains, so a burst of releases collapsing into one signal cannot leave a waiter asleep beside a free slot. `notify` needs no such cascade: `Dequeue` re-checks the pending queue under the lock every time it is called and only parks when the queue is empty, so a coalesced signal costs nothing

### Backlog Scheduler

The worker-owned `Scheduler` (`internal/worker/scheduler.go`) admits backlog (`Queued`) jobs at most `archive_slots` at a time per channel — spec §10's archive-slots pacing. It is the only path out of `Queued`: `ShouldProcess(Queued)` is false by design, so neither startup recovery nor the worker's heartbeat poller ever touches a `Queued` row.

- Single goroutine, woken by `Wake()` (backlog-job creation, job completion, a cookie repair that returns parked backlog to `Queued`) or the worker's 60s heartbeat; wake signals coalesce through a capacity-1 channel
- One admission sweep per wake: for each channel with `Queued` rows, admit `archive_slots − in-flight backlog jobs`, newest `published` first
- Admission writes `status = Upcoming` durably FIRST (the in-flight count observes the DB), then enqueues in the JobQueue — a crash between the two steps self-heals because startup recovery re-enqueues `Upcoming` rows
- The admission write is a compare-and-set on `Queued` (`UpdateJobFieldsIf`, `internal/database/database.go`). Written unconditionally, it overwrote an operator's Cancel that landed between `NextQueuedJobs` and the write, and the cancelled job downloaded after all. A row that left `Queued` in that window is not admitted and takes no slot: the next row the query returned gets it, or the next sweep does — not a re-query or a `Wake`, which a database that cannot write would turn into a spin. The worker's own failure writes take the same care: `setJobError` and the backlog requeue write with `UpdateJobFieldsUnless(..., Cancelled, ...)`, and a failure that a Cancel flagged first (`JobQueue.settle`), or that finds the row Cancelled, ends the run as a cancelled one (`handleCancellation`) instead of turning it into Error or back into `Queued`. The Job Cancelled notification is sent once either way: by the run when the Cancel flagged it first, and by the cancel route or the TUI when the run had already settled
- `resolveSlots` is injected by `cmd/moombox` against the live config store, so per-channel `archive_slots` overrides hot-reload
- A **disabled** channel resolves to 0 slots, so disabling it PAUSES its queued backlog (owner decision O-J, 2026-09-17). Every discovery path already reads `enabled = false` as a pause — the feed, DECAPI and Twitch monitors skip the channel, and the backfill keeps it in `active` while never scanning it (a scan already queued for it is dropped and a running one cancelled, both with their cursor kept — see §13) — and the resolver was the one place that did not, so a disabled channel went on starting downloads M at a time. In-flight jobs are untouched: they have already left `Queued`, and this number is an admission budget rather than a kill switch. A channel with **no config entry at all** still gets the global default, so a removed channel's kept `Queued` rows are not stranded: the scheduler admits them `monitors.archive_slots` at a time, and `NextQueuedJobs` LEFT-JOINs `feed_items` so the partners the departure prune deleted do not hide them (§13, *Removing a channel*).
- **No admissions during an outage.** A sweep admits nothing while the connectivity monitor (`Scheduler.conn`, the worker's `Connectivity`) reports offline, and `Run` subscribes to its `OnStateChange` so the moment it reports online again is a wake. An admission made offline is a backlog VOD sent to fail its first fetch, and each one that failed freed its slot for the next: a channel's whole `Queued` backlog drained into Error in the minutes the network was down, and the archive pass never re-creates a video it has history for. A job already admitted, and every broadcast, which never passes through the scheduler, waits an outage out in `processJob` instead (*An outage is not an error*, under Transition Rules)
- **No admissions onto a full disk.** A sweep with a backlog to admit first reads the volume the jobs write to and admits nothing from the reading at or past `disk_critical_percent` until one 2 points below it (`Scheduler.diskGateClosed`, `internal/worker/scheduler.go`). The reading is the disk alerts' own — `paths.output_directory` through `disk.GetDiskSpace`, judged by `DiskConfig.AtCritical` (`internal/config/types.go`), the rule `ComputeWarnLevel` (`internal/web/routes/stats.go`) applies, and `DiskConfig.ClearOfCritical`, the one an open `disk_critical` alert steps down on — taken fresh by `DownloadWorker.readOutputDisk` (`internal/worker/disk_gate.go`) rather than from the dashboard's last reading, which can be six minutes old. There is no setting of its own. Every sweep reads again, the 60 s heartbeat's included, and nothing signals space being freed, so a held backlog resumes within a heartbeat of the volume dropping 2 points below the threshold — the alert's recovery margin (`DiskRecoveryMargin`, `internal/config/types.go`), so the gate reopens on the reading that steps the alert down.

  A reading in between leaves the gate as it was: reopened on the first reading under the threshold, a volume sitting on the line admitted a backlog VOD every time it dipped under it. The gate's close and its reopen are each logged once; a reading that fails leaves the gate where the last good one put it, as the alerts freeze on theirs. The close lives in memory, so a restart would reopen it: `run()` starts the gate closed when `open-alerts.json` holds the gate's own hold (`diskGateHeld`, which the gate records there on every close and reopen through `Scheduler.RecordDiskHold`) or an open `disk_critical` (`restoreDiskGate`, `cmd/moombox/disk_alerts.go`, calling `Scheduler.RestoreDiskHold` before the worker starts), so the restored alert and the gate still end on the same reading — started open, the gate read 94% against 95 as neither critical nor clear and admitted backlog while the alert held critical. The alert's level alone was not enough: the gate reads on every sweep and the alerts about every six minutes, so a gate that closed on a reading the alerts never took restarted open inside the margin all the same.

  A hold restored from the alert is recorded too, so it then ends on the gate's own reopen. Only backlog admission waits: live, upcoming and manually added jobs never pass through the scheduler, and a backlog VOD already admitted runs on. A sweep with nothing `Queued` takes no reading while the gate is open; a closed gate reads on every sweep, backlog or none, so it reopens on the reading that clears the threshold even when nothing waits — read only with a backlog, a close outlived its incident, and a backlog queued after the volume had cleared and refilled to inside the margin waited on it. The reading is the output directory's volume only — a staging directory or a per-channel output directory on another volume is not what it measures, as it is not what the alerts measure
- **Transient pre-download failures go back to `Queued`.** A backlog job whose stream-processing fetch — or the re-extraction a stale VOD makes once its slots are held, when the URLs it would replace have expired or state no expiry — fails transiently, other than on an outage the connectivity monitor calls (that one is waited out in place, `processStreamThroughOutages`), (`classifyProbeErr`, `internal/worker/probe_classify.go`: network, timeout, 429/5xx and whatever it cannot place) returns to `Queued` instead of Error (`requeueBacklogAfterTransientFailure`, `internal/worker/backlog_retry.go`), only where `CookieResumeStatus` would send it there — priority 1 with a channel, its `feed_items` partner or not (a removed channel's kept backlog has lost it to the departure prune, and the scheduler admits it all the same) — and held from re-admission for a backoff (5, 10, 20 minutes: `backlogRetryBackoff` doubling). A sweep skips a held job without costing its channel the turn, asking `NextQueuedJobs` for enough rows that every hold could be among them.

  After `backlogRetryLimit` (3) runs in a row that each ended back in `Queued` the job ends in Error, saying so, so a video that is really gone still gets there; a definitive refusal (a 404, a playability verdict) is not retried — the re-extraction's verdict included, which reaches the worker as an error whose text `classifyProbeErr` cannot place and is recognised first (`isVodRefreshVerdict`). A YouTube rate limit — its verdict, or an Innertube 429 on the whole cascade (`youtube.HTTPRateLimitError`) — is neither: it takes its own hour back to `Queued` outside the budget (*A YouTube rate limit is not an error*). Holds and counts live in memory: a restart forgets a backoff and grants a fresh budget, never loses the job
- **A download that runs out of disk goes back to `Queued` too.** A backlog job whose download — or the mux after it — fails because the disk is full (`isDiskFull`, `internal/worker/disk_full.go`: `ENOSPC` on unix, `ERROR_DISK_FULL` / `ERROR_HANDLE_DISK_FULL` on Windows anywhere in the chain, which is how `engine.ErrLocalWrite` carries the engine's writes; or the out-of-space text, which is how FFmpeg's stderr tail (the last 500 bytes the archive mux's runner, `runFFmpeg`, keeps — `stderrTail`, `internal/engine/muxer.go`) and the engine's `%v`-flattened HLS init write carry it; or the mux's own refusal to write the repaired copy of a damaged staged recording the staging volume has no room for, `repairNoSpaceError`, `internal/worker/mux_repair.go`) takes the same requeue, backoff and budget (`requeueBacklogAfterDiskFull`, `internal/worker/backlog_retry.go`), and after the backoff waits on the disk gate above for as long as it stays closed. Staging is kept: a whole-file VOD resumes from its last resume checkpoint, while one whose MUX ran out of space downloads again, since a completed download clears its resume state.

  The budget is one streak for both kinds: it counts the runs that ended back in `Queued`, and only a run that ends otherwise — finished, Error or `COOKIES?`, cancelled — resets it (`forgetBacklogRetries`, `internal/worker/backlog_retry.go`). A job waiting in `Queued` has no run to end, so the operator's verbs end its streak themselves — Cancel, Retry and Resume, and a deleted row with it, drop the count and the hold (`endBacklogStreak`), so a backlog VOD cancelled while it waited for space and then retried does not give up into Error on its first requeue with its old count still standing. A row a channel removal's "delete its pending jobs" deletes goes the same way, although that delete fires one `OnJobsChange` rather than an `OnJobDeleted` per row: the worker ends the streak of every counted job missing from that list (`endStreaksGoneFrom`), so a re-added channel's rescan, which creates the same video's row again, does not inherit a backoff and a count it never earned. That list reaches the worker off the writer's goroutine, so an inserted row also starts clean on its own (`OnJobAdded`): a row `AddJob` inserts has had no run to earn a streak, and whatever one its id still holds goes at the insert.

  A fetch that succeeds does not reset it: every run whose download then runs out of disk follows one, and the budget would never be spent. A broadcast or a manually added video that runs out of disk still ends in Error
- **No admissions while YouTube rate-limits the session.** A rate limit on any job's fetch — its verdict or a 429, backlog or broadcast, from stream processing, a stale VOD's re-extraction (even one that then downloads on the URLs it had) or the waiting loop's full fetches — holds every backlog admission for `rateLimitBackoff` (1 h) from that refusal, and a later one pushes the hold on (`Scheduler.holdForRateLimit`, `internal/worker/rate_limit.go`; a shorter hold never cuts a longer one short). A job holds it on the first refusal of a spell only: the ones it meets as it fetches again while it waits are the same limit seen by the same job, and letting each push the hour on before it ran out would let one video YouTube kept refusing hold every channel's backlog for as long as its job waited; a pass that answers ends the spell. A hold that ran out while no sweep reached the gate opens afresh, at Warn, on the next limit. The limit is the account's or the address's, not the video's, and the slot a refused backlog VOD frees would otherwise admit the channel's next one into the same wall.

  The heartbeat's sweep finds the hold run out; the close and the run-out are each logged once. The hold is read after the disk gate, which keeps its readings under it: a disk that fills during the hour closes the gate, and is recorded for the next process, when it fills. It outlives a restart: saved in `open-alerts.json` beside the disk gate's hold on every placement, extension and run-out (`rateLimitHeldUntil`; `Scheduler.RecordRateLimitHold`), it holds the next process until the same instant and runs out on its own then (`restoreRateLimitHold`, `cmd/moombox/rate_limit_hold.go`; `Scheduler.RestoreRateLimitHold`), while one that ran out before the restart restores nothing and is cleared from the file, and one more than the hour ahead — a clock set back — holds for the hour only. Kept in memory, a restart inside the hour reopened admission into the limit. The hold is YouTube's: a Twitch channel's backlog (the clips its `twitch_archive_clips` sweep queued) is admitted through it, from the channels `QueuedChannelsOnPlatform("twitch")` names, since Twitch refused nothing; live, upcoming and manually added jobs never pass through the scheduler and wait the limit out in `processJob`, or in their waiting loop (*A YouTube rate limit is not an error*, under Transition Rules)
- `Run` performs one admission sweep before entering its wait: the wake sites are all event-driven — backlog creation, job completion, a cookie repair — and a restart has none of them, so without it leftover `Queued` rows would wait for the 60 s heartbeat. The sweep is gated to the first pass of `Run`, so a `sweep()` that panics deterministically restarts on the heartbeat cadence rather than every second

### ProgressTracker

The `ProgressTracker` aggregates progress from video, audio, and chat downloaders and persists to the database:

- Update throttling: one report per `downloader.progress_interval_ms` (16ms by default), with gap rows flushed to the database at most once a second (the job row is written on every report). The TUI's own progress tick is finer — 8ms, one per frame at its 120 fps renderer — so the engine's gate, not the tick, is what bounds the rate
- Progress string format (`buildProgressString`, `internal/worker/progress.go`): `"(V: 1234/1300 A: 1234/1300 C: 900)"` for a DASH pair (segment / head per stream, the `/head` part only once it is known, chat messages last and only once there are some); `"Seq: 1234 C: 900"` for a single HLS stream; `"V:95.3% C: 900"` for a byte-ranged VOD. A YouTube VOD that completes writes `"V:100% A:100% C: 900"`, and one finalized behind head writes the DASH shape with its real counts instead (`incompleteProgressString`, `internal/worker/orchestrator.go`). While a download waits on something, the line is that wait instead (`activityMessage`, e.g. `"Verifying stream ended... (2m 10s)"`), a job waiting out a connectivity outage in `processJob` shows `"Waiting for network connectivity... (1m 20s)"` (`networkWaitLine`, rewritten every 10 s), and a YouTube download waiting out its player response's pre-roll ad before its first request shows `"Waiting out YouTube's pre-roll ad... (15s left)"` (`playbackWaitLine`, rewritten every 5 s; see Pre-Roll Ad Wait in platform-services.md). A VOD queueing for a download slot shows `"Waiting for a download slot... (3m)"` (`vodSlotWaitLine`, rewritten every minute with the whole minutes waited; its refresher stops before the clear is written). Every wait line is built by one constructor, `waitLine` (`jobstate.WaitLine`, `internal/jobstate/wait.go`), and so ends in the `"... (<time>)"` tail — the time elapsed, or the time left — which one predicate reads: `jobstate.IsWaitLine`, the TUI task list's test for a wait (`isWaitProgress`, `internal/tui/task_list.go`, which shows `⋯ wait` instead of a frozen percent) and the dashboard's (`isWaitLine`, `web/public/modules/utils.js`, which shows an Upcoming row's wait line in place of its last check). The download-slot line was the one without the tail. `TestEveryWaitLineCarriesTheMarker` pins every writer, and `TestWaitLineParity` (`cmd/moombox`) the dashboard's marker.
- Speed calculation: bytes/second averaged over a 5 s sliding window (`speedAvgWindow`); the earlier EMA over report-cadence deltas jittered with each segment's arrival
- ETA calculation (`calculateETA`): a segmented download divides the segments still to come by the segment rate since the tracker started. A whole-file VOD instead counts only the bytes THIS session transferred (`vodStreamBytes`) — each stream's forward movement from its offset at the session's first progress event, so a resume's inherited bytes are never read as speed — measured from that first event, against what video and audio together still have to fetch, each against its own probed total. Subtracting both streams' bytes, resume baseline included, from the video total alone and dividing by the tracker's age would show seconds where minutes remained on a resumed VOD. A stream opened by an event carrying its total goes on counting the streaming fallback's events, which carry none (`noteVodBytesLocked`): the chunked loop hands its transfer to that fallback on a mid-download 200, and reading only the chunked events would freeze the offset at the handoff while the clock ran on — the ETA climbing as the file neared completion, and the `V:` percent staying where the handoff left it (it is read off the total last stated). An offset below the last one — the fallback restarting the file — moves nothing.
- VOD progress: percentage-based (from chunked download byte position)
- Gap tracking: accumulates `DownloadGap` events from segment downloaders

## Concurrency Model

### Worker Concurrency

The download worker uses a goroutine-per-job model:

```
DownloadWorker.Start(ctx):
    for {
        jobID, jobCtx := queue.Dequeue(ctx)     // blocks until a job is pending
        go processJob(jobCtx, jobID)              // one goroutine per job
    }
```

Each `processJob` goroutine:
1. Has panic recovery (`defer func() { if r := recover() }()`)
2. Calls `queue.Complete(jobID)` on exit (deferred)
3. Tracks in-flight count via `sync.WaitGroup`
4. Is cancellable via the per-job context from `Dequeue()`

The `pollForJobs` goroutine runs a safety-net check every 60 seconds to catch any missed jobs. Normal job discovery is signal-driven via `EnqueueJob()` calls.

### Database Write Path

There is one job writer and it is synchronous. `UpdateJobFields()` (`internal/database/database.go`):
1. Builds the dynamic SET clause from the `fieldToColumn` map and executes the `UPDATE` immediately under `db.mu` (no channel, no batching goroutine, no coalescing window)
2. Re-reads the full job row through the prepared `stmtGetJob` in the same critical section (subscribers need all fields)
3. Releases `db.mu` BEFORE notifying, so a subscriber may call back into the database without deadlocking
4. Notifies `OnJobUpdate` and `OnJobChange` subscribers synchronously on the caller's goroutine; if the row vanished between the write and the read-back, fires `OnJobDeleted` instead

Its conditional forms, `UpdateJobFieldsIf`, `UpdateJobFieldsIfIn`, `UpdateJobFieldsUnless` and `UpdateJobFieldsUnlessTerminal` (`internal/database/database.go`), are the same writer with a status condition ANDed into the `UPDATE`: a write the condition refuses stops after step 1 and reports false (see [data-and-storage.md](data-and-storage.md), Conditional writes).

The only goroutine the package ever starts is the `OnJobsChange` fan-out (`dispatchJobsChange`), used by the two bulk writers. Write amplification during a download is bounded upstream, not here: `ProgressTracker` (`internal/worker/progress.go`) reports at most once per job per configured progress interval (`downloader.progress_interval_ms`, 16 ms default) and flushes gap rows at most once a second, and every other `UpdateJobFields` caller is event-driven. When nothing is being written, nothing runs.

### WebSocket Broadcast Rate

The WebSocket hub throttles nothing. The highest-frequency caller (`OnJobChange` driven by `ProgressTracker.maybeUpdate`, capped to one report per job per configured progress interval — `progressUpdateInterval` is its 16ms default, and `downloader.progress_interval_ms` overrides it per install) broadcasts the slim `job_progress` frame; `job_update` carries the state transitions, and `OnJobAdded`/`OnTrimsChanged` are event-driven. A previous per-job throttle in the hub created an ordering race where the trailing edge could arrive after a `BroadcastJobDeleted` and resurrect a deleted row via the client's upsert handler.

### TUI Async Updates

The TUI uses non-blocking channel sends to prevent the event loop from blocking:

- Job updates, log lines, and status changes are sent via buffered channels
- If a channel is full, the send is dropped and a drop counter is incremented
- Drop counters are logged periodically but are non-fatal
- Key timing intervals:
  - Main tick: 1 second
  - Progress tick (active download): 8ms (one per frame at the 120 fps renderer)
  - Progress tick (idle): 500ms
  - Marquee animation: 150ms
  - Log flush window: 250ms, ring buffer max 200 lines

### BotGuard Triple Cache

The PO token system uses three in-process cache layers to minimize expensive BotGuard operations. Caches are agnostic to which path (the sidecar, or goja when the sidecar is turned off) produced the token:

1. **Session cache (6h TTL):** Caches the complete PO token for a given content binding. Avoids both the sidecar IPC and the goja flow entirely on hits. Single source of truth for "is this token still fresh."
2. **Minter cache (dynamic TTL, single-minter design):** Caches the compiled BotGuard "minter" which can stamp multiple tokens. TTL comes from the BotGuard challenge response. Effectively unused under sidecar mode (the sidecar maintains its own internal minter cache inside the Node process). Populated only when the sidecar fails and the goja path generates a minter. CRIT-2 audit fix: ONE minter under `defaultMinterKey="default"` serves every binding for its TTL — the per-binding cache that pre-existed wasted a BotGuard run on every new content binding. FRESH-2 audit fix: a `time.AfterFunc` 5min before expiry proactively regenerates so user-facing calls don't pay the 2-10s BotGuard cost.
3. **Inflight dedup:** When multiple goroutines request a PO token simultaneously, the first one starts generation and all others wait on the same channel. Prevents thundering herd.

Each cache layer uses `time.AfterFunc` for automatic eviction on TTL expiry. The session cache key is the content binding string. The minter cache key is the challenge hash.

### Cipher 10-VM LRU

YouTube signature decryption requires executing JavaScript from `player.js`. This is expensive (multi-MB Goja VM):

- Maximum 10 VMs cached simultaneously (`solverCacheSize`; ~30-50 MB each, so ~500 MB worst case)
- Keyed by `player.js` URL (changes when YouTube deploys new player versions)
- Mutex-serialized compilation: only one goroutine compiles a given player.js at a time, others wait
- Extraction: full AST parsing of the JavaScript to find cipher functions, with regex fallback if AST fails
- VMs are evicted LRU when the cache is full

## Panic Recovery Patterns

Every goroutine in the codebase must have panic recovery. The patterns used vary by context:

**General goroutine pattern:**
```go
go func() {
    defer func() {
        if r := recover(); r != nil {
            logger.Error("panic in <context>", "panic", fmt.Sprint(r))
        }
    }()
    // ... work ...
}()
```

**HTTP middleware (`RecoveryMiddleware`):**
- Catches panics in HTTP handlers
- Returns HTTP 500 with a JSON error body
- Logs the panic with the stack that raised it (`panicStack` in `internal/web/server.go`): one `stack` field on the same line, innermost frame first from the frame that panicked, `function (file:line)` per frame, at most 32 frames and a count of the rest — no argument values, so nothing from the request beyond the method, path, peer and request ID the line already carries
- The WebSocket upgrade never reaches it (`interceptUpgrades` takes it ahead of the router); `HandleUpgrade`'s own recover logs the same `stack` field
- Neither do chi's `RequestID`, `DrainMiddleware` or `interceptUpgrades`' own gates, which run ahead of it; `outermostRecovery`, the server's outermost handler (`serverHandler` in `internal/web/server.go`), logs a panic there with the same `stack` field and answers 500 when nothing was written (re-panicking `http.ErrAbortHandler` when something was) — the server's `ErrorLog` is discarded, so `net/http`'s own recover would log it nowhere

**Database subscriber callbacks:**
- `safeCallJobUpdate(fn, job)` wraps each `OnJobUpdate` subscriber call
- `safeCallJobsChange(fn, jobs)` wraps each `OnJobsChange` subscriber call
- A panic in one subscriber does not prevent other subscribers from being notified

**Monitor callbacks:**
- `OnVideoFound` and `OnStreamFound` callbacks in `main.go` are wrapped with `defer func() { if r := recover() }()`
- Prevents a bug in job creation from crashing the monitor's polling goroutine

**Background mux goroutines:**
- Quality- and gap-split segment muxing runs under the orchestrator's mux root, not `context.Background()`
- Each has its own panic recovery
- The root outlives the JOB's context, so a user cancel never orphans a half-written output; but `Stop` cancels the root itself (`CancelMuxes` in `internal/worker/quality_split_common.go`) once its 10-second wait for in-flight jobs runs out, so a shutdown ends FFmpeg in order rather than exiting from under it. A mux cancelled that way leaves its row `Muxing` with staging intact, and the next start re-muxes it
- What a crash leaves does not depend on that cancel (W28-A01). Every FFmpeg and ffprobe the child starts dies with it (`CommandContext`, `internal/childproc/childproc.go`): before, a child that died mid-mux (an OOM kill, a fatal runtime error, a kill of the child alone) left its FFmpeg running — on Linux nothing tied it to the child, and on Windows the kill-on-close job it lived in was the LAUNCHER's — and the crash-respawned child's boot re-mux (`enqueueExistingJobs` → `muxOnRestart` → `MuxJob`) wrote the same archive beside it with `-y`, which read as `Finished` and played as garbage while the staging cleanup deleted the only good copy. And no FFmpeg writes an archive's name any more: each output is written to a temporary name of its run's own beside it and renamed into place only after FFmpeg exits 0 and the archive's checks pass (`writeOutput`, `internal/engine/muxer_output.go`), and the next start removes what a crash left (`RemoveStaleMuxTemps`, `internal/worker/mux_temps.go`). [operations.md](operations.md) § Runtime Dependency: FFmpeg has both halves

**Download worker:**
- Each `processJob` goroutine has panic recovery
- On panic: sets job status to `Error` with message `"internal panic: <details>"` — unless the job already reached an outcome during the run (`UpdateJobFieldsUnlessTerminal`): an operator's Cancel that landed while it ran, or a finish or failure before the panic, stands. So does an outcome that is not terminal, which the run recorded and settled before it panicked (`JobQueue.settleRun`): a `COOKIES?` park, a backlog requeue to `Queued`, the `Upcoming` a successful automatic cookie refresh resumed the park to, the row a shutdown leaves to resume on restart. Guarded by the terminal statuses alone, a panic in a failure's tail — its notification, the automatic cookie refresh that can hold it for minutes — turned the park into `"internal panic"`, which only a manual Retry undid
- The panic is recorded by `processJob` itself (`recordRunPanic`, `internal/worker/worker.go`), in a recover deferred so it runs ahead of the run's `queue.Complete`, with the goroutine's own recover behind it for a panic in that record. Complete drops the run's user-cancel flag, so a recover that recorded the panic alone would find nothing left to say a Cancel had flagged the run, and the Job Cancelled the cancel route had left to it would never be sent. The record settles the run as `setJobError` settles a failure (`JobQueue.settle`): a run a Cancel flagged first ends as a cancelled one through `handleCancellation` and sends that Job Cancelled — unless its own `Finished` landed over the Cancel, which stands as above — and a Cancel after the record is its caller's to report. A flagged run whose row the operator has deleted since ends the same way, as `setJobError` ends one: the delete route removes a `Cancelled` row at once, waiting on no run, and a record that ended a flagged run cancelled only on a row still present sent nothing for it
- The off-queue mux (`MuxJob`, `internal/worker/worker.go`: the Mux action, the boot re-mux of an interrupted `Muxing` row, and the automatic mux of an ended Twitch broadcast) recovers the same way: its `Muxing` write comes before its goroutine, so a `Finished` written before a panic in the mux's tail (the notification, the staging cleanup), or an operator's Cancel that landed on the `Muxing` row, stands rather than turning into `Error`. So does an outcome the finalize's own `Muxing` write finds on the row (`ErrCancelled` from `muxFromStaging`): `MuxJob` writes nothing over it, muxes nothing from it (the refusal comes ahead of `muxFromStaging`'s part recovery) and keeps staging, rather than read the refusal as a failure and write `Error`. It refuses with `ErrNotAllowed`, writing nothing, a row that is not one the Mux action is offered on (`Muxing` only for the boot re-mux; see Verb Preconditions). It refuses with `ErrStagingBusy`, writing nothing, while the job's last run is still registered: the cancel route writes `Cancelled` before the run has stopped, so a Mux clicked while a cancelled capture waited out its part muxes and its chat's shutdown grace wrote `Finished` and reclaimed staging, and the run's end then wrote `Cancelled` over the archive. Retry, Resume and Reinitialize wait for that exit (`afterJobExit`); the automatic mux runs after it

## Job Status Lifecycle

```
Queued (backlog VODs only)
    |  admitted by the archive-slots scheduler
    v
Upcoming -----> Live ------> Downloading ------> Muxing ------> Finished
    |              |              |                  |
    |              |              |                  |
    v              v              v                  v
  Error          Error          Error              Error
  Cancelled      Cancelled      Cancelled          Cancelled
  COOKIES?                      COOKIES?
                                   |
                                   +--(cookie repair, priority 0)--------> Upcoming
                                   +--(cookie repair, backlog, priority 1)-> Queued
```

### Status Definitions

| Status | Type | Meaning |
|--------|------|---------|
| `Queued` | `"Queued"` | Backlog VOD resting state: waiting for one of the channel's `archive_slots`. Only the scheduler moves it forward — `ShouldProcess` is false, so startup recovery and the heartbeat poller skip it. |
| `Upcoming` | `"Upcoming"` | Stream is scheduled but not yet live. StreamProcessor is polling. |
| `Live` | `"Live"` | Stream is confirmed live. About to download or actively downloading. |
| `Downloading` | `"Downloading"` | Actively downloading segments. |
| `Muxing` | `"Muxing"` | Download complete, FFmpeg is combining tracks. |
| `Finished` | `"Finished"` | Terminal. Output file is ready. |
| `Error` | `"Error"` | Terminal. Something went wrong. Error message in `error` field. |
| `Cancelled` | `"Cancelled"` | Terminal. User explicitly cancelled. |
| `COOKIES?` | `"COOKIES?"` | Terminal (but retriable). Authentication required -- cookies expired or members-only. The `park_reason` column records which, and gates automatic resume (see below). |

### Transition Rules

- `Queued` -> `Upcoming`: Scheduler admitted the backlog VOD into one of its channel's `archive_slots` (backlog jobs only — broadcasts and newly discovered VODs are created directly as `Upcoming`/`Live`)
- `Upcoming` -> `Live`: Stream went live (detected by probe)
- `Upcoming` -> `Downloading`: Stream is a VOD or non-stream allowed for download
- `Live` -> `Downloading`: Download slot acquired, segments being fetched
- `Downloading` -> `Muxing`: All segments downloaded, FFmpeg muxing started
- `Muxing` -> `Finished`: Mux complete, output file written
- Any -> `Error`: Unrecoverable error at any stage
- **An outage is not an error.** `processJob` runs stream processing through `processStreamThroughOutages` (`internal/worker/outage_wait.go`): a fetch that fails on the outage waits for the network — the row keeps its status, its progress line reads `Waiting for network connectivity... (<elapsed>)` — and stream processing runs again from the top once the connectivity monitor (the worker's `Connectivity`) reports online. The wait follows a failed fetch, never the monitor's word alone, and gives the fetch another try every `networkWaitFloor` (60 s, the waiting loops' `offlineProbeFloor`) while the monitor still reports offline: the monitor can say offline with the network up — its probe dials only `probe_targets`, which a firewall can block, and nothing the platforms answer brings it back — and stream processing held before its first fetch on that word stranded every job `processJob` ran, an interrupted live capture among them, with nothing ever fetched. A fetch made during a real outage fails at once, so only one the network can answer goes ahead.

  "On the outage" is `outageCalled`: a transport failure (`probeVote`'s "down" verdict — a dial, DNS or TLS failure, a deadline with no answer, a connection cut mid-response) met while the monitor reports offline, or one the monitor goes on to call an outage within `outageConfirmWindow` (30 s; the monitor needs two failed 5 s polls). An answer from the service is a verdict whatever the monitor says, and a transport failure the monitor never calls is the platform's failure on a network that is up — both are recorded.

  The stale-VOD re-extraction takes the same rule with its slots held (`refreshStaleVodInfoThroughOutages`); so does a YouTube download's setup (`errDownloadSetup`, `waitOutSetupOutage`), whose first fetch — the HLS master playlist, or the DASH manifest of a live stream without manifest-free formats or of a VOD that still carries one — is made outside the engine's own outage waits: the failed attempt gives its slots back and stops any waiting-room chat it inherited, the row keeps the `Downloading` `ExecuteWithChat` wrote, and once the network is back the job runs again from stream processing, which says afresh what the manifest URLs are and whether the broadcast is still live (rather than ending in Error, with the monitor reporting offline, when the outage began between stream processing and the download — at go-live, or on a network that flaps as it comes back); and a Twitch VOD fetch that never reached Twitch, or that a cancelled run cut short, comes back to `processJob` as an error rather than a verdict so that it can (`twitchVodFetchError`).

  A wait that a shutdown ends, or after which the row is gone or no longer processable, is a cancelled run (`handleCancellation`), so the row resumes on the next start. Ending it in Error would lose every row on an offline boot — the PC back before the router — which re-enqueues every `Upcoming`, `Live` and `Downloading` row: each first fetch would fail with the outage's dial error, and nothing would bring the rows back
- **A YouTube rate limit is not an error.** A playability refusal of the session rather than of the video — a reason saying "try again later" (yt-dlp's "This content isn't available, try again later", the account or session rate-limited for up to an hour) or a captcha challenge, `youtube.PlayabilityRateLimited`, on an extraction with no formats — reaches `processJob` marked `ErrRateLimited`, and an Innertube 429 on every client of the cascade (`youtube.HTTPRateLimitError`), the HTTP form of the same limit, reaches it as the error; either, from stream processing or from a stale VOD's re-extraction whose URLs have expired (one whose URLs are still good downloads on them, as after a blip), goes to `outlastRateLimit` (`internal/worker/rate_limit.go`) instead of `setJobError` or the transient requeue, whose three retries span 35 minutes of an hour-long limit (`isRateLimited`). Upstream words the refusal and ends the extraction — unless `--wait-for-video` is given, when it warns of it and extracts again on the user's flat interval, with no bound (`raise_no_formats`, `YoutubeDL._wait_for_video`); an archiver is the one that runs it again, so here every job waits it out, as if that flag were always given — the captcha with the rate limit, by the plan's choice, which upstream words in the same refusal and treats alike.

  The limit first holds every backlog admission for `rateLimitBackoff` (1 h, `Scheduler.holdForRateLimit`; see Backlog Scheduler), on the first refusal of the job's spell. A backlog VOD then goes back to `Queued`, held for the same hour, outside `backlogRetryLimit` — its streak neither counts the requeue nor ends with it, so three retries do not end a backlog VOD in Error; only the rate-limit cap below does (`requeueBacklogAfterRateLimit`, `internal/worker/backlog_retry.go`). Any other job — a broadcast, a newly published video, a manual add — gives back its slots, keeps its row's status under the progress line `Rate-limited by YouTube; fetching again... (<left> left)`, and runs again from stream processing every `rateLimitRetryInterval` (30 min, the waiting loop's own full-fetch cadence) — or after the `Retry-After` a 429 named, where that is longer, up to the hour — until YouTube answers; a cancel or a shutdown ends the wait as a cancelled run, and so does a row that left the states the queue processes while it waited.

  A broadcast already in its waiting loop never comes back here: it stays in the loop, its chat running, and confirms its go-live again on a taper of its own (step 7 of `StreamProcessor`). Ending either in Error would drain a backlog into Error one admission after another while the limit lasted, and lose a broadcast whose first fetch was refused before it aired, since the feed monitor never re-creates a video it has a job for. The waiting loop never gives up on the verdict as a refusal of the video (`isTerminalPlayability`). Waiting is bounded, though, beyond upstream too (owner decision on W5): a spell of refusals that has lasted `rateLimitCap` (24 h) and held at least `rateLimitCapRefusals` (3) refused attempts ends the job in Error with the refusal as yt-dlp words it, saying it gave up (`rateLimitGaveUp`) — 24 hourly requeues of a backlog VOD, 48 half-hourly tries in place, or a day of a waiting loop's counted refusals, which count only once the stream has begun.

  The same exemption holds on every path (owner decision PR-R4): a job waiting in place counts no refusal while its row is still Upcoming (and is neither a backlog VOD, whose admission writes Upcoming, nor known to be a VOD) or its scheduled start is still ahead (`rateLimitCountsFor`), so a broadcast scheduled more than a day out whose first fetch is refused waits until it airs instead of ending in Error; a refused fetch never moves the row, so one still Upcoming stays exempt past its scheduled start, for as long as YouTube refuses it. The refusal floor (owner decision on FA) keeps a day that saw only one or two looks — a backlog VOD re-admitted a day after its first refusal — from ending the job. The day is the wall clock's from the spell's first refusal (`rateLimitSpells`, which a backlog VOD's runs share), so a `Retry-After` that lengthens the waits or a re-admission that comes late does not stretch it. A pass whose fetch YouTube answers ends the spell (`noteAnswered`), as do a run that ends other than back in `Queued` and the operator's Cancel, Retry and Resume (`forgetBacklogRetries`, `endBacklogStreak`) — a dashboard Retry starts the day over; a transient failure, which is no answer, leaves it.

  The spells live in memory, as the retry counts do, so a restart starts each one over. The Error is written through `setJobError`, never over an operator's Cancel. A captcha (`errCaptchaRequired`, an `ErrRateLimited` that says so) is waited out the same way, under the same cap, but under its own line, `YouTube asks for a captcha... (<left> left)` (`captchaWaitLine`), and it opens the session's captcha spell (`captchaAlert`), which sends the operator one `captcha_required` however many jobs it refuses, so they know to solve it in a browser signed in with the same account; any fetch YouTube answers with no rate-limit verdict ends the spell, which sends one `YouTube Captcha Cleared` on the same `captcha_required` event, so it reaches the same targets (owner decision on FA), and the next captcha tells them again — read at the fetch, stream processing's (`Process`), the waiting loop's or a stale VOD's re-extraction's, whatever the job then does with the answer: read where a pass went on to download, a private or members-only answer, or a broadcast's that went on to its waiting loop, left the spell open, and the captcha that came back after it told no one. The spell lives in memory: a restart that meets the captcha again tells them again
- `Error` -> `Upcoming` (Twitch): the Twitch monitor re-initialises (`AutoReinitializeJob`) a monitor-created live job that failed before any segment was downloaded, within `MaxTwitchAutoRetries`, when it finds the same broadcast live again (`jobstate.TwitchAutoRetryPending`, `internal/jobstate/auto.go` — the one predicate, which `setJobError` also asks of the row it writes to decide whether the failure is worth a Job Failed embed) — for two failures: the offline flap (`TwitchOfflineErrMsg`), and stream processing that never reached Twitch on a network the monitor said was up, which `setJobError` marks `park_reason = 'twitch_unreachable'` (`ParkReasonTwitchUnreachable`, from the error's type, `twitchUnreachableError`). Its error text is the transport failure's own, which the exact-string match does not take, so the rest of the still-live broadcast (Twitch has no DVR) would otherwise be lost
- Any -> `Cancelled`: User-initiated cancellation
- `Upcoming` / `Downloading` -> `COOKIES?`: Auth failure detected (login required, members-only, cookies expired) — before any download too: the playability check that classifies a stream, its credential half re-read on the go-live fetch when that fetch serves no formats (`completeStreamTransition`, `internal/worker/stream_processor_youtube.go` — so a members-only job whose cookies died during the wait does not reach "no download strategy available", a plain Error), and a members-only answer while waiting for it to go live, park an `Upcoming` row. Mid-capture, a live YouTube refresh whose player response is credential-walled with no formats (`liveCredentialFailure`, `internal/worker/orchestrator_youtube.go` — the quality-loss refresh, a part split's refresh and the stream-end verify's refresh) stops the capture with staging kept and parks the `Downloading` row the same way — once the wall has been read twice in a row (one re-read, on the retry cadence, before it is believed: a single walled answer to a healthy session would park a live capture for good, and a membership park waits for an account change nothing will make) rather than retried and then finished like an ended stream. A private verdict goes to `Error`, since no sign-in repairs a session the owner has not shared the video with, unless the request sent the jar's auth cookies and YouTube answered it as signed out (`VideoInfo.SessionCredentialed` and `SessionAuth`, `playabilityVerdict`): an account granted access whose cookies have lapsed is refused in the same words, so that one parks like any credential failure, with its alert, refresh and sweep, and a message saying the cookies look dead. That holds at `Process` and a queued VOD's re-extraction, in the waiting loop's full fetches and at go-live with no formats, and mid-capture on a refresh's response that still states a live stream with no formats, read twice as above; a mid-capture response that states no broadcast is read as the stream's end, as a sign-in wall is. A session that reads signed in or unknown keeps the `Error`, and so does an install with no auth cookies, because public pages read signed out too. What YouTube sends a dead session for a private video has not been captured
- `COOKIES?` -> `Upcoming` (priority 0, or no channel) / `COOKIES?` -> `Queued` (priority 1, backlog): a credential-recovery sweep resumed the job. A backlog row returns to `Queued` rather than `Upcoming` so the archive-slots scheduler re-admits it `archive_slots` at a time instead of releasing a channel's whole parked backlog at once. A parked backlog job of a REMOVED channel returns to `Queued` too: its `feed_items` partner is gone — the departure prune deletes the channel's feed history, and removing a channel keeps its jobs by default — but `NextQueuedJobs` LEFT-JOINs `feed_items`, so the scheduler still admits it, under the global `archive_slots`. Returning it to `Upcoming` would leave a partnerless `Queued` row an INNER JOIN drops with no exit (`/retry` and `/resume` both refuse `Queued`). Every resume — both sweeps (`resumeCookieParkedJobs`, `cmd/moombox/monitor_callbacks.go`) and the worker's own after an automatic cookie refresh succeeds (`attemptCookieRefresh`) — is a compare-and-set on `COOKIES?` (`UpdateJobFieldsIf`): both UIs offer Cancel on a parked row, and the refresh holds the parked run's tail for up to two minutes, so a resume written unconditionally turned the operator's `Cancelled` back into a download. The worker's resume still hands on a row a sweep resumed first — the refresh's own re-check sets the sweeps off before it returns — so it restarts when the parked run exits rather than on the heartbeat. Two sweeps exist and they are not interchangeable:
  - **Auth recovered** (`RefreshService.OnAuthRecovered`) fires when a platform goes from not-authenticated to authenticated, and offers the sweep no account identity. It resumes every park EXCEPT `park_reason = 'membership'`.
  - **Credential observation** (`RefreshService.OnCredentialsChanged`, both platforms — only YouTube can park a job on an account question) hands the sweep the account identity currently in the cookie file. A membership park then resumes if and only if that identity differs from the `park_identity` it recorded when it was refused.
  A membership park is excluded from the first sweep because it happened while the session was ALREADY authenticated, so that transition cannot be the event that fixes it -- resuming there bought a guaranteed-identical failure once per auth cycle. Only a different account can help.
- **Account identity** is `SHA-256(SAPISID || NUL || LOGIN_INFO)` (`cookies.CookieJar.YouTubeIdentity`). `LOGIN_INFO` is the load-bearing half: SAPISID identifies a Google *session*, not an account, which is why `internal/youtube/auth.go` must select the account separately via `X-Goog-AuthUser`/`X-Goog-PageId`. Switching the browser's active account -- the exact remedy Moombox prints for a not-a-member failure -- rewrites `LOGIN_INFO` and leaves SAPISID untouched, so a SAPISID-only fingerprint would be blind to it.
- **The resume decision is durable, not edge-triggered.** The per-job `park_identity` comparison is what moves a job; the observation callback only decides *when* to look. A missed observation therefore costs a delay until the next account change or restart, never a permanent strand. Its process-local baseline advances only on a check that both concluded AND authenticated -- otherwise a stale intermediate export (dead on arrival, then re-exported working) would consume the edge -- and its zero value fires once per process, which is how an offline swap (stop, replace cookies, start) is noticed at all.

### Verb Preconditions

Which statuses each verb is offered and accepted on is one Go predicate per verb in `internal/jobverbs` (`jobverbs.go`): `Cancellable`, `ResumableStatus` (with `ResumeSupported` for the platform), `ReinitializableStatus`, `MuxableStatus` (with `MuxNeedsUnmuxedParts` for a Finished row), `DeletableStatus`, `WatchableStatus`, `TrimmableStatus` and `ChapterImportableStatus`. A leaf package, so the REST routes, the TUI's menu filters and batch loops (which do not import `internal/worker`), `ListJob`'s staging flag and the worker verbs call the same functions; Resume and Reinitialize stay two predicates though their sets coincide today. Status only: the disk facts a verb also needs (`HasStagingFiles`, `HasSegmentFiles`, `HasUnmuxedParts`) are probed separately, where a verb is chosen (CORE-9). The dashboard's sets in `web/public/modules/utils.js` mirror them, and `cmd/moombox`'s `TestVerbStatusSetsMatchTheDashboard` compares the two over every declared `JobStatus`. The Watched, Trim and Resume-platform gates read their sets too (`WATCHED_STATUSES`, `TRIM_STATUSES`, `RESUME_PLATFORMS`), pinned by `TestDashboardVerbArmsReadTheirSets`. The delete paths cancel first exactly when `worker.IsActiveJobStatus` holds.

The worker verbs enforce their predicate themselves, on the row as it reads when the verb is accepted (`afterJobExit`'s gate; `muxJob`): the TUI calls them on the row it last drew, and a route on the row it read a moment before. A refusal is a `*worker.NotAllowedError` (`worker.ErrNotAllowed`, `internal/worker/verbs.go`), "Job cannot be <verb> in current state (<status>)" — `409` over REST, the same text in red in the TUI.

And a transition decided on an earlier read is written conditionally, with what cannot be undone after it:
- **Reinitialize and auto-reinitialize** write their reset (one map, `reinitResetFields`; only `auto_retry_count` differs) with `UpdateJobFieldsIf` on the accepted status FIRST, and delete the staging, the parts and an imported chapter list only once it applied (`reinitializeNow`, `autoReinitializeNow`). A Cancel landing between the verb's last read and its write keeps the staging as well as the row. While the verb still holds the job's staging claim, `EnqueueJob` skips the job (the claim's release wakes the heartbeat), so a monitor cannot start a run on the reset `Upcoming` row while its staging is deleted; the verb queues the job itself (`enqueueHeld`).
- **Mux** writes `Muxing` with `UpdateJobFieldsIfIn` over `jobverbs.MuxableStatuses` — plus `Muxing` for the boot's re-mux of an interrupted row, which its caller says (`muxJob`'s `bootRemux`, also what decides `JobContext.CapturedMux`) rather than one read off the row — so a Mux decided on a row a Resume or a Reinitialize moved on since is refused, not written over it. `Finished` stays in that set only when `muxJob`'s own read finds the row Finished with a part its finalize could not mux (`jobverbs.MuxNeedsUnmuxedParts`, `HasUnmuxedParts`) — the check the route and the TUI make on their earlier read — so a stale caller cannot re-finalize a complete archive. A row gone by then answers `ErrJobNotFound` (the mux route's 404), not `ErrNotAllowed`. Its failure writes are `UpdateJobFieldsIf(..., Muxing, ...)`.
- **The automatic Twitch mux**'s failure write is `UpdateJobFieldsIf(..., Error, ...)`: a Reinitialize landing after its re-read, whose reset deleted the staging the mux then found empty, keeps its `Upcoming`.


### Derived Sub-States

A sub-state that changes what the operator should do is derived from the row and memory, never persisted, and shown in both UIs. `internal/jobstate` holds each derivation once — a leaf package (it imports only `database`), so the worker, the routes and `internal/tui` (which does not import the worker) call the same functions — and the dashboard's twins in `web/public/modules/utils.js` run against one shared table, `web/tests/fixtures/job-state-parity.json`, from both sides (`cmd/moombox/job_state_parity_test.go`, `web/tests/job-substates.test.mjs`).

- **Pending automatic action** (owner ruling R-D2, `internal/jobstate/auto.go`). `TwitchAutoRetryPending` is the one Twitch recovery predicate: the monitor's re-initialisation (`processStreamInfo`), its VOD backlog (`capturedLiveJob`) and `setJobError`'s notification suppression, which asks it of a copy of the job carrying the status, error and park reason it writes. It replaced two copies kept in sync by comment; the end-unconfirmed exclusion only the monitor's had changes no reachable `setJobError` answer (the latch keeps its cause's text), pinned by `TestBothRecoveryCallersKeepTheirAnswers`. `PendingAutoAction` answers `auto_mux` for a Twitch Error row the unconfirmed-end latch marked (`AutoMuxPending`, the automatic mux's own precondition) and `auto_retry` for one `TwitchAutoRetryPending` accepts that the recovery can reach — not a `ManuallyAdded` row, which writes no history row and so is never found `HasProcessed` (its end latch is still the mux's). A row cannot tell whether its channel is still monitored, so the sentence both UIs show states that condition ("Muxes automatically once Twitch confirms the broadcast over, while the channel is monitored"). It is the additive `pendingAutoAction` of `GET /api/jobs/{id}`; the TUI shows a dim `⟳ mux` / `⟳ retry` row tag and an "Automatic" details section, the dashboard an `Auto-mux pending` tag before the row's error and a line in the job dialog. `ReinitializePreview` counts `pendingAutoMux` / `pendingAutoRetry`, so both Reinitialize confirms lead with "cancels the pending automatic mux, and deletes …" — for a mux, the reset deletes the staging it would have archived. The warning leads, and the TUI's A I line puts the clause ahead of the job's title, because that line is one row cut to the terminal's width.
- **Wait lines** (owner ruling R-D1): `jobstate.WaitLine` / `IsWaitLine` (see ProgressTracker). The dashboard's Upcoming row shows its wait line while one is up, "Awaiting processing" for a VOD (`isVod`) or an admitted backlog row (`queuePriority` 1 with a `channelId`), and otherwise "Last check" — Twitch's "Waiting for stream..." carries no marker and keeps it. The awaiting rule is `jobstate.AwaitingProcessing` (`internal/jobstate/awaiting.go`), the dashboard's `isAwaitingProcessing` its twin over the shared table's `awaitingProcessing` cases; no writer stores the text. The TUI's details pane says "Progress: Awaiting processing" for such an Upcoming row with no wait line up; an Upcoming row has no row tag for a wait in either form. A wait line found on an Upcoming row at boot (`enqueueExistingJobs`) is cleared: its writer's deferred clear died with the process, and YouTube's waitForLive writes no progress to replace it. A Live or Downloading row keeps its line — its run writes its own progress — and reads as the last thing it did until then. A cell showing a wait line is never stamped for the relative-time refresher (`upcomingShowsLastCheck`, `web/public/app.js`).
- **Admission holds** (owner ruling R-D3, `internal/jobstate/holds.go`). `Scheduler.Holds` is a read-only snapshot of what the admission sweep tests — offline, the disk gate (`diskHeld`, an `atomic.Bool` so any goroutine reads it), the YouTube rate-limit hold with its run-out time, each row's own backoff with the retry attempt that hold was placed for (0 for a rate-limit requeue, which the streak neither counts nor resets, so such a row reads as rate-limited whatever its streak) — and `DownloadWorker.BacklogRetryState` / `AdmissionHolds` add the retry budget. `jobstate.HoldPrecedence` (offline, disk, rate limit, retry) is the sweep's early-return order, written once; `AdmissionHolds.For` picks a Queued row's reason by it, Twitch rows passing through the rate limit as the sweep admits them. The snapshot is the additive `admissionHolds` of `GET /api/status` and `initial_state`, and every change the scheduler signals (`holdsChanged`, capacity one) is pushed by `runAdmissionHoldsPush` (`cmd/moombox`) as an `admission_holds` frame and to the TUI. Queued rows read "Held: offline", "Held: disk full", "Held: YouTube rate limit until 14:05", "Retry 2 of 3 at 14:10" or "Waiting in queue...", and while the disk gate holds below critical the dashboard's gauge and indicator, and the TUI's disk reading, say "holding".
- **Cookie badge precedence** (owner ruling R-D4): see the cookie badge in user-interfaces.md.
### Cancellation Semantics

- **User cancellation:** `WasCancelled(jobID)` returns true. Status set to `Cancelled`. Notification sent.
- **Shutdown cancellation:** `WasCancelled(jobID)` returns false. Status is preserved (not changed). Job will resume on next startup. Neither orchestrator writes `Muxing` on its way out of a stopped capture: that status is for a recording whose download is over, and the restart re-muxes a `Muxing` row from staging rather than resuming it (`muxOnRestart`).
- **Cancel of a settled run:** a run that has recorded its outcome — `setJobError`'s failure, a backlog requeue, a panic, or the end of a cancelled or interrupted run — is settled (`JobQueue.settle`), and a Cancel that reaches it in what is left of the run is not flagged: `CancelJob` answers false and its caller (the cancel route, the TUI) sends the notification. That covers a Cancel of a `COOKIES?` row whose run is still in its automatic cookie refresh, of a row just requeued to `Queued`, and `CancelJob`'s own order — it writes `Cancelled` before it flags the run, and that write alone can end the run first.
- **Cancel of an ended job:** a Cancel is decided on a status read earlier — the row a UI showed, the cancel route's own read — and `CancelJob` writes `Cancelled` with `UpdateJobFieldsIfIn` over the cancellable statuses (`jobverbs.CancellableStatuses`, `internal/jobverbs/jobverbs.go`; `internal/database/database.go`), never over `Finished`, `Error` or `Cancelled`. Written unconditionally, it turned a job that finished or failed in between into a Cancelled one. A Cancel that finds the job ended does nothing else either — no flag, no stopped run — and answers that nothing was cancelled, which both entry points report: the cancel route with a 409 naming the status the job reached (`cancelJob`, `internal/web/routes/jobs.go`), the TUI's `A X` with a warning that the job had already ended (`cancelJobFromTUI`, `cmd/moombox/job_notifications.go`); neither sends Job Cancelled for it.

- **Cancel of a job already finishing** (owner ruling R-C1): once a finalize has written its archive — after `copyStaged` in the single-file shape, after the parts and the asides in the split one — it marks itself finishing (`beginFinishing`, `internal/worker/worker.go`, through the orchestrator's `finishing` hook), under `finishMu` with a read of the row. `CancelJob` checks the mark under the same lock: a Cancel that reaches a finishing job writes nothing, flags nothing, and answers `worker.ErrAlreadyFinishing` — the cancel route's `409` "Not cancelled — the job is already finishing: its archive is written", the same text in red on the TUI's feedback line — and the job ends `Finished` with its "Download Finished". A Cancel that lands while FFmpeg is still writing, or while the finished copy is being checked against the staged inputs, stops it and stands: the copy returns its error, nothing is recorded, staging is kept. A Cancel that lands in the instants between FFmpeg's successful return and the mark has already been applied and answered, and there **Finished wins** (owner ruling R-H2): the mux completed, so the mark re-claims the row — `Cancelled` back to `Muxing`, with `UpdateJobFieldsIf` on its still reading `Cancelled` — and the finalize records the archive as any other does, once, on the mux root rather than the context the Cancel ended; both UIs get the ordinary job update and one Info line names the superseded Cancel. Before the ruling that row stayed `Cancelled` and the complete archive sat at the output path on no row. "Completed" means checked: the output check (`verifiedCopy`, `internal/worker/orchestrator_mux.go`) runs its probes on the finalize's context, and a copy whose context ended under it fails rather than pass unread, so the window opens only once the copy has been compared with what was staged and renamed into place — a re-claimed finish deletes its staging like any other. The finalize records the re-claim on its `JobContext` (`FinishReclaimed`), and the post-download trim the job asked for then runs on the mux root too (`trimAfterFinalize`, `internal/worker/orchestrator.go`). One terminal notification is sent either way: a Cancel applied while an off-queue mux runs (the Mux action, a boot re-mux, the automatic Twitch mux — runs the queue does not know) is flagged as that run's to announce (`noteMuxRunCancel`), and the run sends "Job Cancelled" at its exit only if the row still reads `Cancelled` (`endMuxRun`); a superseded one is followed by "Download Finished" alone. The split shape's mux work (the same-format merge, the set-aside recovery) swallows its failures, so it tells a Cancel that stopped it from one that came after by the context it ran on, read as the work returns: cancelled, the Cancel stands and the parts stay on their segment rows. The mark is taken only on a row the finalize itself could hold (`Muxing`; `Live` or `Downloading` when its own Muxing write failed on the database): any other row — another outcome, a reset verb's `Upcoming`, the row gone — stops the finalize with `ErrCancelled`, nothing written over it, and what it wrote left where it is, named in a Warn line. A Twitch connectivity-outage finalize, whose mux runs under the mux root rather than the job's context, is stopped by a Cancel the same way: its mux context is a child of the root that the run's Cancel listener also cancels (`cancelOnUserCancel`, `internal/worker/orchestrator_twitch.go`), so FFmpeg stops, nothing is written, staging is kept and Cancelled stands; on the bare root FFmpeg ran on and left a finished archive on no row. Written over, the archive's Finished used to land on a Cancel the route had already answered with success, and a "Download Finished" followed the "Job Cancelled".

This distinction is critical: on shutdown, jobs in `Downloading` status keep that status so they are re-enqueued on restart. User cancellations are permanent.

### Terminal Status Check

```go
func isTerminalStatus(status database.JobStatus) bool {
    switch status {
    case database.StatusFinished, database.StatusError,
         database.StatusCancelled:
        return true
    default:
        return false
    }
}
```

Note: `Muxing` is **not** terminal. If muxing was interrupted by shutdown (the
muxer process was killed mid-encode), `enqueueExistingJobs` in
`internal/worker/worker.go` re-muxes the job from what is already staged —
`MuxJob` hands it to the Mux action's own path, `muxFromStaging` in
`internal/worker/orchestrator_mux.go`, under the same download slot a queued
job takes, and reclaims staging once the archive file exists. Two rows are the
exception and still reset to `Downloading`: one whose staging holds nothing
muxable, and one flagged `incomplete_tail`, whose recording is known to be
short and still needs the post-live VOD-refresh loop that only the download
path runs.

Muxing is NOT idempotent against the recording itself, which is what the previous reset assumed: re-processing re-probed the stream as post-live, the manifest-free strategy seeded sequence 0, and the engine truncated the complete staged file. The engine refuses that outright — `ErrStagedMediaPresent` in `internal/engine/downloader.go` — so no path truncates non-empty staged media unless the caller explicitly asked to discard it, and the one caller that does (the manifest-free restart's `DiscardStaged`) preserves the recording aside instead. A whole-file VOD download (`IsDirectURL`) is outside the guard by design: its partial is re-fetchable from the same static URL, so a restart costs bandwidth, not footage.

## Error Classification

There is no typed error hierarchy and no errors package under `internal/`. Errors are plain Go errors, wrapped with `fmt.Errorf("...: %w", err)` as they travel up, and the only classification anywhere is sentinel matching with `errors.Is`. The sentinels that matter to a job's fate:

| Sentinel | Declared in | Meaning |
|----------|-------------|---------|
| `ErrCookiesRequired` | `internal/worker/worker.go` | Player-API "login required" / "member-only" failure, or any explicit cookies-needed signal |
| `ErrNotAMember` | `internal/worker/worker.go` | Members-only content refused to a session YouTube confirmed was SIGNED IN — a membership problem, not a credential one |
| `ErrNonActionable` | `internal/worker/worker.go` | Nothing the user can do: age-restricted content, exhausted probe budgets |
| `ErrRateLimited` | `internal/worker/worker.go` | A YouTube refusal of the session rather than of the video (`rate_limited`: "try again later", a captcha), on an extraction with no formats — never recorded: `processJob` waits it out (`outlastRateLimit`), as it does an Innertube 429 (`isRateLimited`), until a day of refusals, three at least, ends the job (`rateLimitCap`, `rateLimitCapRefusals`). A captcha carries `errCaptchaRequired` (`internal/worker/rate_limit.go`) in its place, which is an `ErrRateLimited` and reads as one, and which `isCaptcha` tells apart |
| `ErrTwitchAuthExpired` | `internal/twitch/api.go` | Twitch auth token expired or invalid |
| `ErrSubscriberOnly` | `internal/twitch/api.go` | Subscriber-only content refused to a session not shown to be signed in: no token sent, a playback token minted for nobody, or one whose document could not be read |
| `ErrSubscriberOnlyNotEntitled` | `internal/twitch/api.go` | The same Usher refusal to a session the playback token names as signed in — an account without the subscription (G52, owner decision D20). Not a wrap of `ErrSubscriberOnly` |

### Error-to-Status Mapping

In `DownloadWorker.setJobError()` (`internal/worker/worker.go`):
```
cookiesStatusError(err)  ->  StatusCookies      // errors.Is against ErrCookiesRequired, ErrNotAMember,
                                                //   twitch.ErrTwitchAuthExpired, twitch.ErrSubscriberOnly
anything else            ->  StatusError
```
Cancellation is not an error class: `handleCancellation` asks the queue whether the user cancelled (`WasCancelled`) and writes `Cancelled`, or leaves the status untouched on a shutdown so the job resumes on restart. The user's `Cancelled` is the one `CancelJob` wrote before it flagged the run, so `handleCancellation` settles the chat status on a row that still reads `Cancelled` only (`UpdateJobFieldsIf`), and lands on nothing another actor wrote while the run unwound. It settles the chat of a `Cancelled` row without the flag as well: `CancelJob`'s row write runs its subscribers ahead of `queue.Cancel`, and a run can stop on that write alone (its conditional go-live or `Downloading` write refused), in which case the Cancel's caller reports it, and the row's chat does not keep the `pending` or `downloading` both UIs render verbatim. A Cancel that lands after `processJob` last read its context reaches `setJobError` all the same, with the failure the run was already returning. When it flagged the run before the failure settled (`JobQueue.settle`) — its `Cancelled` write may still be on the way — or its write already reads `Cancelled` (`UpdateJobFieldsUnless(..., Cancelled, ...)` does not apply over it), `setJobError` hands the run to `handleCancellation` instead of recording Error or sending Job Failed.

A Cancel after that finds the run settled and is its caller's to report. The error's text becomes the job's `error` column, and `park_reason`/`park_identity` are written on every error transition so the credential sweeps can tell a dead-cookie park from a membership one. An applied `Error` settles a chat its run left in flight by the rule a Cancel uses, on either platform (owner rulings R-E1, R-E1a, R-H1; `settleErrorChat` and `stoppedChatStatus`, `internal/worker/worker.go`): `downloading` becomes `incomplete`, `pending` is cleared, each conditional on the row still reading `Error` with that value. `setJobError`, the panic write (`writePanicError`), a failed Mux (`muxJob`) and an automatic Twitch mux that could not start (`autoMuxNow`, `internal/worker/twitch_end_unconfirmed.go`) all settle through it — they are every `Error` write there is; a `COOKIES?` park is left as it is, and so is a verdict the run recorded, the one `ExecuteTwitch`'s unconfirmed-end arm writes included. A run's chat downloaders are registered with it as they are built (`runChatRegistry`, `internal/worker/run_chats.go`: the YouTube early chat, the orchestrator's own, and both Twitch ones), and the two exits that can end a run without an orchestrator's chat teardown — a panic, which unwinds past it, and `setJobError` — stop them first (`stopRunChats`, `internal/worker/worker.go`), ahead of the `Error` write and its settle; the stop also closes the gate a YouTube downloader's `OnStart` writes `downloading` through (`whileRunning`), so nothing writes over the settle, and `processJob` releases the entry on its way out. An entry holds what its run still owns: the stream processor has a waiting-room chat it stops or restarts forgotten (`forget`), and a run that goes round again in place — a rate limit or a setup outage waited out — starts its new pass from none (`nextPass`, which stops what the earlier pass left), so a multi-day wait does not keep every downloader it built.

### Notification and Recovery Suppression

- `errors.Is(err, ErrNonActionable)` suppresses the failure notification (an age-restricted stream or an exhausted probe budget was never going to succeed) and skips the automatic cookie refresh — recovery would re-queue the job and reset its retry budget. The report is suppressed, not the close: the "Job Failed" embed still goes out marked `SendOptions.EditOnly`, which on an edit-mode target holding the job's lifecycle message edits it to its terminal look and posts nothing else, without the mention, and everywhere else sends nothing (`dispatchOne`, `internal/notifications/lifecycle.go`). Suppressing the send outright left that message reading "Found" or "Downloading" for good. The Twitch retry suppression beside it sends nothing at all: the monitor restarts that job, and its next event goes on editing the same message.
- A Twitch flap still inside its auto-retry budget (`AutoRetryCount > 0` and the exact offline message — or the `twitch_unreachable` marker — with no delivered segments) is also silent, because the monitor will `AutoReinitializeJob` on its next poll; a terminal failure on a retried job does notify.
- A live Twitch capture that stops on its unconfirmed-end latch DOES notify — the job is in Error, and nothing yet says its broadcast is over — and the automatic mux that follows once the monitor confirms the end (D-T4, `AutoMuxEndedBroadcast`) is the Mux action's path: it notifies on Finished, as that path does, and a failure writes the row's error without a second embed.
- `ErrNotAMember` parks the job but skips the automatic cookie refresh (`cookieRefreshWorthAttempting`): the cookies are alive, they belong to the wrong account, and only a different account's credentials resume it.
- `twitch.ErrSubscriberOnlyNotEntitled` does not park at all: it is a plain `Error` (not in `cookiesStatusError`, `ParkReasonNone`), sends the ordinary Job Failed, and is excluded from `cookieRefreshWorthAttempting` too, as a second lock (owner decision D20). `Service.GetHLSMasterPlaylist` and `GetVodHLSPlaylist` re-label Usher's subscriber-only 403 as it when an auth-token was sent and the playback token's `user_id` names a signed-in session (`subscriberOnlyRefusal`, `internal/twitch/playback_token.go`) — yt-dlp's "Your account does not have access to this subscriber-only content", from its split on whether an auth-token was sent; Moombox reads the token Twitch minted instead of the cookie's presence, so a dead token stays a login problem. There is no Twitch account fingerprint a sweep could resume it on (`CurrentCredentialIdentity` has none for Twitch), so it stays in Error until retried. The VOD path keeps it through its `%v` flattening via `twitchAuthSentinel`.

## Key Types and Public API

### database.Job

The primary data model. See `internal/database/types.go` for the complete struct. Key fields:

- `ID` (string): Primary key. For YouTube: video ID. For Twitch: `tw_{streamID}`, `tw_manual_{login}_{timestamp}`, a VOD's `tw_v{vodID}` or a clip's `tw_clip_{slug}`.
- `VideoID` (string): Platform-specific video identifier.
- `Platform` (string): `"youtube"` or `"twitch"`.
- `Status` (JobStatus): Current lifecycle status.
- `Progress` (string): Human-readable progress (e.g., `"(V: 1234/1300 A: 1234/1300 C: 900)"`; the shapes are listed under ProgressTracker above).
- `Percent` (float64): 0-100 for VOD downloads.
- `IsVod` (bool): True for VOD/non-live downloads.
- `ManuallyAdded` (bool): True if added via CLI or UI (vs. monitor discovery).
- `AllowNonStream` (bool): True if non-stream content should be downloaded as VOD.
- `SelectedVideoItag` / `SelectedAudioItag` (*int): Manual format override. -1 = skip track.
- `StartTime` / `EndTime` (*float64): Post-download trim boundaries in seconds.
- `QualityPreference` (string): e.g., `"1080p60"`, `"720p"`, `"best"`, `"audio_only"`. The quality the job was created to record, set at insert and never overwritten; every variant selection reads it, Twitch's included (a Twitch row records `"best"` when none was named, and an empty value selects as `"best"`).
- `TwitchQuality` (string): the Twitch variant the capture is recording, by its playlist name — written at the capture start and on every split that moves to another variant, shown as "Quality", and never selected from.
- `Gaps` ([]Gap): Missing segment ranges detected during download.
- `Segments` ([]Segment): Part records for multi-part downloads — quality splits (both platforms) and Twitch live gap splits. Each row carries the part's video path and (Twitch) its per-part chat file.
- `Trims` ([]TrimRecord): Clips created from this job.

### database.Database

Key methods:
- `Open(dbPath, logger) -> (*Database, error)`: Opens/creates database, runs migrations, prepares the hot-path statement.
- `AddJob(job) -> (bool, error)`: INSERT OR IGNORE. Returns false if duplicate. The row, its `Gaps` and its `Segments` (a split archive import's parts) commit in one transaction, and `OnJobAdded` carries the row read back with its child rows, as `GetJob` reads it — the only event a new row gets, so parts inserted after it reached neither UI.
- `GetJob(id) -> (*Job, error)`: Single job with gaps, trims, segments loaded.
- `GetAllJobs() -> ([]*Job, error)`: All jobs ordered by `updated_at DESC`.
- `UpdateJobFields(jobID, map[string]any)`: Dynamic partial update with auto `updated_at`. Triggers subscribers.
- `UpdateJobFieldsIf(jobID, expected, map[string]any) -> bool` / `UpdateJobFieldsUnless(jobID, unwanted, map[string]any) -> bool` / `UpdateJobFieldsUnlessTerminal(jobID, map[string]any) -> bool`: The same write, applied only while the row's status is `expected` (a compare-and-set), is not `unwanted`, or is not terminal (`Finished`, `Error`, `Cancelled` — `Job.IsTerminal`'s set); reports whether it applied, and triggers subscribers only when it did.
- `DeleteJob(id) -> error`: Hard delete with cascading gap/trim/segment cleanup.
- `OnJobUpdate(fn) -> unsubscribe` / `OnJobChange(fn) -> unsubscribe`: Subscribe to per-job update events; the latter also receives the list of columns written.
- `OnJobAdded(fn)` / `OnJobDeleted(fn)` / `OnTrimsChanged(fn) -> unsubscribe`: Lifecycle events of `AddJob`, `DeleteJob` and `AddTrim`/`DeleteTrim`.
- `OnJobsChange(fn) -> unsubscribe`: Subscribe to full-list refreshes. Fired only by the bulk writers `BatchSetWatched` and `DeleteJobsAndHistoryForChannel`, never by a single add or delete.
- `AddToHistory(videoID)`: Records video ID to prevent re-downloading.
- `HasProcessed(videoID) -> (bool, error)`: Reports whether the video ID is in history, i.e. was jobbed before.
- `JobExists(id) -> bool`: O(1) existence check.

### worker.DownloadWorker

Key methods:

- `Stop()`: Signals stop, waits up to 10 seconds for in-flight jobs.

### worker.DownloadOrchestrator

Key methods:
- `NewDownloadOrchestrator(db, queue, ffmpegPath, logger, cs, pp, nm) -> *DownloadOrchestrator`: Constructor.
- `ExecuteWithChat(ctx, jobCtx, videoInfo, isVod, existingChat) -> error`: Full YouTube download pipeline; `existingChat` is a chat downloader already started during the wait, or nil.
- `ExecuteTwitch(ctx, jobCtx, variant, isVod, twitchChat) -> error`: Full Twitch download pipeline. Its `Downloading` write, made after its cancel listener is registered, applies only to a row with no outcome, as `ExecuteWithChat`'s does, so a Cancel that landed after `processTwitchLive`'s Live write is not written over, and no "Twitch Download Starting" is sent for the job just cancelled; a refusal stops the chat source and returns `ErrCancelled` with nothing announced or staged. Its `Muxing` write as the session loop ends is made only on the way to a finalize — a clean end, or a broadcast that ended or changed during an outage — and only on a row with no outcome. Made ahead of the shutdown/user-cancel exit, it would write Muxing over every operator Cancel of a live capture, and a shutdown would leave the row Muxing, so the restart muxed the partial capture (`muxOnRestart`) instead of resuming the broadcast; the row stays `Downloading`. A refusal (a Cancel whose row write landed before the run's listener heard it) takes the cancel exit, staging kept, and a user-cancel exit returns `ErrCancelled` with the context's error. Which of the two it takes is decided once, on the session's state as the loop ended; only the job's context and the operator's cancel are read again after the part-mux wait.

  Reading the loop's session again there would be wrong: an offline report cancels that session until the finalize's own begins, so a broadcast that ended cleanly, with the connection dropping during the wait, would take the shutdown exit and be recorded as Error "context canceled", which neither the automatic mux nor the Twitch recovery picks up. For live streams this is a *session loop*: the engine runs with `StopOnGap` (the live playlist window is all the live edge has), so a playlist gap muxes the current capture as a finished part (`{name} - partN.mp4` + rolled per-part chat) and continues at the live edge in a new `seg_N` staging dir; a connectivity outage pauses the session and resumes the SAME job once the same broadcast (stream_start_time identity, rechecked post-outage) is reachable again — one job per broadcast. Only an outage that lasts: the session is cancelled once the monitor has reported offline for `twitchOutageCancelAfter` (`connectivity.MinOutage`, 60 s, the Outage Alert's minimum too), and a restore before that disarms the cancel and asks the live chat to reconnect now (`RetryNow`) — the engine's `IsOnline` wiring waits a shorter outage out in place, and its resume and `StopOnGap` decide between a seamless continuation and a gap split. Without that delay a flapping link would cancel the session, recheck the broadcast, refresh the variant and send a "Twitch Download Resumed" on every ~15 s cycle of the monitor.

  Only a CONFIRMED end finalizes it: a post-outage recheck that gets no answer, or a master-playlist refresh that still fails after its retries (`postOutageRefreshAttempts`) while the broadcast is live or unverifiable, takes the same unknown-verdict exit as the in-loop refresh (which retries a failed master-playlist fetch `liveRefreshAttempts` times over about 100 s first — checking the stream before each pause and finalizing at once on a confirmed end — since nothing continues a Twitch capture from Error: `/resume` is YouTube-only, Retry starts over with fresh staging and the monitor recovers offline flaps only) — Error, staging kept — rather than marking a capture of a still-running broadcast Finished, which the monitor would then never re-archive. The exit is gated on the job's own context and the operator's cancel, never on the session's: the post-outage exits latch from the recovery loop, whose session context the outage has already cancelled, and gated on that they would fall through to the shutdown path and write "context canceled" as the job's error.

  Since that gate does not see the outage, a latch the outage cut short inside its own re-verify is discarded where the outage branch takes over: only a latch the recovery itself takes, or the resumed session's own, reaches the exit, so a stale one neither errors a capture the resumed session completes nor overrides a recovery that confirms the broadcast over (which finalizes). That exit marks its error (`ErrTwitchEndUnconfirmed`, `internal/worker/twitch_end_unconfirmed.go`; the text is the download failure's own) and `setJobError` records the mark as `park_reason = 'twitch_end_unconfirmed'`, so once the Twitch monitor's poll shows that broadcast over — the channel offline, or live with a different broadcast (`TwitchBroadcastOver`: by stream ID when the job ID carries one, else by `stream_start_time`) — `DownloadWorker.AutoMuxEndedBroadcast` confirms it with the same two samples (`confirmTwitchLiveness`) and muxes the kept staging exactly as the Mux action does (owner decision D-T4). Once per failure: the marker is cleared as the mux starts (`muxJob`'s `Muxing` write, once it holds the job's staging claim) or with the failure a mux that cannot start writes, so a mux that fails leaves the row in Error with an error saying the automatic mux failed, and no later poll tries again.

  The one refusal that is not a failure is `ErrStagingBusy` — another operation, such as a set-aside recovery (`A S`), which leaves the row in Error while it runs, holds the job's staging — so no mux was attempted: the row keeps its marker and its own error, and the next poll that finds the broadcast over tries again. Only the live broadcast-end latch marks — a VOD's latch and a failed part advance do not — and the Twitch auto re-initialisation refuses a marked row (`jobstate.TwitchAutoRetryPending`), so a row is never both re-initialised and muxed. A job whose channel the config no longer holds is never polled, and only the Mux action archives it. A VOD has no live end to confirm, so an engine failure before its download completes returns an error before the `Muxing` write, and the job lands in Error with staging intact instead of being finalized as a truncated `Finished` file. A connectivity outage is not such a failure: the offline cancel is registered for live captures only, so on a VOD the engine's `IsOnline` wiring waits the outage out and the download carries on from where it stopped, as on the YouTube paths.

  That includes a segment that fails because of the outage: `fetchSegmentWithRetry` (the parallel VOD path, `internal/engine/downloader_fetch.go`) does not charge an attempt that fails offline, and the sequential HLS loop waits instead of counting it toward the stuck-segment skip, whose count restarts after every outage (`hlsOutages`) — charging them would turn the segments in flight during a long outage into gaps, and cancelling the download would end the job in Error and make Retry download the whole VOD again. On daemon restart, `discoverResumeSegment` maps staged `seg_N` dirs + recorded segment rows to the correct part so a resume never appends into an already-muxed part's staging file. Seamless continuation (sequence numbers still covered by the playlist window) keeps appending — splits happen only where data was actually lost. Both TS and fMP4/CMAF delivery are handled: on an fMP4 playlist the engine writes the `#EXT-X-MAP` init segment at the head of each part file before its first fragment (`ensureHlsInit`), tolerates token-rotated init URIs by content hash, and returns `ErrInitSegmentChanged` when the init genuinely changes mid-part (transcode restart) — handled like a gap split minus the lost-data notification, since the successor part re-requests the exact segment the engine refused to write.

  A quality split seeds its successor the same way, from the first sequence the closed part does not hold (Twitch variants share one sequence numbering), so the new part never repeats the closed part's last seconds; only a short part that is discarded rather than muxed leaves the successor to replay the playlist window, which keeps what the window still holds of the dropped span.

### monitor.FeedMonitor / DecapiMonitor / TwitchMonitor

All three monitors share one poll-cycle lifecycle, `pollLoop` (`internal/monitor/pollloop.go`): Start/Stop, CheckNow, the fixed-rate timer chain with its two retired-chain `ctx.Err()` guards, the latched mid-cycle kick (`pendingKick`) and the int64 countdown (a time, `-1` while a cycle runs, `0` with nothing to poll or stopped). Each monitor supplies its own interval, check, logger and panic recovery in a `pollSpec`, and keeps this interface:
- `Start(ctx)`: Begin monitoring loop.
- `Stop()`: Cancel and clean up.
- `CheckNow()`: Trigger an immediate check (used when channels change).
- `GetNextCheckAt() -> int64`: Next scheduled check in epoch milliseconds.

Callback fields:
- `OnVideoFound func(videoID, title, url string, channel *config.ChannelConfig)` (Feed/DECAPI)
- `OnStreamFound func(info *twitch.TwitchStreamInfo, channel *config.ChannelConfig)` (Twitch)
- `OnSchedule func(nextCheckAt int64)`: Called when next check time is determined.
- `ProbeVideo VideoProbeFunc` (Feed/DECAPI): Pre-creation metadata check to filter non-streams.
