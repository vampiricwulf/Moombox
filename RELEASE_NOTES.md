## Features

- **Self-updates are bound to their release by a signed manifest.** Each release now publishes a signed `moombox-manifest.json` naming its version, tag and every platform binary's SHA-256, and the updater refuses a release whose manifest is missing or unsigned, names another or an older version, or does not match the download; before, an older signed binary or another platform's could be served under a newer tag and would install. Updating to this version from an earlier one works as before. Verify Signature (`R S`, and the dashboard's button) now also checks the running binary against its release's manifest, fails a release from this one on whose manifest is missing, and gives releases from before the manifest the signature-only check, shown in yellow.
- **`O L` opens the selected job's own log in the TUI.** The per-job log behind the dashboard's job dialog opens full-screen in the log panel's viewer, with scrolling, PgUp/PgDn, `/` search with `n`/`N`, End to follow and level colours. It is re-read every second while open, so a failed job's lines or an `A S` recovery's progress can be followed without filtering the global log by hand. Esc clears a search, then closes the overlay.
- **Trims run in the background and show their progress on the dashboard.** Reloading the page, closing the tab or losing the connection used to kill a dashboard trim and leave an unplayable partial file under the finished trim's name. `POST /api/jobs/{id}/trims` now answers 202 at once, the trim writes a `.partial.mp4` that is renamed into place only when complete, and the result arrives as a `trim_status` WebSocket frame and a toast. Each running trim appears in its job's Trims section with its range and a progress bar, also after a reload, and every trim that fails or cannot run, from either UI or requested when the job was added, sends Trim Failed (`trim_error`).
- **Backlog archiving waits while the output disk is critically full.** The archive-slots scheduler admits no backlog VOD from the moment the output volume reaches `disk_critical_percent` until usage is back 2 points below it, the same margin the disk alert clears on, and the hold survives a restart. A backlog VOD whose download or mux runs out of space goes back to Queued with its staging kept, and ends in Error only after repeated failures; an interrupted download resumes from its last checkpoint, while one whose mux ran out of space downloads again. Live, upcoming and manually added jobs are never held back.
- **Alerts that are open when Moombox restarts still get their recovery message.** Disk, BotGuard sidecar, channel-health and platform-authentication alerts were closed only by the process that sent them, so an update, a settings restart or a crash left them open in Discord for good. Open alerts are now kept in `open-alerts.json` next to the database: after a restart the first healthy check sends the matching close, and a problem that is still there does not alert twice (an authentication failure is announced again once its 30-minute cooldown has passed).
- **A Twitch capture that failed before its broadcast's end was confirmed is muxed automatically once the end is.** Such a capture went to Error with its staging kept, and only a manual Mux turned it into an archive. The Twitch monitor now does what the Mux action does, once per failure, when it confirms the broadcast is over; if that mux fails, the error says so and staging is kept. A capture interrupted while Moombox was down, whose broadcast ended in the meantime, now says its captured data can be muxed via the Mux action instead of only "twitch channel is offline".
- **Each start cleans up staging leftovers that are safe to remove.** The staging of a Finished job whose cleanup never completed (after a crash, or because Windows held a file open), and set-aside recordings already confirmed in their own file, are removed by a background pass at startup that logs every path and reason. It deletes only when every archive file the job lists is on disk; active jobs, imports and anything it cannot verify are left to the Files tab.
- **Tailscale clients can reach a `lan` dashboard like any other LAN client.** With `network_access = "lan"`, Tailscale's 100.64.0.0/10 addresses now count as private for the IP check, the origin checks and the password exemption, so tailnet users no longer need `external` with a password. The range stays public on `external` and `public`, because some ISPs use it for carrier-grade NAT; if your host sits behind such a NAT, the README recommends a host firewall that lets only the tailnet interface reach the port.
- **`prefer_60fps` now decides the frame rate of live YouTube recordings and of Twitch recordings.** Only YouTube's whole-file VOD downloads read it: live YouTube ranked the renditions of a size by bandwidth alone and Twitch by codec and its source flag, so a 1080p60 source beat a 1080p30 transcode whatever the setting said. At the chosen size, and at the next lower size when the preferred one is missing, the frame rate `prefer_60fps` asks for now decides ahead of bandwidth (on Twitch after codec and before the source flag), and a suffix such as `1080p60` asks for its own rate there too, so a 50 fps broadcast keeps its 50 fps rendition. Sizes are measured by the short edge on both platforms, so a portrait stream's "1080p" no longer falls to 480p.
- **Shift-Tab moves TUI panel focus backwards.** It was documented beside Tab but did nothing. Leaving the log panel by any route (Tab, Shift-Tab or a click) also turns its auto-scroll back on.

## Improvements

- **PO-token requests fail at once while the BotGuard sidecar is down, and the messages say what that costs.** During an outage every request fell through to the in-process path, which BotGuard's timing check rejects, and spent seconds to minutes and three Google round trips minting nothing, queued behind a lock that ignored the request's deadline. The "BotGuard Sidecar Down" alert, both settings UIs, the startup log and the docs no longer promise a slower fallback: without the sidecar no PO tokens are minted and signature-protected formats cannot be solved, while formats that need neither keep working.
- **A sidecar that dies during startup says why, and repairs a damaged unpack.** The warning, health reason and alert used to read only "sidecar exited before ready"; they now end with Node's own last error lines, such as a module that will not load or a missing shared library. The first such death also discards the unpacked sidecar files, so the next start extracts them afresh.
- **The sidecar does less redundant work when YouTube rotates players.** It now caches signature solvers for ten players, up from two, so channels served by several player versions no longer re-download and re-prepare about 3 MB of player JavaScript on every eviction. When several downloads meet a new player at once, one sends the script while the others wait, instead of each load stalling the PO-token requests queued behind it.
- **A failed update check, download or signature check says why, and is logged.** The dashboard's update actions answered fixed strings ("Update failed: update failed") and logged nothing. They now log the error and show its cause, such as a GitHub rate limit, no release for this version or an error page in place of the release asset, and Settings' "Check Now" shows the reason instead of "Check failed".
- **Twitch chat lines up with the start of each part's video.** Each part's chat was timed from the local clock when the part started, while the video begins at the first segment joined, up to one playlist window earlier, so every message played back late. Chat timing now uses the timestamp of the part's first segment, even after a long ad break at the start.
- **Dashboard text meets 4.5:1 contrast in both themes.** Grey helper text, coloured error, warning and success text, empty states, the disk bar and status bar, the light theme's buttons, tabs, status pills and WARN/ERROR/DEBUG log lines (some as faint as 1.7:1) now clear the WCAG AA bar. The setup wizard's steps are drawn as hollow, green and blue circles instead of being faded, and archived rows dim only their thumbnail.
- **More of the dashboard works from the keyboard and with a screen reader.** The filter bar's controls, the import drop zone and the notification chips can be reached with Tab and toggled with Enter or Space. The setup wizard and FFmpeg screen keep focus inside instead of tabbing into the hidden dashboard, and the wizard moves focus to each page. Job rows are announced as table rows, banners are announced when they appear, headings no longer skip levels, and unlabelled fields, switches and delete buttons now have names.
- **Errors name their real cause.** A whole-file VOD that runs out of chunk attempts ends with "chunk download failed after N attempts: <cause>"; a failed signature or n-parameter solve says why the sidecar path failed; a YouTube extraction error names the client that was refused instead of "Innertube API error: HTTP 403"; a deadline that runs out while retrying keeps its "HTTP 5xx". A failed trim's log line includes the FFmpeg lines that give the reason, such as "No space left on device".
- **Failures that used to be silent now reach the log, and repeated ones stop flooding it.** Boot warns about every hand-edited config value it replaced with a default (`port = 0`, `feed_check_interval = 0`, …), which the next save would otherwise have written over unnoticed. A Twitch status check failing for the whole batch warns on the first failure of a streak and logs the recovery, and the worker warns when its job poll cannot read the database. DECAPI's "outside the archive window" and "date fetch failed" lines, which repeated every 15 seconds per channel, log at Debug after the first.
- **The dashboard shows the server's reason when it refuses something.** Trim create and delete now say why (an end past the video, a duplicate range, a trim already running, an unfinished job), as do cookie recheck, force check, format lookup, the watched toggle, View Release Notes, Re-scan Feed History, the custom FFmpeg path check and setup wizard errors. Settings and channel saves refuse an unknown `quality_preference` or an out-of-range `archive_window_days`, `archive_slots` or cookie `refresh_interval` with a 400 that names the field, instead of a bare "failed to save config".
- **Cookie messages name the real problem.** A Firefox read that failed on its first try no longer says "after 5 attempts", an unreadable `cookies.sqlite-wal` is reported as a permissions problem rather than a corrupt database, and the no-browser error lists all ten supported browsers. A job's automatic cookie refresh says "failed" only when it ran and failed: when it could not tell, or the feature is off, the log says so and points at `R C` or the setting.
- **Files tab deletes say what they remove.** Each orphaned-file and history row's delete button is labelled with its path or video ID, and the single and Delete All confirmations warn when a staging folder still holds set-aside recordings, footage that exists nowhere else.
- **TUI text is easier to read.** Long log lines wrap between words instead of splitting addresses and URLs. The selected half of a Yes/No toggle is bracketed, so it reads under `NO_COLOR` and in screenshots. `R N` wraps bullets under their text and keeps a blockquote's bar on every row, and status lines for refusals and errors are yellow or red instead of success green.
- **More settings take effect as soon as they are saved.** Monitor interval changes no longer wait out the old delay (up to a day for the feed), disk thresholds and the output directory reach the gauge and alerts at once, turning on automatic update checks runs the first check within a minute, `cookies.dpapi_fallback` applies without a restart, and a cookie platform switched off leaves the TUI status bar. A `segment_workers` above 16 is warned about when saved, not only at boot.
- **Settings help says what each setting does and when it applies.** `network_access` applies its admission rules as soon as it is saved (only its bind address waits for a restart), as does `cookies.auto_enabled` apart from its refresh timer, and the staging-directory help warns that a change strands anything already staged. `num_parallel_downloads` shows its real default of 10 and limits VODs only, and the README's settings table and `config.example.toml` mark which settings need a restart.
- **Settings that did nothing are retired.** `downloader.po_token` and `downloader.visitor_data` were accepted, saved and documented as a manual PO-token override, but nothing read them; a config that still has them logs one warning per key at boot, and the next save leaves them out. The per-channel `num_desc_lookbehind` leaves both channel editors, since channel terms never matched the description it served, and a config that sets it still loads.

## Bug Fixes

- **Security: a web page can no longer read the dashboard through DNS rebinding.** Local and LAN browsers skip the password and a GET carried no host check, so on any network mode a malicious page whose hostname had been re-pointed at the Moombox host could read jobs, channels, logs, recordings and notification webhook URLs. Those browsers must now address the server by IP address, `localhost` or a name on its TLS certificate, or on `external` and `public` also the host of `network.public_url`. If you open the dashboard by another hostname, such as `nas.local`, switch to its IP address or put that name on the certificate; updating is recommended.
- **Security: Moombox only runs an FFmpeg named `ffmpeg`, and on Windows only a `.exe` browser.** Any client the network filter admits could point `paths.ffmpeg_path` or `cookies.browser_path` at a file it had just uploaded through Import, and Moombox would run it; on a Windows install set to `lan`, any LAN device could run code on the host. The FFmpeg executable must now be named `ffmpeg` or `ffmpeg.exe`, checked whenever the value changes (a path already saved keeps working), and imported files are always renamed so they can never match.
- **Security: failed downloads no longer leak your IP address, PO token or Twitch session, and notification secrets stay out of the log.** A failed fetch quoted its signed URL whole in the job's error, `moombox.log`, both Logs panels and the Job Failed embed, posting the IP the URL was issued to (and sometimes the PO token) or the viewer's Twitch playback session to the webhook channel; those values now read `<redacted>`. Rejected or disabled notification URLs are logged as scheme and host only, a `network.public_url` containing `@` is refused with everything before the `@` shown as `<redacted>`, and a webhook URL with a control character, whose every failed send quoted the token, is rejected.
- **Security: other sites and other local services can no longer act as the dashboard.** On `localhost` and `lan`, any page served from a loopback or private address, such as a dev server on another port or a router or NAS admin page, passed the CSRF check, got credentialed CORS and could open the WebSocket; a page must now come from the port the dashboard was reached on or `public_url`'s port. GET routes that do work (the format lookup, the FFmpeg and setup-status checks, the release-notes fetch) refuse requests the browser marks cross-site, and `/get_pot` and the cache-invalidation endpoints check any request that carries a browser's Origin or Referer; yt-dlp, curl and typed URLs are unaffected. Behind a reverse proxy on another port, the browser's port must reach Moombox in the forwarded host (for nginx, `$http_host` or `$host:$server_port`), and a TLS proxy on 443 must be in `trusted_proxies` or have `trust_forwarded_proto` set; the README's proxy recipe now also sets `public_url`.
- **Security: remembered logins expire on the server, and an update can be applied only from the host itself.** `client_token_ttl_days` only set the browser cookie's lifetime, so a token copied once authenticated forever; the server now checks each token's age and deletes an expired one. Applying an update now requires the request to come from the host itself rather than just a loopback `Origin` header, which a LAN client could forge; a logout from a just-revived session now ends it, and client-token IPv6 addresses are masked correctly.
- **Security: upstream-calling routes are rate-limited, and job adds are validated.** Format lookups, channel resolution and trim creation now share the API rate limit, so a hostile LAN device cannot get your IP rate-limited or bot-flagged by YouTube, and a global IPv6 client is counted by its /64. `POST /api/jobs` requires a valid YouTube video ID or Twitch login or VOD ID (one with `/` or `..` named a staging folder outside the staging directory) and stores the canonical watch URL rather than any link the client sent.
- **YouTube recordings that began mid-broadcast are no longer refused at mux.** In 2.8.9 and 2.8.10 the completeness check counted a fragmented MP4's start offset as missing time, so every later part of a quality split, and every capture started or resumed more than 20 seconds into the broadcast, failed at finalize, again in segment recovery and again under Mux, and stayed unmuxed in staging. Such inputs are now measured by the media they hold, so after updating, a job left in Error this way can be muxed with `A M`, the details dialog's Mux or `POST /api/jobs/{id}/mux`.
- **The Files cleanup no longer offers live recordings for deletion.** It listed, and Delete or Delete All removed: an archive still being muxed (the staging cleanup then deleted the only other copy), a set-aside recovery or trim still being written, the archives, parts, thumbnails and trims of jobs with a per-channel or per-job output directory, an archive tree moved with `paths.output_directory` repointed or recorded under a link or junction spelling, a channel folder named "trim", and every part's chat after a failed database read. A file now counts as in use whenever a job or trim names it, wherever it sits, and Delete re-checks at that moment, answering a stale list with "No longer an orphan… Refresh the list." The cleanup now also looks inside an output directory that is itself a symlink or junction.
- **Imports never overwrite a file already in `imports/`.** Deleting an imported job keeps its files, so a re-import wrote straight onto them, truncating the only good copy, removing it if the upload proved damaged, or replacing it with a different file of the same name. Files are now extracted under a temporary name and moved into place once the job exists; an identical file is re-adopted, any other takes a " (2)" name, and a failed import removes what it extracted.
- **An import reads a zip as one recording.** A split recording's `- partN` files import as one job with per-part chats instead of as part 1 alone, any other zip with several videos is refused, and a chat must be named after its video (`<name>.chat.json`). A Moombox Twitch archive imports as a Twitch job, the video ID comes from the last bracket in the name, long non-Latin titles fit the file-name limit, imported jobs count in Stats, and cancelling after the upload finished no longer creates the job anyway.
- **Muxing and recovery no longer lose good recordings.** Recovering a set-aside recording could delete the only full copy behind a truncated one, since FFmpeg's copy can stop at an unreadable fragment and still report success; the copy is now checked and a short one discarded. A crash between merging a split job's parts and the cleanup no longer makes the next finalize append them again. A Finished job whose part failed to mux can now be muxed (`A M`, the details dialog or `POST /api/jobs/{id}/mux`), shutdown cancels in-flight muxes before it exits, and chat and thumbnail copies go through a temporary file so a failure cannot leave a truncated one.
- **Removing a channel keeps its jobs, and asks before deleting any.** Removal deleted the channel's Queued, Upcoming and `COOKIES?` jobs, including a live capture parked mid-stream with its footage staged, which was left with no job to resume or mux it and then offered for deletion. The dashboard's Remove and the TUI's Settings → Channels `D` now show the channel's job count and the parked recordings with footage, which are kept either way, and offer to keep the channel's jobs (the default) or delete its pending ones (`DELETE /api/config/channels/{id}?jobs=keep|delete`, with counts from `GET /api/config/channels/{id}/removal`). A kept backlog VOD is still admitted, under the global `archive_slots`.
- **VOD downloads can no longer finish truncated or spliced.** A "range not satisfiable", an empty chunk or a shorter range than asked for, arriving before the announced size, was taken as the end of the file, clearing the resume point and finishing the job with a truncated archive; it now fetches what is missing, or fails with the offset and expected size and keeps the resume point. A resume after the chosen format had changed (another `max_video_resolution` or `prefer_60fps`, a token fallback) appended the new format's bytes to the old partial file; each partial file now records its format and size and restarts on a mismatch. Cancelling or restarting mid-way through an HLS VOD no longer leaves a hole of up to one segment per worker.
- **Long VOD downloads survive an expired link, a dropped connection and an outage.** A download link lasts about six hours, so a long VOD failed with a 403 once it outlived it, and an outage of more than a few seconds or a connection dropped mid-chunk ended the job however much had already streamed. An expired link is now refreshed in place, always to the same file, dropped connections and server errors are retried, and outages are waited out without using up the retry budget, with resume checkpoints still every 50 MB. A VOD that waited hours for a download slot fetches fresh links before it starts and is re-checked, so one that turned members-only or private meanwhile goes to `COOKIES?` or Error, and while it waits, a YouTube or Twitch VOD no longer reads Downloading.
- **Restarts no longer throw away or re-download complete recordings.** When a job that had captured part of a live stream came back as a finished VOD, the restart mux or a manual Mux could archive the old partial capture and then delete the complete download with staging. The complete download is now the archive, and the earlier capture or parts are kept beside it as `.restart-` files. A YouTube job waiting for its chat after the media was complete (up to two minutes live, up to the video's length for a VOD) stayed Downloading, so a restart in that window downloaded everything again; it is now Muxing and re-muxes from staging.
- **Chat archives survive failed writes and crashes.** A message that could not be encoded, or a write that failed on a full disk or locked file, could leave a stray or missing comma that no JSON reader would open, and a failed flush dropped its batch while the header still counted it; the batch now stays buffered for the next flush. A YouTube or Twitch chat file torn by a crash is salvaged on resume, keeping every intact message and the damaged original as `.corrupt`, where it used to be overwritten or written into. Twitch messages that still cannot be written are saved to a `.lostbatch.json` beside the part with chat marked incomplete so staging keeps them, and a chat whose copy fails at finalize stays in staging instead of being deleted.
- **Chat archives are no longer duplicated or shrunk, and their status tells the truth.** A capture resumed after its broadcast ended appended the whole chat again from the replay, a re-processed Twitch VOD appended everything past its last 5,000 messages, a crash could repeat a VOD chat's last page, and a second replay-chat run that gave up could replace a complete archive with its first page; each now continues from the file's newest message, or only replaces the archive with something at least as complete. A capture cut short by expired credentials, a crash or a cancel reads "incomplete" instead of "finished" or "downloading". Twitch IRC chat keeps retrying every two minutes instead of giving up after ten failed reconnects, and chat recovered from the replay of a late-starting stream no longer plays early.
- **A YouTube live capture no longer ends early on a passing error.** A refresh that failed after a quality loss or split, or one failed status check (a bot wall, a 429, a 5xx) after ten quiet minutes, finished a live job and deleted its staging, and a failed player fetch after a quality change or any ten-minute HLS stall ended it in Error; these are now retried every five minutes (a failed status check costs one of the six checks a quiet stream gets, not the recording), and a stall resumes from where the downloaders stopped. An interrupted broadcast is waited for the full `interruption_timeout` (120 minutes by default) instead of about half an hour. A capture that cannot write to staging stops at once in Error with its resume point kept, instead of finishing an hour later as if the stream had ended, and a crash in one downloader no longer takes the whole process down.
- **Scheduled, waiting and members-only streams are no longer missed.** A feed entry is dated by its announcement, so a stream scheduled more than `archive_window_days` ahead looked too old when first seen and was never recorded; it is now checked and judged by when it airs. A waiting room whose notice came in a different field, and a live members-only stream without YouTube's live badge, are now recognised instead of being dropped as not a stream or ranked as an old upload. A channel's newest VOD is no longer kept from archiving by a few failed DECAPI checks, or by DECAPI having skipped it before `include_non_live_content` was turned on, and a brand-new VOD whose first check failed is no longer queued as backlog; one already held back this way is freed by deleting its row under Orphaned History Entries in the Files tab (`A O` in the TUI).
- **Credentials are refreshed and parked correctly during live captures.** A members-only job whose cookies died while it waited or mid-broadcast ended in plain Error or finished as if the stream had ended, with no Authentication Required alert and no retry after a cookie repair. It now parks at `COOKIES?` with staging kept; mid-capture, only after the sign-in wall is seen twice with no healthy refresh in between. The 403 credential refresh now really mints a fresh PO token instead of getting the cached one back, and a live job's token request no longer inherits "context canceled" from a monitor probe for the same video.
- **Quality preferences reach every download, and a codec change starts a new part.** Uploads and finished VODs honour the channel's quality preference instead of the global cap; with no Opus track, 128 kbps AAC-LC now beats 48 kbps HE-AAC, and 59.94 fps streams are labelled 60 fps rather than "1080p59". A refresh that switched codec at the same size (AVC to VP9, or Opus to AAC) appended under the old header and corrupted the tail; a live recording now splits on it, as it does when a stream returns from a stall at a new quality. A probe that permanently disagreed with the download no longer restarts the downloaders every 30 seconds.
- **Progress lines say what a download is actually doing.** A YouTube segment download riding out a connection error or stall retried silently behind a frozen counter; it now reads "Segment fetch failing - retrying...", or "Connection lost - reconnecting..." while the machine is offline, and the outage no longer counts toward the stall timeout or the interruption limit. A segment that keeps failing below the live edge says the same instead of "Waiting for next segment", and cancelling during catch-up no longer records phantom gaps. A VOD's ETA no longer counts audio and earlier sessions' bytes as speed, and a finished VOD's final progress line no longer reverts while its replay chat finishes.
- **Twitch captures survive network trouble.** After an outage, one failed playlist refresh or unanswered liveness check finished a broadcast that was still live, which the monitor then never re-archived; an outage cancelled a VOD download, and a VOD cut off by an outage or a download error was muxed short as Finished with its resume data deleted. Refreshes are now retried, VODs and their chat wait for the network and continue, segments that failed offline are retried rather than written off as gaps, and a cut-off VOD or unconfirmed end lands in Error with staging kept. An offline blip during the final chat drain or mux no longer fails a complete recording, and a request throttled on its last attempt fails at once instead of waiting up to 30 seconds.
- **Twitch jobs record what they should.** A job interrupted mid-broadcast and restarted twice could append the channel's next broadcast to the old footage under the old start time; the broadcast check now covers every job holding a capture. A manual add waiting for the channel to go live no longer gets a duplicate job when it does, a quality split no longer re-downloads the end of the previous part, and a resumed job selects by its quality preference rather than the variant it last recorded ("chunked", "720p60"). Notifications for a channel added by hand while offline now carry the stream's real title, art and category instead of "<channel> — Manual Add".
- **Cancel does what it says.** A job cancelled before its download began was treated as finished, its staging (for a resumed job, the recording so far) deleted, and no "Job Cancelled" sent. Cancel on a Muxing job let FFmpeg run on and the job end Finished, a Cancel racing an admission, failure or cookie refresh could be overwritten into Error or a download, and a Cancel from a stale list turned a just-Finished archive into Cancelled. Each now stands, or leaves an ended job as it was, with "Job Cancelled" sent once (also from the TUI for a parked or queued job) and staging kept; Retry, Resume and Reinitialize clicked right after a Cancel wait for the old run to exit instead of being dropped, and a job waiting for its stream ends the wait cleanly when cancelled or when its channel is removed.
- **Job runs no longer interfere with each other or with live broadcasts.** A Retry, the worker's periodic job check or a cookie repair could queue a job again while its failing run was still finishing, and that run's cleanup then cancelled the new one, stalling a live capture; a re-queue now waits for the old run to exit. A backlog VOD waiting for `num_parallel_downloads` held a pipeline slot, so a large backlog could leave a live broadcast waiting and losing footage; it now waits without holding anything a broadcast needs. An internal error late in a run no longer overwrites a Finished, Cancelled, `COOKIES?` or Queued outcome with "internal panic", and the periodic job check no longer restarts a job parked in `COOKIES?`.
- **A network outage no longer sends a channel's whole backlog to Error.** The scheduler kept admitting backlog VODs during an outage, each failed its first fetch, and the backlog ended in Error within minutes with nothing to retry it. Admission now pauses while offline, and a backlog VOD whose first fetch fails transiently goes back to Queued, retrying after 5, 10 and 20 minutes before giving up. A backlog VOD revived by the worker's cookie refresh now waits for its `archive_slots` turn, a deep backfill no longer sends Stream Found for every catalog VOD (backlog VODs announce themselves when admitted), widening `archive_window_days` between a backfill scan and its retry no longer leaves a gap, and disabling a channel pauses its backfill scan, which resumes where it stopped when the channel is enabled again, instead of paging through the whole catalog while other channels' scans wait.
- **Long or reserved titles no longer fail a finalize.** Titles were cut at 200 characters, but a Japanese title takes three bytes per character and Linux allows 255 bytes per file name, so long ones failed with "file name too long". Titles and channel names are now shortened to fit every name the output template produces, and a name Windows reserves for a device, judged by the part before the first dot as Windows does (`CON.Quest.Ep1`), gets a leading `_` instead of writing to the device. The 500-byte `output_template` limit now applies in the TUI and in `config.toml` too.
- **An update can no longer delete files beside a Windows install, or leave a Linux install without a binary.** On Windows, the old launcher's clean-up passed its path to `cmd.exe` unquoted, so an install directory such as `D:\Tools&Apps` deleted every file in `D:\Tools`; on Linux the running binary was moved aside before the new one moved in, so a kill or power loss between the two left none, and it is now replaced in one step. Closing the console window, logging off or shutting down Windows killed Moombox mid-shutdown, skipping resume state, mux cancellation and the database checkpoint; the launcher now waits for that shutdown. A second apply in one session overwrote the rollback copy and is now refused until restart, a startup error's "press Enter" pause no longer counts as a crash to respawn, an update download is cut off only after 60 seconds without data rather than after five minutes in total, and a release pulled from GitHub is no longer offered.
- **A dashboard update survives a slow link, and a crash right after an update is restarted.** The apply ran on the browser's request, so a browser that stopped waiting (Firefox gives up after five minutes) cancelled the download; it now runs on its own, and the dashboard reads a lost answer as "the update may still be downloading". On Linux, a crash in the first two minutes after an update's first healthy boot left Moombox stopped with instructions; it is now respawned like any other crash. An apply is refused while `.update-broken` says a previous swap failed both ways, instead of deleting the only binary left.
- **Moombox finds and reads its config the way the documentation says.** Without `-config`, only `./config.toml` was tried, so a config in `config/config.toml` or `~/.config/moombox/config.toml` was ignored and the first save created a `./config.toml` that shadowed it; if that happened to you, that file still takes precedence, so remove it. Duration strings are now read in each setting's own unit (`probe_cooldown = "2m"` loaded as 2 seconds, `refresh_interval = "1d"` as one minute), so check any you wrote as strings. A fallback port bound because the configured one was busy is no longer saved over it, a fresh install with a cookie file beside the binary gets the first-run setup, `moombox -config X add URL` adds the video with that config instead of booting the daemon, and saved files survive a power loss shortly after they are written.
- **A `database_path` or browser cookie path containing `#`, `?` or `%` opens the file it names.** Earlier releases read such a path as a URI, so `/srv/Moombox #2/moombox.db` kept its data in a file named `/srv/Moombox ` (with a trailing space), and a cookie read under such a path failed as if the browser's database were corrupt. An install whose data lives in that other file keeps using it and warns at every start, naming both paths, until you stop Moombox and move the file, with its `-wal` and `-shm`, to `database_path`.
- **A settings save no longer undoes changes made elsewhere.** A TUI Settings save wrote back the channel list it copied when it opened, dropping a channel added on the dashboard meanwhile (whose jobs were then pruned), re-enabling a disabled one or restoring a removed one; it now merges only the fields the TUI changed. A dashboard save no longer resets an unsaved cookie-browser choice or a custom FFmpeg path saved by its Check button, and the 1–8 tab keys and Play now ask before leaving unsaved Settings. Turning both cookie platform indicators off now sticks, and a TUI save no longer ends a `-log-level` override or switches the TUI to https before the restart that enables it.
- **Channels added by `@handle` or URL are resolved to their ID, and their title filters match as documented.** A bare handle, and in places a URL, was stored as the channel ID and polled forever without archiving anything; every way of adding or editing a channel now resolves the input and refuses a URL that names no channel, a duplicate or an unknown platform, and a channel saved that way migrates the next time it is edited or toggled and can be removed from the dashboard again. Add Channel on an ID already configured replaced the entry and dropped its title filter, output directory and overrides; it now opens that channel for editing, and the API answers 409. A pattern written as `/pattern/g` failed to compile and silently matched nothing, so its streams were skipped; JavaScript-only flags are now ignored, the help says terms match the title (on Twitch, also the category) and that a pattern cannot exclude a word, and the dashboard's broken exclusion example is gone.
- **Browser cookie reads work on signed-in profiles, take only your own session, and recover on their own.** Every Chromium-based read failed with "message too big" on an ordinary signed-in profile, breaking the browser cookie refresh and the setup wizard's finish; answers up to 16 MiB are now accepted. Firefox reads now skip Multi-Account Containers and embedded-site partitions, whose cookies could replace your session, an empty browser cookie no longer replaces a working `LOGIN_INFO`, and on Linux the refresh no longer deletes the `SingletonLock` of a running Chromium profile; a profile in use is skipped with a message naming the lock file. Re-login required now clears when authentication recovers on its own, cookie import and the setup wizard's finish no longer wait up to 45 seconds for a re-check, rotated cookies are written only into the session they came from, and a crash in one refresh no longer stops all later ones.
- **The BotGuard sidecar recovers from hangs and crash loops.** A sidecar that stopped reading its input could hang every later PO-token or signature request, its restart and Moombox's shutdown; requests now give up at their deadline and a stalled write gets it restarted. One that died on its first mint was respawned about every 11 seconds without ever raising `sidecar_down`; it now backs off as intended. It also no longer wedges after one stderr line over 1 MiB, an upgrade replaces the extracted sidecar files instead of layering over the old ones, and a sidecar still running is no longer reported as having died.
- **Notifications post once, ping only when they should, and keep titles from smuggling in links.** A webhook written with a trailing `/` or `?`, on the `ptb.` or `canary.` host or with its query reordered now counts as one target instead of getting every embed once per spelling, `discord://ID/TOKEN/?thread_id=…` posts to its thread, and the RSS and DECAPI monitors share one "Channel Not Responding" alert per outage. With the default mentions, all-clears such as "BotGuard Sidecar Restored" pinged like the alert they close; a close now pings only when listed in `mention_events` itself (the authentication all-clears under a new `auth_recovered` event). Titles and channel names are escaped in every embed, square brackets included, so `[Claim prize](https://…)` no longer renders as a link with a hidden target, and a Discord rate limit that outlasted the retries no longer drops the rest of the queue.
- **Edit-mode lifecycle messages stay on the right message and reach their final state.** Re-adding a deleted job reused its video ID and edited the old job's message far up the channel, and deleting an active job during heavy traffic could leave its message at "Downloading". A failure that sends no Job Failed report left the message at "Found", a late "Found" could overwrite a later state, unmuting a webhook mid-delivery opened a second message, and a failed job re-created a status message you had deleted. Each now edits the job's own message to its final state, in order, and embeds and History lines show when the event happened rather than when it was delivered.
- **Disk alerts fire on time, stop flapping and report the right sizes.** A volume sitting on a threshold sent a Warning and a Recovered every six minutes; an alert now holds until usage falls two points below its line, and a volume already full at startup is reported at once. On Linux, free and total space were inflated up to 256-fold on CIFS mounts, and on Windows they were read from the drive root, so a recordings disk mounted into a folder on `C:` never alerted. Startup also clears stale part-merge folders and import upload spools (up to 500 MB each) from the temp directory.
- **`moombox.log` keeps every line, and each job's log keeps its last ones.** When stdout stopped accepting writes (an SSH hang-up, an exited `| tee`, a Windows child without a console), every later line was left out of `moombox.log`, and on Linux the broken pipe killed the process and every recording with it; the file now gets each line first, and a dead console is just a failed write. A failed job's final error line now reaches its own log, lines no longer appear twice in the Logs panels across reconnects, and a panicking API call is logged and answered with a 500 instead of an empty success. Startup errors reach the log file too and no longer end with "Press Enter to exit..." under Docker or systemd, and crashes caught in background tasks are logged instead of printed over the TUI or lost.
- **The dashboard and the TUI show each job as it is.** Two quick updates could arrive in reverse order, putting a muxing job back to Downloading for the whole mux or reverting a rename or Watched toggle; updates are now numbered and stale ones dropped. Any status change replaced a job with a copy missing its parts, trims and gaps, and the TUI's `A W` could never unmark a job. Mark Watched on archived rows, a job finishing with `hide_finished_age_days = 0`, an open dialog's Resume and Mux buttons after a resync and the Player's recording list now update as they should, and a database error no longer reads as "job not found" and makes jobs vanish.
- **Dashboard actions act only on what you can see and still mean.** A filter now deselects the jobs it hides, and batch actions and the single Delete and Cancel re-read their jobs after the confirm, skipping and naming any that changed (an Error job a monitor had retried used to be deleted mid-download). The filter bar no longer turns a half-typed token into a chip, a query it rewrites keeps its meaning, and `status:constructor` no longer freezes the lists. Ctrl, Cmd and Alt shortcuts belong to the browser again (Ctrl+C copies, Ctrl+F finds), and Enter on a button no longer also opens the job behind it.
- **The TUI acts on the job you meant.** The confirm key of `A D`, `A C`, `A M` and `A S` re-read the job under the cursor, so a click, a scroll or a deletion on the dashboard within the 3-second window could delete a different job; it now acts on the job its prompt named. The details panel follows the cursor after a search or when finished jobs fold into the archive, a filter or collapsed archive drops hidden rows from the selection, batch prompts count only the jobs the chord applies to, and a chord that does not apply cancels and says why instead of leaving its prefix armed. Dialogs act only on their own results, and `R N` offers `U` only beside a pending update's notes.
- **The TUI's import picker can no longer crash Moombox, and keys and fields work as labelled.** Reopening `A Z` in a folder with fewer archives crashed the TUI, and with it every recording in progress, and a large archive was reported as timed out after 30 seconds while the server was still importing it (a retry then failed with 409). Space never reached its bindings, so tasks could not be ticked for a batch and the notification editor's toggles were inert; Add Video with a start or end time always failed, and now sends times as seconds and accepts fractions such as `1:59.5`; and on Settings → Paths a lowercase `i` opened the FFmpeg installer instead of being typed, which now moves to Ctrl+O and asks before discarding unsaved edits. Text fields open with the cursor at the end of their value, Settings fits an 80-column terminal, the action menu pages with PgUp/PgDn/Home/End, and the restart banner names `R P P`.
- **Trims to the end of a recording are no longer refused, and a trim never overwrites another.** A recording whose length was not a whole number of seconds refused a trim ending at its very end with "end time (3600s) exceeds video duration (3600s)". A failed database read was treated as "no trims yet", letting a new trim overwrite one on disk; the trim is now refused with the reason. A slow trim's result no longer closes another job's trim dialog, and the trim editor explains a preview it cannot load, resets out-of-range times and moves its handles with the arrow keys.
- **Turning HTTPS off no longer traps browsers in a redirect loop.** A browser that had used the dashboard over HTTPS kept its year-long HSTS pin and bounced between the two schemes until `ERR_TOO_MANY_REDIRECTS`; the redirect back to http:// now clears the pin. A mismatched certificate and key are warned about once instead of on every handshake.
- **UI polish.** On the dashboard, archived rows, dialogs and error lines fit phones and tablets, the offline indicator no longer sticks after a quick network flap, Stats totals count every job and their storage figures add up, and the Player no longer offers to resume a watched video from its end, lets its resume prompt capture keys on other tabs, or stops playback on a failed fetch. In the TUI, the browser-opening chords no longer leak a process on every press, dialogs fit 60-column terminals and wide emoji, hints name keys that exist, Tasks sort accented titles as the dashboard does, and a paused log view stays on its lines as old ones are evicted. The yt-dlp plugin status shows each port's scheme, and the output-template preview shows the date, time and extension a recording actually gets.

## Internal

- **Database schema 21.** Nothing in the tables changes, but the version moves, and as always an older Moombox refuses to open a newer schema: once 2.9.0 has opened a database, 2.8.x will not start on it.
- **Releases publish only after the full test suite passes on the tagged commit.** The release workflow runs CI as a required job, refuses a tag that does not match the version in the code, fails if any asset is missing, runs the built Linux binary to check its version, and verifies every signature and the manifest against the updater's public key before uploading. The Docker image is published only after the release succeeds, and a manual run is a dry run that exercises the whole pipeline, upload included, against a draft release it then deletes.
- **CI builds the sidecar payload from the commit and runs the race detector over the whole module.** A cache keyed without the sidecar's sources could hand CI an old tarball; the payload is now rebuilt on every run, and a test fails when the embedded tarball does not match `bgutil-sidecar/` (run `node build.mjs` after pulling). The race step now covers `./...` with its own timeout, and three data races it found are closed.
- **Build hygiene.** Shipped binaries are built with `-trimpath`, so panic stacks carry no CI runner paths. CI checks that the Dockerfile's Go version matches `go.mod`, Dependabot now also covers the web test harness and checks GitHub Actions daily instead of monthly, and a weekly govulncheck and npm audit runs outside CI. `fetch-node` rewrites an out-of-date `version.txt`, the sidecar signature probe fails on a bad player download and cleans up after itself, and the embedded sidecar's `source-map-js` moves to 1.2.2 for a denial-of-service advisory.
- **README, BUILDING and `config.example.toml` match the code.** The Quick Start names `O W`, `hide_finished_age_days` sits in `[monitors]` (it was ignored where the README put it), the example config shows every setting including `[disk]` and `[updates]`, and the status flow includes Queued and what `COOKIES?` covers.
- **The specification matches the code again.** SPEC.md and `docs/spec/` were corrected wherever they had drifted, and new docs tests keep the schema version, database methods, WebSocket frames and notification event lists in step with the code.
- **Dead code removed.** Unused functions, fields and URL constants went, among them the importer for the TypeScript-era `moombox.json` and unused smoothing, fuzzy-match and version-parsing helpers. Resetting a job's segments and gaps is a single transaction, and log forwarders exit at shutdown.
- **Tests reach the code where it is called.** Several fixes whose tests covered only a helper are now tested at their call sites, so removing the call fails the suite. Token-provider tests no longer call Google's BotGuard endpoints unless `MOOMBOX_LIVE_BG_TEST=1`, and new suites cover the import's zip-bomb guards, the statistics totals and the TUI and dashboard status filters against each other.
