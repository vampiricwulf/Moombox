## Bug Fixes

- **Mux no longer fails with `ffmpeg timed out: context deadline exceeded` on long streams or slow disks.** The muxer wrapped every `cmd.Run()` with a hardcoded 10-minute inner deadline (`muxTimeout` in `internal/engine/muxer.go`), which assumed SSD speeds and short streams. Codec-copy remux is I/O bound — for a multi-hour stream at 1080p60 the staging video + audio can easily be 30–50 GB, and on a slow HDD, USB drive, NAS, or with Windows Defender real-time scanning files as ffmpeg writes them, sustained throughput drops to 30–50 MB/s, putting a 50 GB mux at 15–30+ minutes. The deadline got hit, ffmpeg got killed, and the user saw the timeout with no underlying stderr (the timeout path bypassed stderr capture entirely). Fix: drop the inner timeout entirely from `runFFmpeg` and `runFFmpegWithProgress` — the parent context already handles shutdown and job-cancel cleanly, and codec-copy with a closed stdin doesn't hang. Error message renamed from "ffmpeg timed out" to "ffmpeg cancelled" since the only remaining trigger is caller-side cancellation. The detached background-mux deadline used by quality splits (`internal/worker/quality_split_common.go`) is raised from 5 minutes to 2 hours for the same reason; it stays bounded because that goroutine intentionally runs detached from job ctx (so user-cancel doesn't orphan a partial output) and a truly stuck ffmpeg there could otherwise pin shutdown via `wg.Wait()`.
