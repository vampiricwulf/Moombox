## Features

- **Notifications raised during a network outage are held and sent when it ends.** A notification raised while the connection was down (a Job Failed for a job the outage failed, a Finished for a mux that completed offline, an update or crash-recovery notice at an offline start) spent its three attempts on the dead link in about seven seconds and was dropped. Delivery now pauses while the connectivity monitor reports offline, a send already under way waits where it is, and the backlog goes out in order once the link is back, each held message marked "Delayed by a connectivity outage — raised <time>"; an edit-mode target still keeps one message per job, with a Delayed field on a held rewrite. A queue that fills while held drops its oldest messages, lower-priority ones first, and says so in one "Notifications Dropped During Outage" embed. Anything still held at shutdown is discarded with a warning in the log.
- **One Outage Alert per outage, and Twitch captures ride out a short drop.** A link that dropped two polls in three sent an Outage Alert at every restore, about one every 15 seconds, and every drop cancelled each live Twitch capture into its outage recovery, with a broadcast re-check and a "Twitch Download Resumed" each time. The Outage Alert is now sent once the link has stayed up for two minutes, and a drop inside that window belongs to the same outage, so a flapping link sends one alert whose Duration adds up the time offline and whose new Flaps field counts the drops. Outages under 60 seconds in total send nothing, and a link that never settles is reported every 30 minutes. A live Twitch capture waits out a drop of under a minute in place and has its chat reconnect at once, and the Resumed notice after a longer one counts from when the link went down.
- **A crash's cause reaches `moombox.log`.** The crashes the launcher restarts Moombox after are reported only on the console (in TUI mode, a screen the restarted TUI then cleared), so the log said only `previousExitCode=2` and Recovered From Crash told you to check logs that held nothing more. A crash is now also written to `moombox-crash.log` beside the log. The next start logs an ERROR with the cause (for a fatal error, including a stack overflow or running out of memory, the function it struck in) and the first 8 KiB of the trace, with URLs cut to their site and PO tokens removed, and keeps the whole trace as `moombox-crash.log.1`, up to 1 MiB, replacing the one before. Recovered From Crash names the cause and that file, or says the process left no crash output, as after a `kill -9` or the out-of-memory killer.

## Improvements

- **Docker: the image's guidance is in `/data/README-docker.txt`.** The image wrote its explanation of the seeded settings as comments in the `config.toml` it creates, and Moombox's first start erased them, as every save does: `config.toml` is written out without comments. The guidance now goes to `README-docker.txt` beside `config.toml` (`./data` on the host with the shipped compose file), which no save touches. Each new image refreshes it while it still holds an image's text word for word; once you edit it, your copy is kept and a newer image's text goes to `README-docker.txt.new` beside it, once. Move that over your copy to take it, or delete it to keep your own.
- **Update prompts offer only what can work.** Update Now is disabled for a dashboard viewer that is not on the host, with a line saying updates install from a browser on the host itself or its TUI, or in Docker by pulling the new image; it used to fail every time with "update apply restricted to local origins". A browser on a Docker host, which the container also sees as remote, gets the same advice when it presses it, and Skip stays available to every viewer. The update dialog sends one of Update Now and Skip at a time, so one no longer hides the other's failure. In the TUI, `R N`'s notes stop offering `U` and `S` once their release has been skipped, applied or withdrawn elsewhere or replaced by a newer one, and say which.
- **Paths pasted with quotes are accepted where a path is typed, and refused as settings.** Explorer's "Copy as path" wraps a path in double quotes, and terminals quote a dropped file. `E I`, the TUI FFmpeg screen's custom-path and manual-install prompts and the dashboard's FFmpeg path check now take one pair of surrounding quotes off; the check used to answer that the executable must be named `ffmpeg`. A setting entered with quotes, such as `"E:\Archive"` as the output directory (on Windows a relative folder with `"` in its name, which failed every mux), is refused with "cannot be wrapped in quotes" by the dashboard, the TUI and both setup wizards.
- **A waiting stream costs one YouTube request fewer every half hour.** While a scheduled stream was six hours or more away, the waiting loop's schedule check, a YouTube call of its own that carries your cookies, ran just ahead of the periodic full fetch, which reads the same schedule. It now runs after the full fetch and stands down on any tick that fetch answered, filling in only when it fails, and the full fetch's own answer starts the download when the stream has begun.
- **`connectivity.probe_targets` entries that can never work are refused.** `1.1.1.1:` (port 0), `1.1.1.1:99999` or `:443` passed the check. A list of the first kind failed every probe, so Moombox never came online and every monitor and the backlog scheduler stood still; an empty host or `localhost` dialled this machine, so a machine serving that port itself never saw an outage. The dashboard and the TUI now refuse a target without a valid port (1–65535 or a known service name) or one that names this machine, naming the entry, and a config file holding one starts on the default targets with a warning.

## Bug Fixes

- **A damaged fragment in a live recording no longer cuts the archive short and deletes the rest.** A live capture is staged as one fragmented MP4 stream, and one damaged fragment in the middle of it (zeroed, torn, or an HTML error page served as video) made the mux stop there without an error. The check that the archive is complete asked FFmpeg about the staged file, which stopped at the same place, so a recording cut at a third of its length was written Finished and its staging, the only copy of everything after the damage, was deleted. Moombox now reads the staged fragments itself, muxes from a repaired copy that leaves out only the unreadable bytes, and checks each track of the archive against the fragments' own timeline. The archive finishes with a short gap where the damage was: the job log names its time and length, the Download Finished notification reads "Archived with a gap" with a Gaps field, the job's details in both UIs say why its staging is kept, and staging keeps the original bytes. A backlog VOD whose repair finds no room on the staging volume goes back to Queued like any other out-of-space mux.
- **A crash during a mux can no longer leave a corrupt archive or delete the recording.** When Moombox died mid-mux (out of memory, a fatal error, its process killed), its FFmpeg kept running, and the restart's re-mux wrote into the same file beside it: the archive looked whole, played as garbage, and the staging cleanup then deleted the only good copy. FFmpeg and ffprobe now end with Moombox on Linux and Windows, and every archive, part, merge, set-aside recovery and trim is written under a temporary `.moombox-tmp-` name and renamed into place only once FFmpeg has succeeded (and, for an archive, a part or a set-aside recording, once the result has passed its length check), so a failed or cancelled mux never leaves a half-written file under the archive's name. Each start removes leftover temporary files, also beside archives left outside a moved output directory and in their trim folders, but never one that another running instance sharing the output tree is still writing.
- **A shutdown or restart during a live Twitch capture resumes it.** The capture was written Muxing however it stopped, so a Stop, a settings restart or a self-update mid-broadcast left it Muxing, and the next start muxed the partial capture as Finished and never went back to the broadcast. It now keeps its status and staging, and the next start resumes it while the broadcast is still live. A broadcast that ended cleanly could also land in Error, with nothing to mux it automatically, when a brief network drop was reported while one of its parts was still muxing; it now finalizes.
- **Recording names use the host's local time.** `${start_date}` and `${start_time}` were always formatted in UTC, so an evening stream in the Americas or a morning one in Japan was filed under the wrong day, and the `TZ` setting the compose file documents for file names did nothing. New recordings are now named in the host's time zone: the system zone on Windows and Linux, `TZ` in Docker (unset is still UTC). Files already written keep their names. The output-template examples in Settings and the first-run wizard now show the host's date rather than the browser's.
- **Jobs wait out a network outage instead of failing into Error.** A start with no network (a PC back up before its router), or a job whose first fetch or download setup met an outage, went straight to Error (a backlog VOD aside) and nothing retried it, so a scheduled YouTube stream went unrecorded and the rest of an interrupted Twitch capture was lost. Such a job now keeps its status under "Waiting for network connectivity... (elapsed)", shown as a wait in the TUI, and tries again once the network is back. A fetch is never held back on the connectivity monitor's word alone, and one that failed while the monitor still reads offline is tried again after a minute, so a monitor stuck offline (its `probe_targets` blocked by a firewall) stops nothing. A Twitch live job that could not reach Twitch on a working network is re-initialised by the Twitch monitor when it finds the broadcast live, and a shutdown in the middle of a Twitch VOD's fetch no longer ends the VOD in Error with "context canceled".
- **YouTube chat survives a network outage.** The chat downloader counted every fetch that failed while offline toward its error budget and gave up for good after about 75 seconds on a replay and about 15 minutes live, so the rest of the replay, or every message after the outage, was missing from the archive. It now waits for the network and continues where it stopped, as Twitch VOD chat already did; an error the chat server actually answered still counts.
- **Rate limits and bot walls no longer take Moombox offline.** A YouTube 429 or bot-wall 403, a 5xx, or a Twitch 429 or 401 counted as the network failing, so a few waiting rooms answering that way plus one network blip took the whole process offline with the internet up: Twitch captures cancelled, monitors paused and an Outage Alert sent on the way back. Only failures to reach a server count now, and a connectivity probe that reaches its targets brings Moombox back online at once. The TUI's status bar also shows OFFLINE from the start when Moombox boots without a network, where it showed nothing for the whole outage.
- **Ended broadcasts are no longer taken for upcoming ones.** A finished stream YouTube lists without formats (behind an age gate, "This live stream recording is not available", or with its formats withheld) read as upcoming to the monitors: an archived one logged "archive: creating job" and "Video found" every five minutes, a newly found one sat Upcoming for good instead of being treated as a past broadcast, and DECAPI probed a channel's newest such video every 15 seconds. The end is now read from the broadcast's own flags. When only a weak sign says it ended, one signed-in check confirms it; an end that cannot be confirmed (no cookies, an error) makes no job and is checked again after an hour, six hours, then daily, and a stream that resumes on the same video is still picked up on the next cycle.
- **Membership and status checks carry the session of the account whose cookies are loaded.** The quick probes (a waiting room's status poll, a live recording's quality probe, the schedule probe, the feed monitor's membership and date checks) kept sending the account session the startup homepage or the last watch page named, whatever cookies were loaded by then. After `cookies.txt` was removed they sent an account's session with no cookies, and after another account's cookies were imported (`E I`, `E L`, the dashboard's import, a file replaced by hand) they paired the new cookies with the old brand-account page until a job fetched a watch page or Moombox restarted, so a membership held on a brand account read as not held. The session now stays with the account it was read under, and the first probe to see a new account reads that account's session from the YouTube homepage, again after five minutes if that read fails.
- **A Cancel stands.** The status a run writes as it moves on (Live at go-live, Downloading as the download starts, Muxing as it finishes) was written over a Cancel that had landed a moment before, and a live Twitch capture was written Muxing after every Cancel, so a just-cancelled job read Live, Downloading or Muxing in both UIs, could send "Twitch Download Starting" or "Muxing Starting", and on Twitch started the capture, until the run wrote Cancelled again. Each of those writes now leaves a Cancel or a finished outcome alone, and the run stops with nothing muxed and staging kept. A cancelled job's chat status settles instead of staying "pending" or "downloading", and Mux on a job whose cancelled run is still stopping is refused (409) until it has stopped, where it used to finish the archive and then have the Cancel written back over it.
- **Discovery and schedule notifications say what happened.** A job cancelled or deleted while its first fetch was in flight, including by removing its channel together with its pending jobs, could still send a lone "YouTube Start Time Confirmed" for a discovery never announced and briefly turn the Cancelled row back to Upcoming; it now sends nothing and stays as left. A fetch a shutdown cut short no longer sends that confirmation either, so the next start's Stream Found carries the start time on its own. A stream that began late and was already over when the waiting loop next looked was announced as "YouTube Schedule Changed", its actual start given as the new time; it is still downloaded as a VOD, with nothing announced. A discovery whose first fetch met an outage sends its one Stream Found, start time included, once a fetch succeeds.
- **Closing the terminal, a dropped SSH session or Ctrl+C shuts Moombox down cleanly.** A hangup killed the TUI or a foreground `--headless` run on the spot, with no worker drain, resume save, mux cancellation, notification flush or database checkpoint, and Ctrl+C sent to the launcher alone (`docker run` without `-t`, `kill -INT`, a supervisor signalling the main process) was ignored. Both now run the full shutdown, and a `nohup`'d run still ignores the hangup. On Linux, FFmpeg runs in its own process group, so the terminal's signal no longer kills a mux in progress and leaves the job in Error for a manual Mux: the shutdown cancels it and the next start re-muxes. A cookie refresh in flight at shutdown is cancelled and waited for (up to two seconds) instead of rewriting `cookies.txt` afterwards.
- **Stops and startup errors end Moombox as they should.** A stop that arrived during a restart's 5-second drain or the shutdown after it (Ctrl+C, SIGTERM, a closed terminal) was answered with a respawn; the stop now wins, and Moombox stops. On Linux, a launcher killed with `kill -9` keeps the single-instance lock until its child has finished shutting down, so a new start can no longer run a second Moombox on the same database beside it. A startup error in a container started with a TTY (`docker run -t`, compose `tty: true`) exits at once instead of sitting at "Press Enter to exit...", which only `docker stop`'s kill ended, and Ctrl+C or SIGTERM now ends that prompt in an interactive session too.
- **`moombox add` writes to the running daemon's database.** A relative `database_path` (the default `./moombox.db`) was opened against the directory `add` ran in, so `moombox -config <the daemon's config> add <id>` from anywhere else either said "Start the Moombox daemon first." while it ran, or wrote into some other `moombox.db`, printed "Added" and sent Job Added for a job the daemon never saw. The daemon now records the database it opened in `moombox-daemon.json` beside its single-instance lock. While it runs, `add` uses that database and refuses, naming both files, a config that points at another; with no daemon running, a relative path that names no database is refused with the absolute path it tried. A video ID that begins with `-` is now taken as the target (`moombox add -XyZ123abcd`) instead of an unknown flag.
- **A dashboard Settings save no longer undoes changes made elsewhere.** The full-form Save, and every notification card, sent the whole form and the whole target list as the page had loaded them, so a setting or notification target the TUI changed while the page was open was put back by a dashboard save of anything else. The dashboard now sends only the fields you changed ("No changes to save" when there are none) and each target change as an edit the server merges, as the TUI already did, and Restart Required asks only after a save of a restart-needing field you changed. "Filter..." on a target with no event filter opens the event chips without saving a filter that lists every current event, which would miss events a later release adds, and "Clear filter" removes such a filter that an earlier "Filter..." saved. For API clients, `PUT /api/config` no longer replaces the notification target list whole: send `notification_edits`. A whole list is still accepted, and ignored, when it matches the live one, so a tab still open from before the update can save.
- **Quality-split recordings are merged into one file with the default output directory too.** The lossless merge of a split recording's parts never worked with a relative output directory such as the default `./output`: FFmpeg looked for the parts beside its temporary list file, the merge gave up with only a Debug line, and the recording stayed split. Docker installs (`/data/output`) and any absolute output directory were not affected.
- **An output directory at the root of a drive works on the dashboard, and long Windows paths are probed.** With the archive on its own drive (`E:\`, `\\nas\share\`, `/`), every player, thumbnail, chat and Open Folder request answered 403 and every import failed with "invalid output path". On Windows without long-path support, an archive path of 260 characters or more was muxed but not probed, so the job finished without resolution or duration, the short-output check was skipped, a part merge gave up, and a trim fell back to 128 kbps audio.
- **Zips made by Windows' Compress-Archive import the same on every host.** PowerShell 5.1 writes a folder's entries with backslashes, which the Linux build and the Docker image read as part of the name, titling a recording "Folder\Stream" and storing it as `Folder_Stream [id].mp4`. A backslash is now a folder separator everywhere, and re-importing such a zip after deleting its job adopts the files the old reading wrote instead of storing a second copy beside them.
- **Large trims and imports no longer fill the system temp directory.** A trim across the parts of a split recording re-encoded each part in the temp directory, and an import spooled its upload, up to 500 MB, there too. In Docker that is the container's writable layer, which no disk alert watches, and on a tmpfs `/tmp` it is RAM, where a long trim or a large import failed with "no space left on device" however much room the output disk had. Both now work beside their output (the trim's own folder, `imports/`), and the startup sweep clears day-old leftovers there and in the temp directory.
- **Link-local IPv6 clients count as LAN, and the docs say the dashboard listens on IPv6 too.** The dashboard listens on IPv6 as well as IPv4 wherever the host has IPv6, Docker included; it always did, though the docs said IPv4 only. On `lan`, a ULA (`fc00::/7`) or link-local (`fe80::/10`) client is admitted and a global IPv6 client gets 403, which browsers do not retry over IPv4, so a LAN device on a global IPv6 address should reach the dashboard by the host's IPv4 address. Link-local clients were refused on `lan` and asked for the password, because the interface suffix on their address (`fe80::1%eth0`) was not understood; they are now treated as the LAN clients they are.

## Internal

- **Database schema 23.** Feed entries gain the schedule for re-checking an unconfirmed broadcast end. As always, an older Moombox refuses a newer schema: once 2.9.6 has opened a database, 2.9.5 will not start on it.
- **Dependencies.** bubbletea 2.1.0, charmbracelet/x/ansi 0.11.9, go-runewidth 0.0.31, modernc.org/sqlite 1.60.1 (libc 1.77.1), golang.org/x/crypto 0.58.0, x/sync 0.24.0 and x/text 0.43.0, and jsdom 30.1.2 in the BotGuard sidecar and the web test harness.
- **Tests stay off the network and out of the source tree.** The worker suite sent 180 real thumbnail fetches per run, which waited out their timeouts on a runner without internet; it and the YouTube suite now fail on any request that leaves the machine, naming the host. Every tested package now fails its run when its tests leave files behind in the source directory.
- **The test suites are consolidated and steadier.** The worker package's tests share their helpers, near-duplicates are merged into tables, tests that could not fail now can, and tests another one already covers are gone. Fixed: a throughput test whose wall-clock budget measured the runner, two player tests that relied on jsdom focusing hidden elements, and a feed-history test that could start its re-scan before the first scan had finished, which the race detector's slower scheduling exposed. The goja BotGuard live check runs under its own `MOOMBOX_LIVE_GOJA_TEST`, so a `MOOMBOX_LIVE_BG_TEST=1` run can pass when the sidecar works.
- **The docs match the code.** Every build doc names go1.27.2 as the toolchain floor, pinned to `go.mod` by a test. SPEC.md and the architecture docs give the launcher's real exit rules (an update whose first boot fails is rolled back, a fresh launch that dies within 60 seconds fails fast, any other crash is respawned up to five times in a row) instead of "exits on anything but 42", the docs state yt-dlp's current default YouTube clients correctly and list Moombox's own client ranking in its current order, stored job paths are described as written rather than absolute, and the package figures have one maintained copy.
