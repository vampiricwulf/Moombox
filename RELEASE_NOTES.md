## Features

- **Docker/headless cookie recovery.** A container operator can now hand Moombox a fresh `cookies.txt` directly through the dashboard — paste it or upload the file — to recover a dead session without a local browser. A new `POST /api/cookies/import` endpoint does the work, and the existing re-login prompt now links straight to it.
- **TUI cookie login (`R L`).** Start the cookie login flow from the TUI at any time, not just during first-run setup. First-run setup can also be reopened at just its cookie step, without repeating the rest of the wizard.
- **A real liveness check for YouTube sign-in.** Moombox can now test whether a saved session is *actually* still signed in — a channel-membership probe and a channel-independent account probe — instead of only checking that a cookie file is present. The channel-independent probe means this works even on an install with no monitored channels configured.
- **Twitch gets its own liveness probe.** Previously Twitch had no way at all to detect a dead session between capture attempts. It now reuses the same playback-access-token request the downloader already makes as a session-liveness signal.
- **Twitch chat auto-recovers from a credential downgrade.** When a live chat session loses valid credentials, Moombox now marks the platform, tells the operator once per job (the current download is unaffected, but the next capture would start anonymous), and reconnects chat automatically with the corrected credentials as soon as they're fixed — no restart required.
- **A browser-free cookie-refresh mode (`cookies.acquisition`).** A new `auto` / `profile` setting in `config.toml` — with matching controls in the dashboard settings panel and the TUI settings overlay — lets an operator choose how Moombox refreshes a session's cookies. `auto` is the default and keeps today's behavior: launch a browser when one is available, otherwise fall back to a profile import. `profile` never launches a browser for a refresh — every refresh instead becomes a browser-free read of the configured profile directory, whether that's a real desktop browser profile or one mounted into a container. The safety guard that refuses to drive a real browser profile headlessly still holds in every mode, and this browser-free read is now allowed only once an operator has explicitly opted into `profile` mode. The "Force Refresh Cookies" pre-flight message (TUI `R F` / the dashboard's refresh control) now names which of the two mechanisms is about to run.
- **The automatic liveness-recovery pilot is ARMED in this release** (`livenessRecoveryArmed = true`). A liveness check that finds a session genuinely signed out now triggers recovery instead of only logging the verdict. With automatic cookie refresh on, that is one headless browser refresh under a two-minute timeout — silent if it works, otherwise a "Cookie Auto-Refresh Failed" or "Cookie Auto-Refresh Ineffective" notification. With automatic cookie refresh off, no browser runs and a "Cookie Re-Authentication Required" notification naming the cookie file is sent immediately. A session that stays dead re-alarms on a per-platform back-off — 30 minutes after the first alarm, doubling each time, capped at 24 hours, reset the moment a check comes back signed-in — and a loss already raised by the periodic auth check or by a Twitch chat downgrade will not be raised a second time by a liveness verdict. The switch is a source constant rather than a config setting, so if a liveness check ever reports a working session as dead, the only way back is a rebuild with it set to `false`.

## Improvements

- Firefox cookie setup now closes its own browser window when you finish or cancel setup — it used to stay open.
- The TUI cookie-setup countdown was extended from 60 seconds to 300 seconds, giving more time to complete a login before it times out.
- The manual "Force Refresh Cookies" action (TUI `R F` / the dashboard's refresh control) is no longer hidden or disabled when automatic cookie refresh is turned off. It now always works, falling back through a browser refresh, a profile import, or an in-process refresh depending on what's available.
- Turning on automatic cookie refresh and then completing setup no longer requires a restart before the periodic browser refresh actually starts.
- Cookie status checks no longer re-scan the filesystem and Windows registry on every poll.
- The sign-in liveness re-alarm backs off per platform (30 minutes after the first alarm, doubling each time it re-fires, capped at 24 hours, reset the moment a check comes back signed-in) instead of re-firing on a flat 30-minute clock. This is the cadence the now-armed pilot below runs on.
- The startup `Cookies loaded` line and the cookie-refresh success line now report each platform's auth-cookie horizon and the Twitch `login` cookie's expiry (timestamps only, never a cookie value), and a warning now fires if an expired Twitch `login` cookie gets pruned during a refresh while an `auth-token` cookie survives — the half-credential shape that leaves chat capturing anonymously.
- The cookie-refresh result on both the dashboard and the TUI now says which mechanism actually ran — a browser refresh or a profile import — instead of always saying "Browser cookie refresh," even on a pass that never launched a browser.
- The startup log no longer logs an ERROR saying Moombox is "refusing to launch" a headless browser against the configured profile directory when `cookies.acquisition = "profile"` is the intended configuration; that configuration now gets a plain INFO line naming the read-only import that runs instead.
- The setup wizard now shows its accepted sign-in verdict inside the wizard itself, not only on the status line behind it, so the confirmation stays visible while the overlay is still open.

## Bug Fixes

- **The automatic browser-based cookie refresh could report success without refreshing anything.** It exited as soon as it launched a browser, before that browser had actually finished, so a "successful" refresh could have renewed nothing at all. It now waits for the real browser process and reports success or failure per platform.
- Fixed several ways a cookie refresh or save could silently destroy working credentials: a blank `Set-Cookie` response, a partial write, or a transient read error could each wipe out a cookie file that was still valid instead of leaving it alone.
- Closing the cookie-setup browser window (or its tab) no longer leaves cookie acquisition stuck. Moombox now checks whether the browser process itself exited, instead of the launcher process that spawned it.
- The cookie health badges (dashboard and TUI) no longer report an inconclusive check — a network hiccup, a redirect, an unreadable page — as if it were failed or dead credentials. A parked job now reddens its own platform's badge instead of always blaming YouTube, and a failed check no longer aborts a settings save.
- **Twitch live chat could never actually log in.** It always joined anonymously (as `justinfan...`), even with valid credentials configured. It now authenticates with the saved account, and a reconnect after a dropped connection stays authenticated instead of falling back to anonymous.
- YouTube and Twitch cookies are now kept in two fully separate stores instead of one shared map keyed by cookie name, closing a possible cross-platform mix-up. Downloads and live chat also now read the current cookies at the moment they're used, instead of a stale copy captured when the job started.
- Fixed the Windows credential-decryption (DPAPI) browser filter incorrectly excluding Brave and Edge cookie profiles.
- First-run platform detection no longer misreads a configured-but-broken YouTube or Twitch login as "never configured" — this could permanently disable the auth-loss notification and automatic recovery for that platform.
- Orphaned temporary cookie-file writes left behind by a crash are now cleaned up automatically, and a failed permission-hardening attempt now retries on the next write instead of giving up for the rest of the run.
- A panic while loading cookies at startup can no longer take down the whole process, and two automatic cookie refreshes can no longer run at the same time and race each other.
- Fixed several cookie-merge edge cases around `Set-Cookie` parsing, deletions, and declined updates that could silently drop or misapply a cookie.
- When automatic cookie refresh is disabled, Moombox now notifies the operator when a session is found to have gone from working to signed-out — previously this case was completely silent.
- An unrecognizable response body from YouTube's guide check is now treated as inconclusive instead of being read as proof the session is dead.
- A declined cookie refresh (for example, one already in progress) is no longer reported as a failure.
- The cookie merge key now includes a cookie's path in addition to its name and domain, so two different cookies that share a name and domain but live at different paths can no longer overwrite each other.
- Abandoned or cancelled cookie-setup browser processes are now cleaned up on Linux and in Docker. Previously this reaping only happened on Windows, so an abandoned setup could leave a browser process running indefinitely elsewhere.
- Fixed the pre-mux wait for a possibly-resuming interrupted stream: it could get pinned to its maximum timeout just because live chat outlived the stream. It now releases as soon as both chat and the segment downloader have gone idle together. (Not related to cookies.)
- A Twitch GQL response body — which an intermediary's error page could fill with echoed headers — never reaches a log line or an error string any more: `gqlRequest` now renders a byte count, and the retry line logs the status.
- The chat downloader's resume signal now closes the moment the orchestrator marks a stream ended, instead of waiting for the chat loop's own exit, and a poll result landing after any exit can no longer re-open it. This is a contract-robustness fix — the arc-close review found no operator-visible behavior change today.
- The browser-based cookie refresh can now roll a platform back to its previous cookie file when a real regression is detected — verified working before the refresh, failed verification after. Previously the browser path had no rollback at all, so a credential that broke mid-refresh (for example, a session signed out mid-flight) left the broken cookies in place with nothing to catch it. An inconclusive check (a network hiccup, a redirect) still never triggers a rollback on this path, since a browser refresh has just re-fetched from the live site and a blip afterward is evidence about the network, not about the cookies.

## Internal

- Extensive documentation and test-coverage pass bringing `SPEC.md` and `docs/spec/` back in sync with the cookie subsystem's actual behavior after the fixes above.
- Internal-consistency fix pinning the YouTube WEB client's version string to a single source instead of a duplicated constant that could drift.
- Planning-tracker and process-documentation updates for the cookie-subsystem remediation effort itself; no behavior change.
- Internal-consistency fix splitting the cookie-profile safety guard into a launch-specific check (`validateBrowserProfileDirForLaunch`, unchanged behavior at every browser-launch site) and a separate read-only-import check for the two profile-read-only call sites, which now refuses with its own `ErrProfileDirNotOptedIn` reason instead of borrowing the launch guard's message. Guard and settings-panel test coverage was also hardened to assert the actual error returned and the real rendered markup, rather than a loose "no error" or substring check.
- The shared last-new-segment clock's only write site is now an extracted, tested function (`noteSegmentProgress`); behavior is unchanged.
- The `Platforms` config comment now states the real seeding rule, and `*.css`/`*.svg` are pinned to LF alongside the existing text-asset rules in `.gitattributes`.
- A citation-rot test (`internal/docs`) now guards the six spec docs against stale citations; it found and fixed five on its first run.
- `authStatusChanged`'s contract — which fields can move a platform's push-notification verdict on their own — is now pinned by two new table-test rows; previously a gate that dropped either platform's `Authenticated`-boolean comparison alone would have passed the entire existing test suite undetected.
- The Twitch credential mark's recovery-dedupe stamp is now directly asserted by a test, closing half of the automatic-recovery pilot's ARMING checklist (row 12); the arming change in this same release closed the other half, pinning that one chat-marked Twitch loss plus the liveness verdict that follows it trigger recovery once, not twice.
- The TUI's feedback message, severity, and expiry timer — previously three separate `App` fields kept in sync by convention — are now one struct written as a single value, so a stale message can no longer outlive its own severity by construction.
- A new test walks the TUI and startup wiring code itself and fails if any of the five call sites that re-check cookie health after a write is ever moved out of its `defer`, or if a new credential-writing site appears with no decision made about its shape.
- `RefreshResult` gained a `Mechanism` field, threaded through every return path by a single deferred assignment instead of edited at each return site individually, and surfaced as an additive `mechanism` key on the dashboard's cookie-refresh-outcome payload — the shared source both of the mechanism-naming fixes above read from.
